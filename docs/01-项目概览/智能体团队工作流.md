# 智能体团队工作流

## 1. 范围与授权

本规约用于 DG-OS 的 herdr 开发团队，内部工程任务为 `ENG-HERDR-TEAM`。用户于 2026-11-01 授权建立团队、角色、布局和工作流；这不是自动开发全部产品功能、自动合并、付费外部调用或发布授权。没有具体任务包时，角色只读入职并待命。

团队遵循 [AGENTS.md](../../AGENTS.md) 与[文档入口](../README.md)。本规约不取代功能规格、OpenAPI、migration、冻结决策或版本实现状态。herdr 的 idle/done 是运行状态，不是 AC 通过或功能完成。

## 2. 角色与布局

角色与程序的机器配置在 [team.json](../../tools/herdr-team/team.json)，专属说明见 [团队工具入口](../../tools/herdr-team/README.md)。模型使用现有工具默认值，不猜测或统一覆盖模型。

| 角色 | 职责 | 默认工作区与边界 |
| --- | --- | --- |
| lead：调度与集成 | 用户入口、分级、拆片、依赖、资源与集成队列、汇报 | 控制仓库；不直接开发业务，不改动用户现有修改 |
| spec：规格架构 | 滚动规格、AC、设计、决策草案、文档追踪与证据回写 | 独立 worktree；共享文档默认单写者 |
| rust：Rust 宿主开发 | crate、应用服务、Tauri、数据层与定向测试 | 独立 worktree；仅写任务允许路径 |
| ui：前端交互开发 | React/store、公开 API 接入、统一 UI 与前端测试 | 独立 worktree；不另造设计系统 |
| review：独立验证审查 | AC/分支验证、安全与回归审查、证据核对 | 独立 worktree，agent 默认只读；实际写缓存的测试由专用终端授权执行 |

初始五个角色，最多两个并行实现任务。专项顾问只有命中明确问题且获准后才增设，不默认常驻。每个 workspace 包含角色 Tab 和检查/测试 Tab，测试终端全宽。本机 reviewr 插件会给关联 worktree 自动增加差异查看 pane，保留它与 agent 并列，不再切出第三列；若屏幕窄，优先使用 herdr zoom 查看 agent，不关闭未知 pane。不抢用户焦点，既有项目会话不接管、不关闭。

初始 rust/ui worktree 是开发 slot，不代表已分配业务任务。一个 slot 同时只承接一个切片。下一切片前检查未提交修改、基准和分支归属；需要换基线时由 lead 创建新的任务 worktree、在新 pane 启动并重新入职，不能重置旧 worktree 丢弃工作。review 必须使用明确的候选提交或不可变 diff 快照，不能默认初始审查 worktree 包含开发者的修改。

## 3. 任务包与状态

使用 [任务模板](../../tools/herdr-team/task.template.json)，包括唯一任务 ID、目标、不做范围、L0-L3、owner、完整 base SHA、FR/AC/决策、规格引用及内容哈希、允许修改路径、依赖、验证命令与证据等级、停止条件和时间盒。L2/L3 必须关联功能或明确技术任务；权限、状态机、接口、迁移等冲突先决策再编码。

派发前，lead 与接收者显式核对实际 worktree HEAD 是否等于任务 base SHA，并逐项核对 specRefs 的内容哈希。隔离 worktree 不会自动跟随控制仓库的未提交文档；发现文档落后时停止，不能默认读取本地旧副本。lead 应提供已经确认的不可变规格上下文快照及来源哈希，或在获准后更新任务基线。快照只是复现已确认修订的交接产物，不是第二个持续维护的权威来源，也不能把 Draft 变成可开发规格。

临时任务与交接文件放 `.herdr-team/tasks/`，只记录调度阶段和产物位置，不复制一份功能完成率。任务阶段按以下顺序由 lead 管理：

```text
待澄清 -> 规格可开发 -> 待派发 -> 实现中 -> 待审查
                              ^           |
                              |--- 返工 ---|
审查通过 -> 待人工批准 -> 集成验证 -> 证据回写 -> 本切片交付
```

每次交接必须包含实际 base/head SHA；如允许未提交候选，附 `git diff --binary` 快照、内容哈希和未跟踪文件清单，最终正式审查仍以固定提交为宜。命令保存退出码、环境、覆盖及未覆盖范围。不得把上一提交的测试直接绑定到新代码；集成改变代码树后重跑受影响检查。

`check-task` 检查任务包结构、基准可解析、路径边界和规格文件哈希；它不自动证明业务规格足够、依赖已完成、审批属实或任务已通过版本门禁。这些由 lead/spec/review 核对。

## 4. 三条执行路径

| 级别 | 路径 | 验证与批准 |
| --- | --- | --- |
| L0/L1 | 简短内部说明或现有规格引用 -> 修改 -> 定向检查 -> 审查 | 不要求完整新规格；合并仍需用户明确授权 |
| L2 | 关联 FR/AC 或明确技术任务 -> 规格核对 -> 最小切片 -> 独立审查 | 按影响增加构建/契约，行为变化同步权威文档 |
| L3 | 决策/独立技术设计 -> 分支测试追踪 -> 专项评审 -> 实现与故障验证 | 权限、凭据、迁移、真实外部副作用与发布保留人工控制 |

每个任务建议 45 分钟检查点，耗时长则报告已完成、剩余、阻塞与下一切片，不丢弃工作。最多两轮自动审查返工，仍未解决则升级根因与分歧。限额和时间盒目前是调度规则，不宣称存在强制 token 计费器或后台杀进程定时器。

## 5. 滚动规格与变更协议

当前切片实现、下一切片 Draft 和上一切片验证可交错进行。只稳定正在开发的切片，不冻结整个项目。V2 草案或门禁准备不能作为全面开发授权。

发现冲突时：发现者报告位置、差异、影响和候选方案 -> lead 暂停受影响任务 -> spec 提请用户选择 -> 记录决策并同步权威来源 -> 受影响任务重新确认依据。未受影响任务继续；纯文字修订不导致全队重启。不得为迎合现有代码降低 AC。

默认由 spec 串行维护决策编号、需求编号、实现状态及文档浏览器。OpenAPI、共享 DTO、migration、错误码、lockfile 与 UI 公共导出由 lead 在任务包指定唯一写入者。多 worktree 仍共享同一个 Git 仓库对象库，不能当作权限隔离。

规格工作使用 spec-docs-pro 对应模式；安装包若无 `instructions.md`，读取 `SKILL.md` 与模式文件。项目规则优先，工程校验使用仓库 vendored 命令，不混用全局版本通过结果。

## 6. 验证资源与成本

顺序为：受影响用例 -> crate/前端测试 -> 相关契约/构建 -> 必要外部 smoke/E2E -> 切片或里程碑全量回归。只修改团队设施时不触发 Provider/MCP 真调用或产品全量回归。

真实 WebView、Vite 1420 端口、LAN 端口、应用数据目录、OS vault、发布构建由 lead 串行预约。worktree 不隔离数据库、钥匙串、端口或 app 实例锁；未证明可隔离时不能并行。单元测试使用临时库，不读写正式用户库。

资源占用用 `.herdr-team/resources.json` 临时登记持有者、任务、开始时间和命令，由 lead 唯一修改。进程仍活跃时不自动按过期时间抢占。工具脚本不强制资源锁，实际执行前须由 lead 检查登记。

静态检查、单元/mock、本地协议兼容 smoke、真实 Provider/MCP、真实 WebView、完整桌面 E2E、发布安装是不同证据。VoiceOver、第二台设备、跨平台、签名等未覆盖项必须如实保留。真实外部调用先确认费用、凭据范围及用户授权，敏感输入不写进普通交接日志。

## 7. 调度、集成与恢复

常用命令见 [团队工具入口](../../tools/herdr-team/README.md)。派发前确认目标 agent 在登记 pane，状态空闲，前台确实为该 agent。超时、stalled 或连接失败不证明未送达；先读取，不盲目重发。unknown 不当成功，blocked 先读原因，信任/授权/登录由用户处理。

不默认后台轮询、定时任务、自主拉取待办或自动合并。用户交给 lead 一个具体目标后，lead 可以在授权范围内拆片、派发、读取和审查；跨产品范围、冻结决策、额外外部成本、权限与最终合并要重新提请批准。需要事件编排时另行接入可验证的看板，不把 herdr 生命周期 API 当作完整 DAG 引擎。

集成前要求独立审查无未关闭 major/critical，相关检查通过或延期理由可见；由用户明确批准目标提交后，在干净且专用的集成分支执行，不在用户 dirty 主工作区自动合并。spec 依据已核实证据回写当前版本实现状态，生成浏览器并检查新鲜度。一个切片交付不自动使整个功能“已完成”。

恢复先检查本机登记、Git worktree 和前台进程。只恢复自己创建的角色；不停止 herdr server、不强杀、不清理别人工作区、不重置分支。配置、角色说明和工具应纳入用户后续正常提交；本机拓扑、临时报告、任务与锁不提交。

## 8. 本次建立的验证边界

本次只验证团队配置、CLI 自测、文档一致性、herdr 布局与角色入职。初始化结果以当次交付说明和本机 `.herdr-team/state.json` 为准，不预写“所有 agent 已就绪”。不运行产品外部调用、桌面 E2E、签名、安装或全量业务回归，也不提升任何 FR 的实现状态。
