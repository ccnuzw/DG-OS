## 第一部分：项目背景与老项目教训

### 老项目问题

**infinite-canvas-ccnuzw 项目失败原因**：

```python
# 问题：单文件 19,038 行
main.py (19,038 lines)
├── 167 个 API 路由
├── 684 个函数和类
├── WebSocket 管理
├── Canvas 逻辑
├── Provider 适配
├── ComfyUI 连接
├── 文件管理
├── 素材管理
└── ... 所有功能

# HTML 也是巨石
static/*.html (10,543 lines total)
├── canvas.html (359 lines + 大量内联 JS)
├── index.html (120.7KB)
└── ...
```

**教训**：
1. 没有好好规划
2. 文件太大，无法维护
3. 没有解耦
4. 没有设计好

**核心价值**：
- 无限画布是核心功能
- 需要保留交互逻辑
- 但必须重新设计架构

### 新项目目标

**DGOS 定位**：
- 本地优先的 AI 应用开发框架
- 强制模块化（避免老项目问题）
- 可扩展的应用模块系统
- Provider/Skills/MCP 作为底层能力

## 第二部分：产品定位演进

### 初始理解（错误）

用户最开始的描述：
> "我要做的是本地端软件，它也能拉起服务来供本地局域网协同，同时有一些资产和工作流是可以保存在云端的，帐号系统作为官方后台暂时只用于积分管理用于 provider 的内置推荐提供"

我的初始理解：
- 这是一个"操作系统"级别的产品
- 需要完整的桌面/窗口壳层
- 需要应用商店、manifest、运行时

### 纠正过程

用户澄清：
> "我只需要你管理标准的 Skills，能从远程仓库拉取并安装，并且能在项目中进行管理"

**关键纠正**：
1. Skills/MCP 是**现有标准**，不需要重新实现
2. DGOS 只需要**管理和调用**，不需要**执行引擎**
3. 就像 Chrome 管理扩展，不是实现扩展引擎

### 最终定位

**DGOS = 本地优先的 AI 应用开发框架**

```
核心能力：
├── Provider 适配（统一接口，多厂商）
├── Skills 管理（安装、调用）
├── MCP 管理（连接、桥接）
└── 模块系统（热更新、权限管理）

应用模块：
├── AI 工作台
├── 无限画布（分多版本）
├── 系统设置
└── 第三方模块...

运行模式：
├── 单机模式（默认，完全本地）
├── 局域网模式（一台做服务器）
└── 云端模式（可选增强）
```

## 第三部分：技术栈决策过程

### 数据库选择

**问题**：PostgreSQL vs SQLite？

**初始建议**：PostgreSQL（因为老文档用了）

**用户澄清**：
> "数据库可以用 SQLite，并且我不需要复杂我租户系统"

**最终决策**：SQLite
- 理由：本地优先、零配置、单文件
- 记录：D002

### QuickJS 的误解

**我的错误理解**：
- 需要 QuickJS 运行 Skills/MCP
- 需要实现 JavaScript 沙箱
- 需要执行引擎

**用户纠正**：
> "Skills 和 MCP 就是标准的，不需要你再创建什么，你只需要让本地的项目能管理/导入/安装"

**最终决策**：不需要 QuickJS/Node.js
- 理由：Skills/MCP 自己运行，我们只调用
- 记录：D003

### Rust vs Node.js

**问题**：后端用什么语言？

**我的分析**：
```
Rust 优势：
✅ 强制模块化（编译期检查）
✅ 性能好
✅ 内存安全
✅ 避免单文件问题

Node.js 优势：
✅ 生态成熟
✅ 开发快速
✅ Skills/MCP 生态
```

**用户选择**：Rust

**最终决策**：Rust + Tauri
- 理由：强制模块化，避免老项目错误
- 记录：D001

### 模块热更新

**方案对比**：
- QuickJS：过度设计
- iframe：性能差
- Module Federation：成熟方案 ✅

**最终决策**：Module Federation
- 记录：D004

## 第四部分：核心概念澄清

### Provider/Skills/MCP 的关系

**初始混淆**：
- 以为都需要我们实现
- 以为需要执行引擎
- 以为是插件系统

**最终理解**：

```
Provider（我们要开发）：
├── 适配各厂商 API（OpenAI、Claude 等）
├── 统一接口封装
├── 获取模型列表
├── 给模型打标签（文本/图片/视频/音频）
└── 提供调用接口

Skills（现有标准）：
├── 远程仓库列表
├── 我们提供：管理界面
├── 我们提供：安装/卸载
├── 我们提供：调用接口（HTTP/CLI）
└── Skills 自己运行，返回结果

MCP（现有标准）：
├── Anthropic 的 Model Context Protocol
├── 我们提供：连接管理
├── 我们提供：工具列表展示
├── 我们提供：调用桥接
└── MCP 服务器自己运行
```

**使用场景**：
- Provider：必须（调用模型）
- Skills：可选增强（在 LLM 节点中可选择）
- MCP：可选增强（系统工具）

**记录**：D005

### 应用模块 vs 功能模块

**澄清**：
- 两者是同一概念
- 可以叫"应用模块"（因为独立开发、版本管理）
- 也可以叫"功能模块"（因为提供特定功能）
- 本质：可热更新的独立单元

**特性**：
```
应用模块：
├── 独立开发（独立仓库）
├── 独立版本管理
├── 热更新（无需重启）
├── 权限隔离
├── 可从应用市场安装
└── 官方模块 + 第三方模块
```

## 第五部分：关键功能设计

### 无限画布策略

**用户明确**：
> "无线发布不必在 1.0 模块完成，可以延后或分多个版本进行。因为当前重点是搭建底层能力和底层框架。"

**分步计划**：
```
V1.0: 不包含画布（框架优先）
V1.2: 画布核心（视口、缩放、拖拽）
V1.3: 10+ 节点类型、连线系统
V1.4: 实时执行、循环节点
V1.5: 工作流导入导出
```

**节点执行**：
- 实时执行（用户操作立即执行）
- 支持循环节点（LoopNode）

**从老项目学习**：
- 保留交互逻辑（手感好）
- 重做架构（避免单文件）

**记录**：D009

### Provider 多配置和排序

**用户需求**：
> "可以配置多个同类的 provider，是可以的"

**设计**：
```
用户可以配置：
├── OpenAI 账号 1（个人）
├── OpenAI 账号 2（工作）
├── 官方 Provider（积分）
└── ...

排序机制：
├── 用户拖拽调整顺序
├── 默认使用排序第一个
└── 有选择界面时可以手动选择
```

**记录**：D012

### 模型分类标签

**问题**：如何给模型打标签？

**决策**：内置维护，手动编码
```rust
// Provider 适配器中维护
match model_id {
    "gpt-4" => vec![Capability::TextGeneration],
    "dall-e-3" => vec![Capability::ImageGeneration],
    "sora" => vec![Capability::VideoGeneration],
}
```

**标签类型**：
- 文本生成（text-generation）
- 图片生成（image-generation）
- 视频生成（video-generation）
- 音频生成（audio-generation）

**记录**：D014

### 权限模型

**用户明确**：
> "权限模型不需要做得这么细"

**设计**：粗粒度模块级权限
```typescript
permissions: [
    "providers.call",      // 调用所有 Provider
    "skills.execute",      // 执行所有 Skills
    "mcp.call",           // 调用所有 MCP
    "storage.read",       // 读取存储
    "storage.write",      // 写入存储
    "network.local"       // 局域网访问
]
```

**记录**：D006

### 局域网协同

**用户需求详细说明**：

**开启方式**：
> "局域网模式始终开启"

**认证**：
> "远程设备登录需认证，请在此处设置简单认证"

**权限**：
> "远程设备不可修改 Provider 码，仅支持只读和使用"

**协同细节**：
> "多个设备可同时编辑同一画布，需注意协同细节：当 A 用户移动鼠标或节点时，B 用户的界面需实时显示。双方互动及指针均可见，指针上带有标记以区分不同用户。此外，还需设计锁等机制。"

**设计**：
```
主机：
├── 自动启动 HTTP 服务（0.0.0.0:3000）
├── 端口可配置（避免冲突）
├── 生成随机密码或用户设置
└── 管理连接用户列表

远程设备：
├── 访问 http://主机IP:端口
├── 简单认证（用户名/密码）
├── 只读模式（不能修改配置）
└── 实时显示指针和操作

协同编辑（V2.0）：
├── 实时同步节点移动
├── 显示其他用户指针（带标记）
├── 锁机制（编辑时锁定）
└── CRDT/OT 冲突解决
```

**记录**：D007、D013

### 统一设计系统

**用户强调**：
> "系统的整体样式管理和组件管理需要统一化。因为将来还会开发更多的功能模块，也就是应用。所以关于整个系统的样式框架，包括字体大小、主题等，都要进行标准化和规范化。"

> "后期开发的应用都要复用这些主题，不能每个应用一个主题，主题色、主题大小、主题配色、主题字体肯定是不行的。"

**设计**：
```
统一 Design System：
├── 主题系统（亮色/暗色）
├── 色彩规范（固定主色、辅助色）
├── 字体规范（字体家族、字号、字重）
├── 间距规范（4px 基准）
├── UI 组件库（基于 Shadcn/ui）
└── 所有模块强制复用

禁止事项：
❌ 自定义样式覆盖
❌ inline styles
❌ 自定义 CSS 变量
❌ 每个模块不同主题
```

**强制机制**：
- CI 检查（扫描代码）
- 审核阶段（人工检查）
- 模块模板（强制使用）

**记录**：D008

## 第六部分：应用市场与生态

### 应用市场模式

**问题**：应用市场如何设计？

**用户明确**：
> "应用市场必须登录云端账号才能下载，这是对的，匿名是不行的。"

> "应用市场是中心化的，对接官方服务器，不能添加第三方源，这是不允许的。"

> "审核流程为人工审核。审核系统不需要在 V1.0 里面完成，可以在后面完成。"

**设计**：
```
应用市场（V1.5+）：
├── 中心化（官方服务器）
├── 必须登录云端账号
├── 人工审核（初期）
├── 自动化检查（V2.0+）
└── 不支持第三方源

审核标准：
├── 代码安全性
├── 权限合理性
├── 视觉一致性（设计系统）
├── 功能完整性
└── 文档完整性
```

**记录**：D010

### 模块更新

**用户需求**：
> "模块的更新是自动推送的。应用市场的图标如果有更新，会有版本号显示，图标上也可以加小红点，这都是可以的。"

**设计**：
```
更新流程：
1. 后台检测新版本
2. 图标显示小红点 + 版本号
3. 用户查看更新日志
4. 用户确认更新
5. 下载新版本
6. 热重载（无需重启）
```

**记录**：D015

### 官方 Provider 积分

**问题**：如何计费？

**用户说明**：
> "官方的 provider 积分计算这个到后面再说吧。这个里面主要是图片按张计算，API 的话，有些是按照倍率，有些是按 token 数量积分的，一般图片按张，视频按秒。"

**设计**：
```
积分计费（V2.0）：
├── 文本生成：token 数量 * 倍率
├── 图片生成：按张
├── 视频生成：按秒
└── 音频生成：按秒
```

**记录**：D011

## 第七部分：版本规划策略

### 版本边界讨论

**我的初始规划**：
- V1.0 包含所有功能
- 详细的功能列表
- 完整的验收标准

**用户纠正**：
> "内容是由浅入深：V1.0 版本只需实现简单的核心功能，后续在 V2 至 V6 版本中逐步完善。因此，可以设计多轮迭代，不必急于在 V1.0 中完成所有功能。"

> "我希望提供一个良好的开发框架，以便后续快速迭代和开发。所以，设计时应注重快速推进，而非将所有功能堆砌在 V1.0 中。"

**最终策略**：
```
V1.0（3个月）：底层框架优先
├── Provider 框架
├── Skills/MCP 管理
├── 模块系统
├── AI 工作台
└── 系统设置

V1.2-V1.5：核心价值（无限画布）
├── 分步实现
├── 不阻塞 V1.0
└── 验证框架可扩展性

V2.0+：生态系统
├── 应用市场
├── 云端同步
├── 协同编辑
└── 移动端
```
