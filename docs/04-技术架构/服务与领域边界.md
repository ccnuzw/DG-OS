# 服务与领域边界

本文档定义 DGOS 的服务架构和领域边界，明确各模块的职责和交互关系。

> **实现状态说明（2026-10-28）**：本文的“服务”描述包含跨版本目标。当前代码仍处于模块化单体前置收口阶段，Transport 与 Domain Manager 之间的 Application Service / Use Case 层尚未完整建立；新增入口不得把该目标层当作已实现事实，优先遵循 [V1 架构优化评审草案](当前版本/V1-架构优化评审草案.md) 的分层边界。

---

## 1. 总体架构

DGOS 采用**模块化单体架构**（Modular Monolith）：
- 单一应用进程
- 内部按领域划分模块
- 模块间通过明确的接口通信
- 前端模块可独立加载和卸载

```
┌─────────────────────────────────────────────────────────────┐
│                        Tauri Desktop                        │
├─────────────────────────────────────────────────────────────┤
│                    React Frontend (SPA)                     │
│  ┌───────────┬───────────┬───────────┬──────────────────┐  │
│  │ AI工作台  │ 系统设置  │ 画布编辑  │  第三方模块...    │  │
│  └───────────┴───────────┴───────────┴──────────────────┘  │
│              Module Federation（FR-004 规划）                │
├─────────────────────────────────────────────────────────────┤
│                      Tauri IPC Layer                        │
├─────────────────────────────────────────────────────────────┤
│        Rust Backend（Tauri commands；Axum 为 FR-010 规划）     │
│  ┌──────────┬──────────┬──────────┬──────────┬─────────┐  │
│  │Providers │ Skills   │   MCP    │ Modules  │Auth(规划)│  │
│  └──────────┴──────────┴──────────┴──────────┴─────────┘  │
├─────────────────────────────────────────────────────────────┤
│                        SQLite Database                      │
└─────────────────────────────────────────────────────────────┘
```

当前 Rust crate 与领域的对应：`dgos-providers`（Providers）、`dgos-skills`（Skills）、`dgos-mcp`（MCP）、`dgos-workbench`（Workbench）、`dgos-modules`（模块发布，FR-004 前置）、`dgos-application`（Application Service 与 Host Capability 授权，D030）、`dgos-db`（Storage）、`dgos-types`（共享类型）。Auth、Network、UI 尚无对应 crate。

## 2. 领域划分

### 2.1 底层能力领域

**职责**：提供框架级能力，不涉及具体业务逻辑

| 领域 | 说明 | 核心功能 |
|------|------|---------|
| **Providers** | Provider 适配框架 | 统一接口调用各类 AI 模型 |
| **Skills** | DGOS 技能中心 | 官方内容包、来源适配、版本锁定、按需准备任务上下文（D016，不执行内容） |
| **MCP** | MCP 管理系统 | 连接、管理、调用 MCP 工具 |
| **Modules** | 模块系统 | 模块包发布与恢复（已有前置切片）；加载、卸载、热更新（规划） |
| **UI** | 统一设计系统 | 主题、组件、样式规范 |

### 2.2 应用模块领域

**职责**：面向用户的业务功能

| 领域 | 说明 | 核心功能 |
|------|------|---------|
| **Workbench** | AI 工作台 | 当前：单任务文本/工具任务（D018/D022）；规划：多轮对话、流式响应、历史记录 |
| **Settings** | 系统设置 | Provider/Skills/MCP 管理界面 |
| **Canvas** | 无限画布（V2） | 节点、连线、工作流 |

### 2.3 系统功能领域

**职责**：系统级支撑功能

| 领域 | 说明 | 核心功能 |
|------|------|---------|
| **Auth** | 身份与权限（FR-008/009 规划） | 宿主会话解析、本地账户与会话（FR-008）、模块授权四层检查（FR-009）；当前身份由宿主派生（D023），模块授权在 `dgos-application`/`dgos-db`。统一边界见 §3.5 |
| **Storage** | 数据存储 | SQLite 操作、数据隔离（`dgos-db`） |
| **Network** | 网络服务（FR-010 规划） | HTTP 服务、局域网协同 |

## 3. 模块职责

### 3.1 Providers（Provider 适配框架）

**职责**：
- 统一 AI Provider 调用接口
- 适配不同 Provider 协议（OpenAI、Claude 等）
- 处理重试、超时、流式响应

**对外接口**：
```rust
pub trait Provider {
    async fn call(&self, request: ChatRequest) -> Result<ChatResponse>;
    async fn stream(&self, request: ChatRequest) -> Result<Stream<ChatChunk>>;
    async fn list_models(&self) -> Result<Vec<Model>>;
}
```

**依赖**：
- Storage（保存 Provider 配置）
- Auth（用户隔离）

**被依赖**：
- Skills（Skills 可能调用 AI）
- Workbench（用户发起对话）

### 3.2 Skills（Skills 管理系统）

**职责**（D016）：
- 登记随应用发布的官方内容包，离线可浏览
- 来源适配与安装（第三方来源尚未接入）
- 用户启用、版本锁定、按需准备任务上下文
- 旧 HTTP/CLI 包只读，不再执行（D017）

**对外接口**（D016 之前的草图，当前实现见 `crates/dgos-skills`）：
```rust
pub struct SkillsManager {
    pub async fn install_skill(&self, skill_id: String) -> Result<Skill>;
    pub async fn call_skill(&self, skill_id: String, params: Value) -> Result<Value>;
}
```

**依赖**：
- Storage（保存 Skills 配置）
- Auth（权限检查）

**被依赖**：
- Workbench（可选 Skills 增强）

### 3.3 MCP（MCP 管理系统）

**职责**：
- 连接 MCP 服务器
- 管理 MCP 工具列表
- 调用 MCP 工具

**对外接口**：
```rust
pub struct MCPClient {
    pub async fn connect(&self, config: MCPConfig) -> Result<()>;
    pub async fn call_tool(&self, tool_name: String, params: Value) -> Result<Value>;
}
```

**依赖**：
- Storage（保存 MCP 配置）
- Auth（权限检查）

**被依赖**：
- Workbench（AI 可调用 MCP 工具）

### 3.4 Modules（模块系统）

**职责**：
- 模块注册和发现
- 模块动态加载和卸载
- 模块热更新
- 模块权限管理

**对外接口**（规划草图；当前实现为 `dgos-modules::ModulePublisher`（包发布与恢复）和 `ModuleRuntimeSupervisor`（启停、失败上报、最小热更新/回滚、准入与加载器截止时间），经 `ModuleLoader` 端口加载 Publisher 验证过的本地 artifact。执行型加载器 `PageModuleLoader` 经 `ModulePageTransport` 把源码交给主窗口页面真实执行（D041～D046，Tauri `Channel`、命令和页面加载钩子只在 `src-tauri`），`LocalArtifactLoader` 不执行模块代码；每个 runtime 实例的加载器资源只释放一次，热更新后释放失败的旧实例保留为待释放并由 `stop` 重试。D034 的 `dgos-application::ModuleOperationManager` 统一持有两者，经 `start_module`/`stop_module`/`update_module`/`get_module_operation`/`get_module_runtime_status` 向 Settings 路由开放受控生命周期，返回宿主生成的 `operation_id`，command 被取消不取消已受理 operation。尚无 Federation 插件、状态恢复、崩溃上报与管理 UI。权限检查在 `dgos-application::HostCapabilityService`，请求经 `ModuleCapabilityDispatchService` 准入，模块能力调用不是 renderer 可调用的命令。下方 `ModuleLoader` 结构体仅为早期草图，实际端口是 `dgos-modules` 中接收 `VerifiedModuleArtifact` 的 trait）：
```rust
pub struct ModuleLoader {
    pub async fn load_module(&self, manifest: Manifest) -> Result<()>;
    pub async fn reload_module(&self, module_id: String) -> Result<()>;
    pub fn check_permission(&self, module_id: String, permission: Permission) -> bool;
}
```

**依赖**：
- Storage（保存模块配置）
- Auth（权限检查）

**被依赖**：
- 所有前端模块

### 3.5 Auth：统一身份与安全边界（FR-008/009/010）

本节是 FR-008、FR-009、FR-010 共用的身份边界，只写由冻结决策和当前代码确认的结论（2026-10-31 收口；行为细节由 D086、D087、D088 冻结）。各功能的细节在各自主规格 §2.4 维护：[FR-008](../03-功能规格/V1/03-系统功能/08-本地用户管理.md#24-身份边界收口2026-10-31)、[FR-009](../03-功能规格/V1/03-系统功能/09-模块权限管理.md#24-四层权限模型与生命周期语义2026-10-31)、[FR-010](../03-功能规格/V1/03-系统功能/10-局域网协同.md#已决安全默认值d088)。

#### 3.5.1 当前实现事实（代码核对）

| 事实 | 位置 |
| --- | --- |
| 身份只有一个宿主常量 `default-user`，注释写明保留到 FR-008 提供会话为止 | `src-tauri/src/host.rs`（`LOCAL_USER`）、`crates/dgos-types/src/execution.rs`（`HostSession::local_default()`） |
| 桌面命令经 `host::context(window, caller, capability)` 校验 `main` 窗口、可信来源与 caller 能力，产出 `HostExecutionContext`；模块管理命令经 `host::module_session` 另加 Settings 路由门禁 | `src-tauri/src/host.rs` |
| 命令入参不含 `user_id`、`module_id`（模块命令的选择器除外）、caller；由 `npm run contracts:check` 静态检查 | `scripts/check-host-contracts.mjs` |
| 没有 `users` 表、登录、会话管理器、密码哈希或 JWT 依赖；没有 HTTP/LAN 服务、CORS 代码或 LAN 凭据存储 | migrations、`Cargo.toml`、`src-tauri/src` |
| 所有用户作用域表的 `user_id` 是 TEXT，没有指向用户表的外键；`modules` 表没有 `user_id`（全局），`module_permissions`、`module_permission_audits`、`module_crash_logs` 按 `user_id` 隔离 | `crates/dgos-db/src/migrations/` |
| Provider/MCP 凭据在 OS vault，账户名是含 `user_id` 的哈希，不能按用户枚举 | `crates/dgos-providers/src/credentials.rs`、`crates/dgos-mcp/src/credentials.rs` |

#### 3.5.2 统一身份模型（已确认）

| 概念 | 定义 | 依据 |
| --- | --- | --- |
| 本地用户 | 数据归属的唯一主体，标识为 TEXT `user_id`。现有数据归 `default-user`，不新建或迁移到另一个默认用户 | D023 |
| 宿主会话 `HostSession` | “谁在操作”的唯一来源，只能由宿主构造；renderer、模块代码、Skill 文本、模型输出和 HTTP 请求都不能声明或选择用户 | D023、D025、D030 |
| 宿主会话解析器（FR-008 中称 SessionManager） | 规划组件，替换 `LOCAL_USER`/`HostSession::local_default()` 这一处出口，为桌面命令给出当前登录用户。现有命令签名不变，仍不携带身份 | D023；[FR-004 前置收口设计](当前版本/V1-FR004前置收口设计.md) |
| `HostExecutionContext` | 每次请求由 transport 适配层构造：用户 + 来源（内置 caller 或模块 `(module_id, version, integrity)`）+ 宿主生成的 `request_id`。Tauri command、模块调用通道和未来 LAN handler 构造同一种上下文后交给 Application Service | D026、D030 |
| 模块身份 | 由发布器/supervisor 绑定 `(module_id, version, integrity)`；不携带、不授予用户身份或能力令牌 | D025、D032、D042 |
| 远程（LAN）会话 | 主机签发的、有期限、可撤销的会话对象，不是用户账户；没有独立用户身份，绑定签发访问凭据时登录的桌面用户（FR-008 实施前即 `default-user`），只能使用、不能改配置；V1 不建用户名/密码账号、不建 JWT | D039、D053、D088 |

各入口的身份来源：

| 入口 | 身份来源 | 不接受 |
| --- | --- | --- |
| 桌面 Tauri command | `host::context`/`host::module_session` → 宿主会话解析器 | `user_id`、caller、会话令牌、授权结论 |
| 模块能力调用 | supervisor 签发的 runtime 句柄（用户在 start 时绑定） | 模块自报的 `module_id`、用户、版本、摘要 |
| LAN handler（FR-010，规划） | 宿主签发的 LAN 会话 → 签发者（D088） | 请求中的用户、模块身份、授权结论；任意 Tauri command 映射 |

#### 3.5.3 不变量

1. Transport 只解码业务 DTO、绑定宿主上下文、映射协议错误；授权、幂等、取消和审计在 Application Service（D030）。
2. 用户授权、模块准入与 LAN 会话互不替代：授权不构成准入（D041），授权只取 manifest 交集（D029），LAN 会话不继承也不授予模块权限，模块不能借 LAN 会话获得能力。
3. 凭据、密码、LAN 访问凭据与会话令牌不进入普通 DTO、SQLite 明文、日志、fixture 或错误消息（D023、D053）；密码只以单向哈希保存。
4. 外部能力（MCP、Provider、Skill）的授权只走宿主策略；模型输出、Skill 文本、远程请求不能创建授权（D021、D022、D075）。

#### 3.5.4 依赖顺序（推荐）

推荐 FR-009 → FR-008 → FR-010（推荐顺序，未冻结为决策）。FR-009 在 D055 已实现的管理命令上收口，不依赖 FR-008（授权已按宿主派生的 `user_id` 隔离）。FR-008 替换会话解析器，并按 D086、D087、D088 执行用户切换时的 runtime 停止与远程会话撤销。FR-010 不依赖 FR-008（D053 否决了依赖 FR-008 的方案 B），但在 FR-008 之后实现可以直接使用会话解析器与失效事件；若先实现，远程会话绑定 `default-user`（D088）。依据与差距见 [V1 实现状态](../02-产品与版本/当前版本/V1-实现状态.md) §10。

#### 3.5.5 已作废的旧口径

本节之前的 `AuthService { login → Session, verify_token, check_permission(user_id, …) }` 草图与“用户认证（登录、JWT）”职责描述作废：JWT 不是任何入口的方案（D053）；`check_permission` 接收 `user_id` 与 D023/D025 冲突，权限检查在 Host Capability API 内部逐次执行（D026）。

## 4. 模块间通信

### 4.1 前端到后端

**通信方式**：Tauri IPC（Command）

```rust
#[tauri::command]
pub async fn call_provider(
    app: tauri::AppHandle,
    window: WebviewWindow,          // 宿主据此派生调用上下文
    provider_id: String,
    model_id: String,
    request: ChatRequest,
) -> CommandResponse<ChatResponse> {
    // host::context(&window, ...) 取得用户与来源，再交给应用服务/领域 Manager
}
```

命令参数不得包含 `user_id` 或调用来源（D023）。D034 的模块生命周期 command 例外地接受 `module_id` 选择器与查询用 `operation_id`，但不得包含 runtime/handle/context/session/version/integrity/path/source/url 等字段，且必须经 `host::module_session` 入口（Settings 路由门禁）。D046 的页面桥接命令 `attach_module_host`/`report_module_host` 是页面生命周期的 transport 扩展，不是通用模块 IPC：只接受 Tauri 通道与宿主签发的 `attachment_id`、`ticket`、回执，经 `host::module_host_window` 入口，该入口只校验 `main` 窗口与可信来源，不要求 Settings 路由，也不依赖 caller/capability 策略。三类规则均由 `npm run contracts:check` 静态检查。模块运行时对宿主能力的调用（D048）不经过 renderer：`ModuleCapabilityDispatchService` 是 Rust 内部服务，只接受 supervisor 签发的 `ModuleRuntimeHandle`，没有 Tauri command，模块 JS 目前没有触发路径。

### 4.2 后端模块间

**通信方式**：直接函数调用

```rust
// Workbench 调用 Providers
let response = providers_manager.call(provider_id, request).await?;

// Workbench 使用 Skill（可选）：准备固定版本的内容作为上下文，不执行（D016/D018）
if let Some(skill) = selected_skill {
    let context = skills_manager.prepare_content(skill).await?;
}
```

### 4.3 前端模块间

**通信方式**：
- 共享状态（Zustand/Redux）
- 事件总线（EventEmitter）
- Module Federation 共享依赖（FR-004 规划）

## 6. 边界规则

### 6.1 依赖方向

**规则**：依赖只能自上而下，不能反向

```
应用模块（Workbench、Settings）
     ↓ 可以依赖
底层能力（Providers、Skills、MCP）
     ↓ 可以依赖
系统功能（Auth、Storage、Network）
```

**禁止**：
- ❌ 底层能力依赖应用模块
- ❌ 系统功能依赖底层能力

### 6.2 数据隔离

**规则**：每个用户的数据完全隔离

- 所有查询必须带 `user_id`，由宿主派生，不接受前端传入（D023）
- 不允许跨用户查询
- 隔离在应用层的仓储与 Manager 中执行（SQLite 没有行级安全策略）

### 6.3 权限边界

**规则**：模块只能访问已授权的资源

| 权限 | 说明 | 示例 |
|------|------|------|
| `providers.call` | 调用 Provider | AI 工作台 |
| `skills.execute` | 使用 Skills：模块经 `module_prepare_skill` 只取得已安装技能的固定版本内容（D016、D093），模块授权不自动授予技能内容 | AI 工作台；模块 |
| `mcp.call` | 调用 MCP 工具；模块发起的调用每次由用户在宿主确认框批准（D093） | AI 工作台；模块 |
| `storage.read` | 读取模块自己的键值存储（每用户 × 每模块，D093） | 所有模块 |
| `storage.write` | 写入或删除模块自己的键值存储（D093） | 所有模块 |
| `network.local` | 模块只访问回环地址的 HTTP(S)（D093） | 模块能力；与 FR-010 局域网服务及其远程会话无关 |

## 7. 扩展点

### 7.1 Provider 扩展

**如何添加新的 Provider**：
1. 实现 `Provider` trait
2. 注册到 `ProviderRegistry`
3. 前端添加配置表单

### 7.2 Skills 扩展

**如何添加新的 Skill**：
1. 官方技能：在 `skills/official/` 添加 `SKILL.md` 内容包，运行 `npm run skills:catalog` 更新目录哈希
2. 第三方来源：通过来源适配器按需安装（FR-002 Batch B，尚未实现）

### 7.3 模块扩展

**如何添加新的前端模块**：
1. 开发 React 模块
2. 使用 Module Federation 打包
3. 创建 manifest.json
4. 用户通过界面加载

- 所有功能在一个进程
- 前端模块可独立加载
- 后端模块编译时静态链接

### 8.2 V3 起：微前端架构

- 前端模块完全独立
- 应用市场分发（V3）
- 运行时动态加载

### 8.3 V4 起：混合架构（可能）

- 后端保持单体
- 前端微前端
- 可选云端服务
