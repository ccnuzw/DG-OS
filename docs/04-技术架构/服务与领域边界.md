# 服务与领域边界

本文档定义 DGOS 的服务架构和领域边界，明确各模块的职责和交互关系。

> **实现状态说明（2026-10-28）**：本文的“服务”描述包含跨版本目标。当前代码仍处于模块化单体前置收口阶段，Transport 与 Domain Manager 之间的 Application Service / Use Case 层尚未完整建立；新增入口不得把该目标层当作已实现事实，优先遵循 [V1 架构优化评审草案](当前版本/V1-架构优化评审草案.md) 的分层边界。

---

## 1. 总体架构

DGOS 采用**模块化单体架构**（Modular Monolith）：
- 单一应用进程
- 内部按领域划分模块
- 模块间通过明确的接口通信
- 前端模块可独立加载和卸载

```
┌─────────────────────────────────────────────────────────────┐
│                        Tauri Desktop                        │
├─────────────────────────────────────────────────────────────┤
│                    React Frontend (SPA)                     │
│  ┌───────────┬───────────┬───────────┬──────────────────┐  │
│  │ AI工作台  │ 系统设置  │ 画布编辑  │  第三方模块...    │  │
│  └───────────┴───────────┴───────────┴──────────────────┘  │
│              Module Federation（FR-004 规划）                │
├─────────────────────────────────────────────────────────────┤
│                      Tauri IPC Layer                        │
├─────────────────────────────────────────────────────────────┤
│        Rust Backend（Tauri commands；Axum 为 FR-010 规划）     │
│  ┌──────────┬──────────┬──────────┬──────────┬─────────┐  │
│  │Providers │ Skills   │   MCP    │ Modules  │Auth(规划)│  │
│  └──────────┴──────────┴──────────┴──────────┴─────────┘  │
├─────────────────────────────────────────────────────────────┤
│                        SQLite Database                      │
└─────────────────────────────────────────────────────────────┘
```

当前 Rust crate 与领域的对应：`dgos-providers`（Providers）、`dgos-skills`（Skills）、`dgos-mcp`（MCP）、`dgos-workbench`（Workbench）、`dgos-modules`（模块发布，FR-004 前置）、`dgos-application`（Application Service 与 Host Capability 授权，D030）、`dgos-db`（Storage）、`dgos-types`（共享类型）。Auth、Network、UI 尚无对应 crate。

## 2. 领域划分

### 2.1 底层能力领域

**职责**：提供框架级能力，不涉及具体业务逻辑

| 领域 | 说明 | 核心功能 |
|------|------|---------|
| **Providers** | Provider 适配框架 | 统一接口调用各类 AI 模型 |
| **Skills** | DGOS 技能中心 | 官方内容包、来源适配、版本锁定、按需准备任务上下文（D016，不执行内容） |
| **MCP** | MCP 管理系统 | 连接、管理、调用 MCP 工具 |
| **Modules** | 模块系统 | 模块包发布与恢复（已有前置切片）；加载、卸载、热更新（规划） |
| **UI** | 统一设计系统 | 主题、组件、样式规范 |

### 2.2 应用模块领域

**职责**：面向用户的业务功能

| 领域 | 说明 | 核心功能 |
|------|------|---------|
| **Workbench** | AI 工作台 | 当前：单任务文本/工具任务（D018/D022）；规划：多轮对话、流式响应、历史记录 |
| **Settings** | 系统设置 | Provider/Skills/MCP 管理界面 |
| **Canvas** | 无限画布（V2） | 节点、连线、工作流 |

### 2.3 系统功能领域

**职责**：系统级支撑功能

| 领域 | 说明 | 核心功能 |
|------|------|---------|
| **Auth** | 认证与权限（FR-008/009 规划） | 用户登录、会话、权限检查；当前身份由宿主派生（D023），模块授权在 `dgos-application` |
| **Storage** | 数据存储 | SQLite 操作、数据隔离（`dgos-db`） |
| **Network** | 网络服务（FR-010 规划） | HTTP 服务、局域网协同 |

## 3. 模块职责

### 3.1 Providers（Provider 适配框架）

**职责**：
- 统一 AI Provider 调用接口
- 适配不同 Provider 协议（OpenAI、Claude 等）
- 处理重试、超时、流式响应

**对外接口**：
```rust
pub trait Provider {
    async fn call(&self, request: ChatRequest) -> Result<ChatResponse>;
    async fn stream(&self, request: ChatRequest) -> Result<Stream<ChatChunk>>;
    async fn list_models(&self) -> Result<Vec<Model>>;
}
```

**依赖**：
- Storage（保存 Provider 配置）
- Auth（用户隔离）

**被依赖**：
- Skills（Skills 可能调用 AI）
- Workbench（用户发起对话）

### 3.2 Skills（Skills 管理系统）

**职责**（D016）：
- 登记随应用发布的官方内容包，离线可浏览
- 来源适配与安装（第三方来源尚未接入）
- 用户启用、版本锁定、按需准备任务上下文
- 旧 HTTP/CLI 包只读，不再执行（D017）

**对外接口**（D016 之前的草图，当前实现见 `crates/dgos-skills`）：
```rust
pub struct SkillsManager {
    pub async fn install_skill(&self, skill_id: String) -> Result<Skill>;
    pub async fn call_skill(&self, skill_id: String, params: Value) -> Result<Value>;
}
```

**依赖**：
- Storage（保存 Skills 配置）
- Auth（权限检查）

**被依赖**：
- Workbench（可选 Skills 增强）

### 3.3 MCP（MCP 管理系统）

**职责**：
- 连接 MCP 服务器
- 管理 MCP 工具列表
- 调用 MCP 工具

**对外接口**：
```rust
pub struct MCPClient {
    pub async fn connect(&self, config: MCPConfig) -> Result<()>;
    pub async fn call_tool(&self, tool_name: String, params: Value) -> Result<Value>;
}
```

**依赖**：
- Storage（保存 MCP 配置）
- Auth（权限检查）

**被依赖**：
- Workbench（AI 可调用 MCP 工具）

### 3.4 Modules（模块系统）

**职责**：
- 模块注册和发现
- 模块动态加载和卸载
- 模块热更新
- 模块权限管理

**对外接口**（规划草图；当前实现为 `dgos-modules::ModulePublisher`（包发布与恢复）和 D033 `ModuleRuntimeSupervisor`（启停、失败上报、最小热更新/回滚），经 `ModuleLoader` 端口加载 Publisher 验证过的本地 artifact，内置 `LocalArtifactLoader` 不执行模块代码；每个 runtime 实例的加载器资源只释放一次，热更新后释放失败的旧实例保留为待释放并由 `stop` 重试。D034 的 `dgos-application::ModuleOperationManager` 统一持有两者，经 `start_module`/`stop_module`/`update_module`/`get_module_operation`/`get_module_runtime_status` 向 Settings 路由开放受控生命周期，返回宿主生成的 `operation_id`，command 被取消不取消已受理 operation。尚无 Federation/WebView 加载、生命周期钩子、状态恢复与 UI。权限检查在 `dgos-application::HostCapabilityService`，请求经 `ModuleCapabilityDispatchService` 准入，模块能力调用不是 renderer 可调用的命令。下方 `ModuleLoader` 结构体仅为早期草图，实际端口是 `dgos-modules` 中接收 `VerifiedModuleArtifact` 的 trait）：
```rust
pub struct ModuleLoader {
    pub async fn load_module(&self, manifest: Manifest) -> Result<()>;
    pub async fn reload_module(&self, module_id: String) -> Result<()>;
    pub fn check_permission(&self, module_id: String, permission: Permission) -> bool;
}
```

**依赖**：
- Storage（保存模块配置）
- Auth（权限检查）

**被依赖**：
- 所有前端模块

### 3.5 Auth（认证与权限，FR-008/009 规划）

当前没有登录或 JWT；所有命令由宿主从可信窗口派生 `default-user`（D023）。

**职责**：
- 用户认证（登录、JWT）
- 会话管理
- 权限检查

**对外接口**：
```rust
pub struct AuthService {
    pub async fn login(&self, username: String, password: String) -> Result<Session>;
    pub fn verify_token(&self, token: String) -> Result<User>;
    pub fn check_permission(&self, user_id: String, permission: Permission) -> bool;
}
```

**依赖**：
- Storage（用户数据）

**被依赖**：
- 所有需要认证的模块

## 4. 模块间通信

### 4.1 前端到后端

**通信方式**：Tauri IPC（Command）

```rust
#[tauri::command]
pub async fn call_provider(
    app: tauri::AppHandle,
    window: WebviewWindow,          // 宿主据此派生调用上下文
    provider_id: String,
    model_id: String,
    request: ChatRequest,
) -> CommandResponse<ChatResponse> {
    // host::context(&window, ...) 取得用户与来源，再交给应用服务/领域 Manager
}
```

命令参数不得包含 `user_id` 或调用来源（D023）。D034 的模块生命周期 command 例外地接受 `module_id` 选择器与查询用 `operation_id`，但不得包含 runtime/handle/context/session/version/integrity/path/source/url 等字段，且必须经 `host::module_session` 入口；两类规则均由 `npm run contracts:check` 静态检查。

### 4.2 后端模块间

**通信方式**：直接函数调用

```rust
// Workbench 调用 Providers
let response = providers_manager.call(provider_id, request).await?;

// Workbench 使用 Skill（可选）：准备固定版本的内容作为上下文，不执行（D016/D018）
if let Some(skill) = selected_skill {
    let context = skills_manager.prepare_content(skill).await?;
}
```

### 4.3 前端模块间

**通信方式**：
- 共享状态（Zustand/Redux）
- 事件总线（EventEmitter）
- Module Federation 共享依赖（FR-004 规划）

## 5. 数据流

### 5.1 用户发起对话流程

下图是早期草图：当前 Workbench 为单任务（D018/D022），Skill 作为上下文而非 HTTP/CLI 调用，暂无流式返回。

```
用户输入 → Workbench（前端）
           ↓
        Tauri IPC
           ↓
     Workbench Handler（后端）
           ↓
    ┌──────┴──────┐
    ↓             ↓
 Providers     Skills（可选）
    ↓             ↓
  OpenAI       HTTP/CLI
    ↓             ↓
 Response      Result
    ↓             ↓
    └──────┬──────┘
           ↓
      合并结果
           ↓
       流式返回
           ↓
    Workbench（前端）
           ↓
       用户查看
```

### 5.2 模块加载流程（FR-004 规划）

```
用户打开设置 → Settings（前端）
                 ↓
              点击"加载模块"
                 ↓
              Tauri IPC
                 ↓
          ModuleLoader（后端）
                 ↓
           验证 manifest.json
                 ↓
           检查权限要求
                 ↓
           用户授权（前端）
                 ↓
           动态加载代码
                 ↓
           注册到系统
                 ↓
           通知前端
                 ↓
        Settings 显示新模块
```

## 6. 边界规则

### 6.1 依赖方向

**规则**：依赖只能自上而下，不能反向

```
应用模块（Workbench、Settings）
     ↓ 可以依赖
底层能力（Providers、Skills、MCP）
     ↓ 可以依赖
系统功能（Auth、Storage、Network）
```

**禁止**：
- ❌ 底层能力依赖应用模块
- ❌ 系统功能依赖底层能力

### 6.2 数据隔离

**规则**：每个用户的数据完全隔离

- 所有查询必须带 `user_id`，由宿主派生，不接受前端传入（D023）
- 不允许跨用户查询
- 隔离在应用层的仓储与 Manager 中执行（SQLite 没有行级安全策略）

### 6.3 权限边界

**规则**：模块只能访问已授权的资源

| 权限 | 说明 | 示例 |
|------|------|------|
| `providers.call` | 调用 Provider | AI 工作台 |
| `skills.execute` | 使用 Skills（D016 起为准备内容上下文，模块授权不自动授予技能内容） | AI 工作台 |
| `mcp.call` | 调用 MCP 工具 | AI 工作台 |
| `storage.read` | 读取存储 | 所有模块 |
| `storage.write` | 写入存储 | 系统设置 |
| `network.local` | 访问局域网 | 局域网协同 |

## 7. 扩展点

### 7.1 Provider 扩展

**如何添加新的 Provider**：
1. 实现 `Provider` trait
2. 注册到 `ProviderRegistry`
3. 前端添加配置表单

### 7.2 Skills 扩展

**如何添加新的 Skill**：
1. 官方技能：在 `skills/official/` 添加 `SKILL.md` 内容包，运行 `npm run skills:catalog` 更新目录哈希
2. 第三方来源：通过来源适配器按需安装（FR-002 Batch B，尚未实现）

### 7.3 模块扩展

**如何添加新的前端模块**：
1. 开发 React 模块
2. 使用 Module Federation 打包
3. 创建 manifest.json
4. 用户通过界面加载

## 8. 未来演进

### 8.1 V1：单体架构

- 所有功能在一个进程
- 前端模块可独立加载
- 后端模块编译时静态链接

### 8.2 V3 起：微前端架构

- 前端模块完全独立
- 应用市场分发（V3）
- 运行时动态加载

### 8.3 V4 起：混合架构（可能）

- 后端保持单体
- 前端微前端
- 可选云端服务
