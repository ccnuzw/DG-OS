## 2. 后端技术栈

### 2.1 Rust（引用 **D001**）

**选择理由**：
- ✅ **编译期强制模块化**：不可能写出单文件 19,038 行的巨石代码
- ✅ **零成本抽象**：性能优于 Python/Node.js
- ✅ **内存安全**：所有权系统防止内存泄漏
- ✅ **类型安全**：编译期捕获大部分错误
- ✅ **并发安全**：防止数据竞争

**替代方案对比**：

| 方案 | 优点 | 缺点 | 为什么不选 |
|------|------|------|-----------|
| **Python** | 开发速度快 | 性能差，无类型安全，容易写巨石 | 老项目教训 |
| **Node.js** | 生态丰富 | 单线程，内存占用高 | 性能不足 |
| **Go** | 简单，并发好 | GC 延迟，生态不如 Rust | 性能要求高 |
| **Java** | 成熟稳定 | 笨重，内存占用大 | 不适合桌面应用 |

**从老项目学习**：
- ❌ 老项目：Python + FastAPI，单文件 19,038 行
- ✅ 新项目：Rust 强制模块化，每个文件 < 1000 行

### 2.2 Axum

**选择理由**：
- ✅ 基于 Tokio 异步运行时
- ✅ 类型安全的路由
- ✅ Tower 中间件生态
- ✅ 性能优异

**替代方案**：
- Actix-web：性能更好，但 API 复杂
- Rocket：简单，但异步支持不完善

### 2.3 SeaORM

**选择理由**：
- ✅ 异步 ORM，支持 Tokio
- ✅ 类型安全的查询
- ✅ 迁移管理
- ✅ 支持 SQLite

**替代方案**：
- Diesel：成熟，但同步 API
- sqlx：轻量，但需要手写 SQL

## 3. 桌面技术栈

### 3.1 Tauri 2（引用 **D001**）

**选择理由**：
- ✅ **轻量级**：安装包 < 10MB（Electron >100MB）
- ✅ **安全性**：Rust 后端 + 权限系统
- ✅ **跨平台**：macOS/Windows/Linux
- ✅ **原生性能**：系统 WebView，无 Chromium 包袱

**对比 Electron**：

| 指标 | Tauri | Electron | 差距 |
|------|-------|----------|------|
| 安装包大小 | ~5-10MB | ~100-150MB | **10-15x** |
| 内存占用 | ~50-100MB | ~200-400MB | **2-4x** |
| 启动时间 | ~0.5-1s | ~2-3s | **2-3x** |
| 安全性 | 高（Rust） | 中（Node.js） | - |

**从老项目学习**：
- 如果用 Electron，安装包会超过 100MB
- Tauri 更适合本地优先应用

## 4. 前端技术栈

### 4.1 React 18（引用 **D001**）

**选择理由**：
- ✅ 成熟稳定，生态丰富
- ✅ Hooks + Concurrent Mode
- ✅ 社区活跃
- ✅ Module Federation 支持好

**替代方案**：
- Vue 3：简单，但生态不如 React
- Svelte：性能好，但生态小
- Solid.js：性能最好，但太新

### 4.2 TypeScript

**选择理由**：
- ✅ 类型安全
- ✅ IDE 支持好
- ✅ 重构友好

### 4.3 Vite

**选择理由**：
- ✅ 快速的开发服务器（ESM）
- ✅ 快速的生产构建（Rollup）
- ✅ 开箱即用
- ✅ 支持 Module Federation

**替代方案**：
- Webpack：成熟，但慢
- Turbopack：太新，不稳定

### 4.4 pnpm

**选择理由**：
- ✅ 节省磁盘空间（硬链接）
- ✅ 安装速度快
- ✅ 严格的依赖管理

**替代方案**：
- npm：慢，占空间
- yarn：好，但 pnpm 更快

## 5. 数据库技术栈

### 5.1 SQLite（引用 **D002**）

**选择理由**：
- ✅ **本地优先**：零配置，单文件
- ✅ **数据隔离**：每个用户独立数据库
- ✅ **轻量级**：无需服务器进程
- ✅ **事务支持**：ACID 保证
- ✅ **跨平台**：所有系统支持

**对比 PostgreSQL**：

| 指标 | SQLite | PostgreSQL |
|------|--------|-----------|
| 配置复杂度 | 零配置 | 需要安装和配置 |
| 用户隔离 | 每用户一个文件 | 需要数据库设计 |
| 性能 | 本地读写快 | 网络延迟 |
| 并发 | 读并发好，写串行 | 并发写好 |
| 适用场景 | 本地优先 | 云端多用户 |

**V1 不需要 PostgreSQL**：
- 本地单用户场景
- SQLite 完全满足需求
- 简化部署和维护

**未来扩展**：
- V2.0 云端同步：可选 PostgreSQL
- V1.0：只用 SQLite

## 6. 模块化技术栈

### 6.1 Module Federation（引用 **D004**）

**选择理由**：
- ✅ **运行时加载**：无需重启应用
- ✅ **独立构建**：模块可单独开发和部署
- ✅ **共享依赖**：React、Zustand 只加载一次
- ✅ **成熟方案**：Webpack/Vite 都支持

**对比其他方案**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| **iframe** | 完全隔离 | 通信复杂，性能差 |
| **Web Components** | 标准化 | 生态不成熟，React 支持差 |
| **动态 import** | 简单 | 无法共享依赖，包体积大 |

### 6.2 设计系统（引用 **D008**）

**技术栈**：
- **组件库**：自研 `@dgos/ui`（基于 Radix UI）
- **样式方案**：CSS Variables + Tailwind
- **主题系统**：亮色/暗色主题切换

**为什么自研**：
- 强制视觉一致性
- 禁止模块自定义样式
- 主题切换全局生效

### 7.1 Skills 协议（引用 **D005**）

**选择**：LangChain Tools 标准

**理由**：
- ✅ 成熟生态
- ✅ 广泛使用
- ✅ 标准化接口

### 7.2 MCP 协议（引用 **D005**）

**选择**：Anthropic Model Context Protocol

**理由**：
- ✅ Anthropic 主导
- ✅ 标准化协议
- ✅ 社区支持

### 7.3 为什么不自定义协议

- ❌ 重复造轮子
- ❌ 生态割裂
- ❌ 维护成本高

## 11. 性能考虑

### 11.1 后端性能

- Rust 零成本抽象
- 异步 I/O（Tokio）
- SQLite 本地访问
- 无 GC 暂停

**预期性能**：
- API 响应时间 P95 < 200ms
- 内存占用 < 200MB（空闲）

### 11.2 前端性能

- Module Federation 按需加载
- React 18 Concurrent Mode
- Vite 快速构建
- 代码分割

**预期性能**：
- 应用启动时间 < 2s
- 模块加载时间 < 1s
- UI 交互帧率 > 60fps
