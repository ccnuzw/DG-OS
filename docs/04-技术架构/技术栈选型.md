## 2. 后端技术栈

### 2.1 Rust（引用 **D001**）

**选择理由**：
- ✅ **编译期强制模块化**：不可能写出单文件 19,038 行的巨石代码
- ✅ **零成本抽象**：性能优于 Python/Node.js
- ✅ **内存安全**：所有权系统防止内存泄漏
- ✅ **类型安全**：编译期捕获大部分错误
- ✅ **并发安全**：防止数据竞争

**替代方案对比**：

| 方案 | 优点 | 缺点 | 为什么不选 |
|------|------|------|-----------|
| **Python** | 开发速度快 | 性能差，无类型安全，容易写巨石 | 老项目教训 |
| **Node.js** | 生态丰富 | 单线程，内存占用高 | 性能不足 |
| **Go** | 简单，并发好 | GC 延迟，生态不如 Rust | 性能要求高 |
| **Java** | 成熟稳定 | 笨重，内存占用大 | 不适合桌面应用 |

**从老项目学习**：
- ❌ 老项目：Python + FastAPI，单文件 19,038 行
- ✅ 新项目：Rust 强制模块化，每个文件 < 1000 行

### 2.2 Axum（规划，FR-010）

Axum 尚未加入当前 workspace。D001 将其列为后续 HTTP 后端选项；只有在设计并实现 V1-FR-010 局域网服务时才引入。

**规划理由**：
- ✅ 基于 Tokio 异步运行时
- ✅ 类型安全的路由
- ✅ Tower 中间件生态
- ✅ 性能优异

**替代方案**：
- Actix-web：性能更好，但 API 复杂
- Rocket：简单，但异步支持不完善

### 2.3 SeaORM

**选择理由**：
- ✅ 异步 ORM，支持 Tokio
- ✅ 类型安全的查询
- ✅ 迁移管理
- ✅ 支持 SQLite

**替代方案**：
- Diesel：成熟，但同步 API
- sqlx：轻量，但需要手写 SQL

## 3. 桌面技术栈

### 3.1 Tauri 2（引用 **D001**）

**选择理由**：
- ✅ **轻量级**：安装包 < 10MB（Electron >100MB）
- ✅ **安全性**：Rust 后端 + 权限系统
- ✅ **跨平台**：macOS/Windows/Linux
- ✅ **原生性能**：系统 WebView，无 Chromium 包袱

**对比 Electron**：

| 指标 | Tauri | Electron | 差距 |
|------|-------|----------|------|
| 安装包大小 | ~5-10MB | ~100-150MB | **10-15x** |
| 内存占用 | ~50-100MB | ~200-400MB | **2-4x** |
| 启动时间 | ~0.5-1s | ~2-3s | **2-3x** |
| 安全性 | 高（Rust） | 中（Node.js） | - |

**从老项目学习**：
- 如果用 Electron，安装包会超过 100MB
- Tauri 更适合本地优先应用

## 4. 前端技术栈

### 4.1 React 19（引用 **D001**）

**选择理由**：
- ✅ 成熟稳定，生态丰富
- ✅ Hooks + Concurrent Mode
- ✅ 社区活跃
- ✅ 与当前 React 19 前端工具链兼容；Module Federation 仍是后续规划，不代表已经接入

**替代方案**：
- Vue 3：简单，但生态不如 React
- Svelte：性能好，但生态小
- Solid.js：性能最好，但太新

### 4.2 TypeScript

**选择理由**：
- ✅ 类型安全
- ✅ IDE 支持好
- ✅ 重构友好

### 4.3 Vite

**选择理由**：
- ✅ 快速的开发服务器（ESM）
- ✅ 快速的生产构建（Rollup）
- ✅ 开箱即用
- ✅ 支持 Module Federation

**替代方案**：
- Webpack：成熟，但慢
- Turbopack：太新，不稳定

### 4.4 npm

**当前采用**：仓库使用 npm 与 `package-lock.json`；没有 pnpm lockfile。

**替代方案**：
- pnpm/yarn：均未作为本仓库的包管理器

## 5. 数据库技术栈

### 5.1 SQLite（引用 **D002**）

**选择理由**：
- ✅ **本地优先**：零配置，单文件
- ✅ **数据隔离**：单个 `dgos.db` 内以 `user_id` 作用域隔离；当前宿主身份固定为 `default-user`
- ✅ **轻量级**：无需服务器进程
- ✅ **事务支持**：ACID 保证
- ✅ **跨平台**：所有系统支持

**对比 PostgreSQL**：

| 指标 | SQLite | PostgreSQL |
|------|--------|-----------|
| 配置复杂度 | 零配置 | 需要安装和配置 |
| 用户隔离 | `user_id` 列作用域 | 需要数据库设计 |
| 性能 | 本地读写快 | 网络延迟 |
| 并发 | 读并发好，写串行 | 并发写好 |
| 适用场景 | 本地优先 | 云端多用户 |

**V1 不需要 PostgreSQL**：
- 本地单用户场景
- SQLite 完全满足需求
- 简化部署和维护

**未来扩展**：
- V4 云端与协同：可选 PostgreSQL
- V1：只用 SQLite

## 6. 模块化技术栈

### 6.1 Module Federation（引用 **D004**）

**规划理由（尚未引入）**：
- ✅ **目标是运行时加载**：无需重启应用
- ✅ **目标是独立构建**：模块可单独开发和部署
- ✅ **目标是共享依赖**：React、Zustand 只加载一次
- ⚠️ D025/D028 限制 V1 只能加载受信任代码，不允许任意远程 JS；当前没有模块运行时

**对比其他方案**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| **iframe** | 完全隔离 | 通信复杂，性能差 |
| **Web Components** | 标准化 | 生态不成熟，React 支持差 |
| **动态 import** | 简单 | 无法共享依赖，包体积大 |

### 6.2 设计系统（引用 **D008**）

**规划技术栈（FR-005/D008，尚未引入）**：
- **组件库**：自研 `@dgos/ui`（基于 Shadcn/Radix）
- **样式方案**：CSS Variables + Tailwind
- **主题系统**：亮色/暗色主题切换

**为什么自研**：
- 强制视觉一致性
- 禁止模块自定义样式
- 主题切换全局生效

## 7. 协议标准

### 7.1 Skills 内容包（引用 **D016**）

**选择**：`SKILL.md` 内容中心

**理由**：
- ✅ 内容包可校验、版本化并固定 hash
- ✅ 工作台将正文作为受控上下文消费
- ✅ 不授予 Skill 任意工具、HTTP 或 CLI 执行权

### 7.2 MCP 协议（引用 **D005**）

**当前支持**：MCP 2024-11-05、2025-03-26、2025-06-18

**理由**：
- ✅ Anthropic 主导
- ✅ 标准化协议
- ✅ 传输包括 stdio、Streamable HTTP，以及 HTTP adapter 内的 legacy SSE fallback

### 7.3 为什么不自定义协议

- ❌ 重复造轮子
- ❌ 生态割裂
- ❌ 维护成本高

## 11. 性能考虑

### 11.1 后端性能

- Rust 零成本抽象
- 异步 I/O（Tokio）
- SQLite 本地访问
- 无 GC 暂停

**预期性能**：
- Provider/桌面 command 响应目标需按功能规格验证；当前没有 HTTP API
- 内存占用 < 200MB（空闲）

### 11.2 前端性能

- 未来 Module Federation 按需加载（规划）
- React 19 并发能力
- Vite 快速构建
- 代码分割

**预期性能**：
- 应用启动时间 < 2s
- 模块加载时间 < 1s
- UI 交互帧率 > 60fps

## 12. 安全考虑

### 12.1 后端安全

- Rust 内存安全
- SQLite 参数化查询
- Provider/MCP 凭据由 OS vault 保存或引用（D023），不在普通 DTO、SQLite 或日志中保存明文；不是 AES/SQLCipher 方案
- JWT 仅属于未来 HTTP/LAN 认证设计，当前没有登录/JWT

### 12.2 前端安全

- Tauri 权限系统
- CSP（Content Security Policy）
- 输入验证
- XSS 防护
