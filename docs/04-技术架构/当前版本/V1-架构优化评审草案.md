# V1 架构优化评审草案

> 状态：评审草案（Application Service 分层已由 D030 冻结；发布 lease 与可信注册根已由 D031/D032 冻结，runtime 仍为候选方案，非实现状态来源）
>
> 日期：2026-10-28
>
> 目的：在 FR-004 前置收口和当前代码增量之后，重新评估后续版本持续开发所需的中间层、生命周期和契约边界。本文提出候选方案；确认后应拆分为 ADR/冻结决策和可验证实现切片。

## 1. 当前结论

当前代码已经补齐了重要的安全前置：宿主执行上下文、持久化授权 broker、最小 Host Capability API、包 staging/完整性校验、版本目录和启动恢复。首个 `ProviderCallService` 已抽到 `dgos-application`，证明中间层可以独立于 Tauri transport 演进；但 FR-004 仍是规划中，且 Application Service / Use Case 层尚未覆盖全部入口。

现在直接继续堆叠 Tauri command、Provider/Skills/MCP Manager 和模块运行时，会把以下职责重新耦合：调用者身份绑定、能力授权、资源归属、事务编排、幂等、取消、审计和错误映射。短期能跑通，长期会导致每增加一个入口（Workbench 流式、多用户、LAN、模块运行时）就复制一套绕过规则。

### 1.1 本轮增量复评结论（2026-10-28）

本轮在加入 `dgos-application`、模块发布器和数据库 lease 后重新检查了代码、迁移、契约和测试。结论是“前置边界明显变好，但还没有形成可安全扩展的完整平台层”，不能把当前切片直接升级为 FR-004 完成：

- **已经站稳的边界**：宿主派生执行上下文、Provider 的首个 Application Service、manifest 能力上限与用户授权交集、包 staging/摘要/指针恢复、失败事件和启动恢复。
- **仍然存在的结构缺口**：Skills/MCP/Workbench 的入口仍主要直达 Manager；模块身份注册根仍是公开 Rust API；`ModulePublisher::execution_context` 仍接收调用方提供的用户和模块标识；发布幂等、lease 续租、孤儿版本清理和断电故障注入尚未闭环。
- **仍然存在的信任缺口**：SHA-256 只证明包完整性，不证明发行者；manifest 尚未冻结 host 兼容性、依赖、包大小和来源策略；同 realm Module Federation 仍不能提供安全沙箱。
- **仍然存在的运行时缺口**：没有 supervisor、runtime handle、draining、加载/卸载/热更新和在途请求终态，因此不能开始“边写 federation 边补安全”的实现方式。
- **验证边界**：当前 Rust workspace 与前端定向回归通过，但没有 lease 等待/过期/强杀恢复、跨平台文件系统语义、真实桌面模块加载或 LAN 认证证据。

因此，下一阶段的目标不是继续增加模块功能，而是先把“跨入口 Application Service + 可恢复发布状态机 + 可信身份根”做成可验收的稳定底座。

## 2. 现状与目标分层

### 2.1 当前可确认的事实

- Tauri 宿主已派生本地执行上下文；renderer 不能自报 `user_id` 或模块身份。
- `ModulePermissionRepository` 是持久化授权 broker，不是可信身份根，也尚未被真实模块运行时调用。
- 生产宿主只通过 `HostCapabilityService::with_publisher` 构造能力网关；不带发布器的构造路径仅用于 crate 内测试，避免把数据库注册行误当作可信模块身份。
- `HostCapabilityService` 已作为 Provider capability adapter；Skills/MCP 尚未全部接入该网关。
- `ModulePublisher` 已覆盖本地包暂存、manifest/路径/symlink/摘要校验、版本发布、DB 指针和启动恢复。
- 发布器同一实例内已串行化；跨进程锁、签名信任根、运行时加载、断电故障注入和 Federation 尚未完成。

### 2.2 建议的目标分层

```text
Renderer / LAN HTTP / Module Runtime
            │  仅业务 DTO，不携带身份或授权结论
Transport Adapter（Tauri command、HTTP handler、事件流）
            │
Host Session & Execution Context
            │  派生 user/source/request/task，绑定生命周期
Application Services / Use Cases（缺失的中间层）
            │  编排授权、幂等、事务、取消、审计、错误映射
Policy / Capability Gateway（HostCapabilityService）
            │  每次 dispatch 前 fail-closed
Domain Managers（Provider / Skills / MCP / Workbench / Modules）
            │  资源归属、状态机和业务不变量
Ports / Repositories / External Adapters
            │
SQLite、OS Vault、Provider、MCP、文件系统
```

### 2.3 每层不可越过的边界

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| Transport | 解码 DTO、连接/事件生命周期、协议错误映射 | 选择用户、模块身份或权限结果 |
| Host Context | 从可信窗口/认证会话派生调用者和 request/task | 接受 renderer 自报身份 |
| Application Service | 一个用例的编排、事务/幂等/取消/审计 | 直接持有 SQL 细节或实现 Provider 协议 |
| Capability Gateway | 能力上限、授权交集、调用前检查 | 替代领域 Manager 的资源归属校验 |
| Domain Manager | 领域状态机和不变量 | 解析 Tauri/HTTP 输入或跨领域私有表 |
| Repository/Adapter | 持久化和外部协议适配 | 决定产品权限和流程 |

## 3. 优先补齐的设计

### P0：建立 Application Service 层

先从高风险路径抽取三个用例服务，而不是一次性重写全部 Manager。当前已完成第一个最小切片：

1. `ProviderCallService`：已完成基础版本，绑定 execution context、能力网关和 Provider provenance，再调用 `ProviderManager`；Provider revision、取消、幂等和审计 warning 仍由 Manager/后续 service 补齐。
2. `ModuleReleaseService`：已完成最小版本，统一编排 stage → commit；`ModulePublisher` 保持文件/摘要端口和恢复实现。operation id、幂等发布和跨进程锁仍待补齐。
3. `ModuleCapabilityDispatchService`：从可信 runtime handle 获取 context，调用 `HostCapabilityService`，再转入 Provider/Skills/MCP 具体 adapter。

每个服务必须有输入/输出契约、事务边界、错误分类和 AC；Tauri command 只负责调用服务，不再直接串 Repository + Manager。

### P1：冻结模块运行时生命周期

建议状态：`discovered → staged → validated → installed → enabled → draining → disabled`，异常状态为 `failed` 和 `recovery_pending`。更新必须有 release/operation id，重复提交可安全返回已有结果；旧版本在新版本通过加载 smoke 前保留。

必须另行决定：

- artifact 来源与签名信任根（SHA-256 只能证明完整性）；
- 同 realm Federation 是否仅限受信任包，还是改用独立进程/WASM；
- runtime handle 如何产生和失效，不能由 renderer 构造；
- 在途请求取消、撤权、更新和卸载之间的终态语义。

### P1：发布恢复从“同实例安全”提升到“进程安全”

当前实现已在实例 mutex 之外增加 `module_release_locks` 数据库 lease，并用唯一键保护独立 publisher 的发布互斥；但 lease 过期、进程强杀恢复、CAS 版本指针、孤儿版本清理和 crash-injection 测试仍待补齐，并需验证 Windows/macOS/Linux 的 fsync/rename 语义。启动恢复应同时更新 DB 的禁用状态、失败事件和 orphan cleanup 结果。

### P2：统一契约和可观测性

- 所有应用服务使用统一 `OperationId`、错误类别（denied/invalid/stale/timeout/cancelled/unknown）和审计摘要。
- manifest、capability、release event、Host API 均带 schema/version；破坏性变更使用新版本或兼容迁移。
- 增加跨层追踪：`request_id → task_ref → operation_id → update_event`，但禁止记录 token、凭据、完整输入输出。

### P0.5：先修正当前实现中的可扩展性风险

这些事项不一定需要新功能，但在进入 FR-004 runtime 前必须解决或明确冻结：

1. **收紧可信注册根**：将 `ModulePermissionRepository::register_module` 从普通公开写入口改为仅由 Publisher/受信任发布服务调用的内部端口；`execution_context` 不再接受任意调用方传入的 `user_id`，而是接收已认证的宿主会话或由宿主创建的不可伪造上下文（D032，代码切片仍待完成）。
2. **发布操作可重放**：为一次发布分配 `operation_id`，以 `(module_id, version, integrity)` 做幂等键。重复请求返回已有结果；不同摘要不得覆盖同一版本；失败事件、恢复事件和清理事件都绑定同一个 operation（D031，代码切片仍待完成）。
3. **Lease 失效语义**：D031 已冻结全局锁、60 秒 TTL、15 秒内续租、失锁即停止提交、过期清理和释放告警；实现仍需补齐续租、恢复和故障注入证据。
4. **孤儿文件处理**：DB 提交失败后版本目录可能仍留在 store 中。恢复流程必须把 orphan version、未完成 staging 和 `recovery_pending` 作为可观测状态，采用延迟清理而不是启动时盲删。
5. **manifest v1 冻结**：补齐 schema version、宿主兼容范围、entry 类型、依赖/共享依赖、来源类别、最大包大小和能力列表的规范化规则。manifest 仍不参与 artifact digest，但必须单独校验并纳入未来签名范围。

## 4. 面向未来功能的复用判断

| 未来能力 | 是否可复用当前边界 | 还缺什么 |
| --- | --- | --- |
| Workbench 流式 | 可以，复用 Host Context、Provider revision、取消和 unknown-result | `ProviderCallService`、部分输出持久化决策、真实 HTTP 中断测试 |
| 多用户 | 可以，替换当前固定会话解析器 | 认证会话、会话切换失效、跨用户缓存/权限隔离决策 |
| LAN | 可以复用 Application Services，不复用 renderer IPC | 认证中间件、速率/来源策略、网络权限和审计决策 |
| 模块运行时 | 只能复用发布器、Capability Gateway 和生命周期语义 | runtime supervisor、可信 handle、签名/隔离边界、加载/卸载 smoke |

结论：当前前置工作足以支撑下一步抽取中间层，但不足以宣称“未来版本已经被完全支撑”。只有 P0 应用服务层、P1 生命周期/进程安全和相应契约测试完成后，才适合进入真正的 FR-004 runtime 开发。

## 5. 建议的推进顺序

1. **文档收口（先做最小集合）**：D031/D032 已冻结；下一切片只同步受影响的 FR-004、服务边界、接口契约、数据模型和 V1 实现状态，不等待所有未来版本文档完成。
2. **Application Service 扩面**：保留 `ProviderCallService`、`ModuleReleaseService` 的外部行为，继续抽取 Skills、MCP、Workbench 的高风险用例服务。每个服务先定义输入/输出、错误分类、事务边界、取消和幂等，再替换一个入口并补测试。
3. **发布一致性闭环**：实现 operation id、重复提交语义、lease 续租/失锁终止、恢复事件、孤儿清理和故障注入；在 macOS 通过后再安排 Windows/Linux 文件系统与 SQLite 语义验证。
4. **可信包契约**：冻结 manifest v1、来源 allowlist、签名/信任根方案和包大小/资源上限。SHA-256 继续作为完整性校验，但不再被当作发行者认证。
5. **运行时 supervisor**：只在 1～4 通过后实现 runtime handle、`starting/ready/draining/stopped/failed` 状态、在途请求终态、加载 smoke、卸载清理和热更新回滚；Module Federation 仅作为受信任同 realm 包的加载技术。
6. **跨入口复用**：最后接入 Workbench streaming、多用户会话和 LAN HTTP。HTTP middleware 或 Tauri host 先构造同一种 `HostExecutionContext`，handler 不接受 `user_id`、`module_id` 或授权结论。

## 6. 验收门槛

- 任一公开入口都能追溯到 Host Context、Application Service、Capability Gateway、Domain Manager 和 Adapter。
- 授权撤销、版本切换、配置变更和取消不会伪造外部操作已回滚；未知结果可观察且不自动重放。
- 发布故障注入覆盖 DB 失败、指针失败、进程中断、重复提交和并发实例；恢复结果可重放、可审计。
- 规格、决策、接口、migration、实现状态和测试证据互相引用；没有仅凭“代码存在”提升功能状态。

## 7. 本轮复评后的明确不做事项

- 不把 `cargo test` 全绿解释为模块 runtime、签名信任或跨平台 crash consistency 已完成。
- 不在 operation/idempotency 代码和失锁测试闭环前继续扩大发布器 API。
- 不先实现远程 URL、任意 JS、通用 `invoke` 或同 realm federation，再用 Error Boundary 补安全。
- 不一次性重写所有 Manager；每次只替换一个 transport 入口，并保持旧契约和错误语义可追踪。
- 不为“文档全部完成”而阻塞正常开发；L2/L3 切片先更新对应权威规格和决策，L0/L1 可按滚动式规格边做边回写证据。
