## 3. 最小复用结构与共享契约

### 3.1 单一执行核心

在 `dgos-workbench` 内抽出不含聊天页面和聊天消息仓储的 `AiExecutor`（候选文件 `execution.rs`），复用已有文本流驱动与 `tools.rs` 的 `advance_tool_context`。抽取的是运行机制，不是复制代码；ChatManager、WorkbenchManager 和模块用例均调用它。ChatManager 继续负责聊天 history、destination fingerprint、附件归属及终态事务，WorkbenchManager 负责单任务审计；公共执行器不读取别人的聊天上下文。

`dgos-application` 增加 `AiService`（候选 `ai.rs`），依赖现成 workbench/skills crate，负责可信上下文、逐步准入、模块在途生命周期、确认及事件路由。依赖方向为 Tauri/LAN adapter → application → workbench → providers/skills/mcp/types/db；workbench 不反向依赖 application。application 实现 workbench 定义的窄 `AiExecutionGuard`/确认端口；核心不持有 Tauri AppHandle 或 JS 回调。

工具循环保留完整 Provider reasoning/tool message 往返及现有限制，不把 reasoning 序列化到普通 DTO/SQLite。纯文本真实流通过现成 stream adapter 产生 delta；工具回合仍沿现有非流式 Provider tools API，发阶段/提议/最终文本事件，不伪造逐 token 流。P1 的流式验收分别证明纯文本增量和工具阶段事件；不把“有 Channel”当工具 token streaming 已实现。

### 3.2 可信调用上下文

`AiInvocationContext` 是宿主内部类型，不实现 Deserialize，不作为 renderer DTO。包含：

- `HostExecutionContext`：user、来源、module/version/integrity、宿主 request_id。
- 账户 lease：由 SessionResolver 在同一锁下读取的 owner 和取消 token；同账户重登也换 token。模块 route 的 owner 必须与取得的 lease owner 相同；读后每次执行再验 token，避免 await 期间切换后冒用新账户。
- 模块授权代次：准入时捕获宿主数据库的 `(user_id,module_id,authorization_epoch)`，run 与每个 pending proposal 固定原值；后续不更新该值以追随重新授权。它与账户 lease 分别防止 revoke→grant 和同账户重登复活。
- 生命周期绑定：内置 window 或远程会话绑定；模块持有一个 `BoundModuleCall`，包括 runtime、attachment、page generation 和 control。不能把它换成模块上传的字符串身份。
- `run_id`、来源应用、取消 token、共享 MaintenanceGate 的 ActivityPermit、固定能力快照及宿主 deadline。

`client_request_id/call_id` 只用于传输去重，绝非身份、权限或任意取消令牌。输入中的 Provider/skill/server 等 ID 是选择器，读取必须受 context owner 限制。模块输入不接受聊天 session_id、宿主消息 ID、system prompt、认证信息、权限声明、账户 ID、CLI 路径或租约；业务参考字段也不能参与授权。

`ExecutionProvenance` 继续用 `caller=module` 和宿主 request_id 串起 Provider、Skills、MCP 审计；不得把模块运行写成 Workbench。模块版本、完整性和 runtime 的归属在运行绑定记录中关联，不能仅凭 caller=module 区分两个模块。

现有 `providers.call` 仍是非流式底层能力。D136 的 `host.ai` 是新增编排契约，以 `providers.call` 为必需授权；选了技能/工具时额外要求 `skills.execute`/`mcp.call`。不新增全能 `ai.*` 权限，不把聊天页内置授权转给模块。此增量须由共享文档写入者在 P1 前更新 FR-004/接口对应章节；保留旧原始 Provider stream 拒绝测试，新增编排入口的许可及拒绝测试。

### 3.4 流事件与终态

公共事件 envelope：`{run_id, request_id, seq, kind, ...payload}`，每个 run 的 seq 单调递增。事件类型：`started`（本次能力快照摘要）、`delta`、`reasoning_delta`（仅临时展示）、`phase`（model/awaiting_confirmation/tool；D140增补processing_result/final_answer）、`terminal`。`final_answer`仅在无工具调用的完整模型终止边界确认，不把工具前说明误标为最终答复。终态 payload：`{status, content?, error?, result_unknown, audit_warning, usage?}`；status 为 `succeeded | failed | cancelled | interrupted`。模块取消仍用 `1004028`，account lease 失效用 `1008007`；工具明细中的敏感参数只交宿主确认 UI，不广播给其他 module/view。D140共享执行增量不向模块或LAN授予聊天技能读取/恢复入口。

运行状态：accepted → running → awaiting_confirmation → running → terminal；accepted/running/awaiting_confirmation 均可转 cancelling，再终结。只有 executor 的单一 finalizer 有终结权。返回 ack、发取消请求、Provider 返回字节都不等于成功落账。

- 成功：执行完成，运行审计终态提交，再发 terminal；聊天沿原消息/任务事务返回持久化消息快照。
- 无副作用前取消：cancelled，unknown=false。调用已派发而结果无法确定：interrupted，unknown=true；已获得部分内容可显示并标记非完成，不能再接着执行工具。
- 固定失败：failed；Provider/MCP 原错误码保留，错误描述用固定类别，不含上游正文或地址。明确的 Provider 本地拒绝及上游认证、权限、参数、配额拒绝不标 unknown；transport、timeout、协议损坏和不确定失败保留 unknown。公共执行器本地输入、预算、选择变化、工具提议/次数、期限、空回复与执行失败使用[通用 AI 错误码](V1-错误码.md#23-通用错误00) 1000010～1000017。审计写失败与外部结果未知分别表达，不改成可自动重试的业务失败。
- Promise 正常返回的 terminal 与 Channel terminal 必须同 run/seq；页面只结算一次。传输断开不能保证“恰好送达”，宿主保证只终结一次；客户端走状态核实，不能自动重发。
- 终态写库前原子封存 BoundModuleCall 的取消竞争，同时继续持有 runtime 在途请求；取消先成功则保存取消终态，封存先成功则后续取消返回 false。终态存储期间不再改写已确定的业务结果，CAS 后返回与 Channel 使用同一终态；持久化失败另报 persistence_failed/audit_warning。
- 通道丢失/真实页面卸载取消所属 run；SPA 切换、隐藏、设置覆盖不注销通道，不停止运行。模块明确关闭当前 document 时要求先取消并等待本地终态，unknown 保留核实入口；不批量取消同 runtime 的其他 document。
- 热更新、禁用、账户结束撤销旧调用租约；晚到事件须同时匹配原 route/page generation、原 run 与前端 view 活性。终态后不接收 delta，不复活旧 view。

错误 DTO 固定为 `{domain, code, reason, result_unknown}`；`domain` 为 admission/provider/skill/mcp/execution/storage，`code` 仅填已登记数值，`reason` 是白名单类别。准入拒绝复用 `1004004`，在途额度复用 `1001005`，会话失效复用 `1008007`，模块取消复用 `1004028`，模块工具未确认复用 `1003019`；Provider/Skills/MCP 的领域错误保留原码。公共执行校验类别明确区分 invalid_input、context_too_long、selection_changed、confirmation_expired、tool_denied、tool_call_limit、generation_limit、persistence_failed、process_interrupted，不直接借用“聊天消息不存在”等不匹配的 1006xxx。尚无适用数值码的类别由 P1-C 在错误码权威文档登记后再落 DTO，不临时使用成功、任意整数或上游字符串掩盖。取消请求返回值和最终 `result_unknown` 分别表达本地控制与外部效果。

## 4. 逐次授权、Skills、MCP 与账户 lease

### 4.1 授权时机与固定快照

模块每次 start、每次模型外发、每次技能内容准备、工具提议批准后且真正 MCP 外发前，均由 guard 重新核验：当前账户 lease、runtime/attachment/page generation、发布模块的 version/integrity/enabled、manifest 对相关权限的声明、当前 grant，以及原 `authorization_epoch` 是否仍相等。只看 permission bool 不足以授权：false→true 后仍不得恢复旧 run/proposal。权限撤销阻止下一步；已经派发的外部请求不宣称被撤回。

Provider/model/revision 在 start 时固定，后续每轮由 ProviderManager 自身锁内重读验证；revision 变更或禁用即拒绝后续轮次，不自动选别的模型、默认账号或新凭据继续。P1 不添加 CLI 依赖。

Skills 使用现有校验与固定版本内容。当前 `ai-workbench` 是已有内容执行配置，不能冒充调用者 module_id：P1 的公共 executor 声明支持该 content profile，模块身份仍为 provider-console；只允许此 profile 当前可消费且 `required_tools` 为空的内容技能。调用 `prepare_content_skill_with_provenance` 后比对选中 version/hash；后续外发前重验所选技能仍可用且 pin 未变，不静默接受更新。若后续要支持其他 compatible_apps 或 required_tools 解析，应单独补齐技能契约，不在 P1 绕过现有检查。

#### 4.1.1 不可复活授权代次与撤销入口

最小数据增量为 `module_authorization_epochs(user_id, module_id, epoch)`，复合主键，epoch 为非负 64 位整数；首次授权/首次准入在事务中建立 0 代，之后每次撤销只增不减。行缺失、读取失败或溢出均拒绝执行，不能回退 0。grant 只改变权限 bool，不重置 epoch；普通运行结束、模块卸载/重装或清理任务审计均不得删除代次行。保留 owner/module 墓碑防止复用同 module_id 后回到旧代次。run binding 与 pending proposal 固定开始时的 epoch；任何不等即终止旧运行，重新 grant 只能供用户显式新建 run 使用。

采用每 owner/module 一代，而非每 permission 一代：撤销该模块任一能力均使该 owner 的旧 AI run/待批准直接 MCP 调用失效，避免多权限组合留下部分旧授权。不同 owner/module 不受影响；模块级 disable/uninstall 等失效则覆盖该模块所有已建立代次的 owner。范围必须在权限 UI 契约中说明。

| 失效入口 | 原子变更与保留规则 |
| --- | --- |
| 单项 revoke、批量撤权、撤销全部权限，包括已为 false 的重复撤销 | 同一事务修改权限并递增对应 owner/module epoch；重复 revoke 可以继续递增，不恢复旧值 |
| 模块 disable/uninstall、因崩溃策略自动禁用、完整性失败触发禁用、发布失败回滚后禁用 | 同一模块级失效事务递增该 module 全部 owner 代次，再撤 runtime/route；重新启用/安装不重置墓碑 |
| 模块更新、回滚或发布过程删除 manifest 声明并收回 grant、其他权限行删除/替换 | 权限收回与代次递增同事务；普通版本切换也撤销旧 runtime/proposal，旧版本号恢复不恢复旧 runtime 租约 |
| 显式停止、reload、热更新排空、崩溃、页面 attachment/page generation 失效 | 至少不可逆撤销原 runtime/route 的执行租约并销毁 proposal；没有 grant 变化时不强制递增持久代次，旧 runtime 永不重新签发 |
| 账户切换/退出/删除、应用退出 | 先取消现有可信账户 lease 并撤 route/proposal；账户删除的代次行清理由 §5.1 约束；重新登录不可沿旧 token 继续 |

所有权限撤销写入必须经过 DB 统一事务单元，覆盖 `ModulePermissionRepository` 的 revoke/批量删除及 publisher/management/崩溃自动禁用调用点；不得只在 UI command 递增。P1-C 负责仓储原语及全部现有 DB 写路径的代次落账，P1-R 负责 application 的检查/失效，模块发布与生命周期接线由唯一集成者落实。上表是写入口验收清单；实施时若发现额外直写权限路径，必须纳入同一事务，不以仅列出的命令作为完整覆盖证据。

并发线性化：同 module 的授权变更和下一步派发准入共用宿主短期 gate。撤销在 gate 内提交 epoch 后失效旧 pending；执行在 gate 内重读 grant/epoch、比较固定值、消费 proposal 并登记 dispatch permit，释放 gate 后才做 I/O。撤销先完成，则旧提议无论后来是否 grant 都拿不到 permit；permit 先成立则视为已准入的在途调用，撤销取消本地等待且禁止后续步骤，外部结果按 unknown 处理。gate 不跨网络等待；事务提交失败不返回撤销成功。按 module gate → 短事务/短 registry 锁排序，不反向持锁等待。直接 `ModuleMcpService::call_tool` 同样在等待前捕获代次，批准后比较，不能临时采纳最新 epoch。

### 4.2 工具确认与执行

模型只可提议显式选择的工具，保留 `tools.rs` 对单个 tool_call、唯一调用 ID、JSON object/schema、16 KiB arguments 和最多 8 次调用的检查。server/tool/schema/arguments 存于宿主内存，不取模型声明的 owner 或权限。
真实 Attachment lease 由 `ModuleHostBridge` 创建，在 supersede、`page_started`、窗口销毁撤销；账户 lease 由 `SessionResolver::agent_session` 原子取得。`module_run_ai` 的宿主 task 持有 service future 到审计和 `BoundModuleCall` 结算，即使 IPC Channel 断开也不丢弃 finalizer；退出先撤 attachment，再有界等待 AI 与 Provider mutation drain。
本批次新增 Tauri AI catalog/run/list/get/cancel command 与宿主 `resolve_module_mcp_confirmation` 接线；模块 `host.ai` 提供对应 typed 目录、run/事件、list/get/cancel 和 AbortSignal 取消。目录/历史/取消均使用当前 runtime-bound call，run 的事件按 route、attachment、view epoch、run/request id、单调 seq 隔离。静态源码不构成运行证据。
`run_builtin` 仍是未被生产 Chat/Workbench 消费的 host-only application 入口；现有两个领域消费者继续直接使用共享 executor，不宣称其切换到 `AiService`。provider-console 的编排入口只使用 `host.ai`；P2 CLI 宿主仍为独立交付。各项实际验证证据只维护于 V1 实现状态。

复用 ModuleMcpConfirmations 的宿主 UI 与一次性 pending registry，增加 run/proposal/schema/账户 lease/authorization_epoch 绑定。聊天提议可继续由已有聊天确认 UI 操作，模块提议必须由 App 根的宿主对话框操作，模块不能直接调用 approve。等待期间结束、取消、撤权或过期即销毁 pending；即使失效通知尚未送达，持久代次比较也会拒绝旧批准。

批准之后：在 §4.1.1 的派发准入 gate 内消费 pending → 重验 owner/账户 lease/runtime/grants/原 authorization_epoch/Provider revision/Skills pins/所选 MCP server 与 schema → 登记一次 dispatch permit；释放短期 gate 后由宿主创建现成 confirm_call 一次性 token，并使用 `call_tool_at_schema_cancellable_with_provenance` 执行精确请求。schema 变化拒绝并要求重新选择，不能用旧批准匹配新 schema。MCP audit_warning/unknown 阻止自动续跑模型。工具明确 `is_error` 且完整回包可作为工具结果交模型；transport timeout/unknown 不可冒充工具业务错误后继续。

确认和执行使用同一个消费点；禁止“模块确认一次 + workbench 再确认一次”。原 `ModuleMcpService` 保留直接 callTool 用例，复用相同 MCP manager 的 schema 固定和一次性 token 边界，并在自身批准后重新检查身份、租约和原授权代次；不提前 finish 整个 AI run。直接调用的预检和批准后准入也计入总期限；完整回包保留 audit_warning，超时/失联返回固定 MCP 类别并按 Interrupted 结算。

同 realm 官方模块不是安全沙箱：`host.rs:169-175` 已明确页面脚本可以调用宿主确认命令。本文沿既有受信任包准入边界，不声称一个弹框能够防恶意同 realm 模块；第三方不可信代码隔离不在本任务。

### 4.3 有界生命周期

| 场景 | 目标限制与处理 |
| --- | --- |
| 新模块 AI run | 总期限 120 秒，自准入起含技能准备、模型、逐次确认与工具；沿现有模块调用期限，不允许模块延长 |
| 内置聊天纯流 | 保留 10 分钟总期限、64 KiB 回复、24 KiB 上下文、16 KiB 当前输入 |
| 内置工具回合 | 保留 15 分钟回合、120 秒 proposal、120 秒单次模型、30 秒 MCP；每步取总期限剩余值与自身上限的较小值 |
| 模块确认/工具 | proposal 最多 120 秒但不超过 run 剩余；MCP 最多 30 秒且不超过剩余；用户等待耗尽期限也不派发 |
| 模块目录 / 技能准备 | 最多 10 秒；同样受 run/lease 取消约束；工具 schema 与内容总量计入现有上下文预算 |
| 主动取消、账户结束 | 先撤销 lease/路由、关闭 pending，再发取消；AI 清理等待上限 5 秒，未结算仍保留原归属、interrupt/unknown 核实，不伪报远端已撤销 |
| 模块停止排空 | 沿 supervisor 的 30 秒上限；AI 不允许占用脱离 BoundModuleCall 的后台任务 |
| 应用退出/重启 | 停止本宿主拥有的 run；启动把遗留 running 收敛为 interrupted，不恢复 token/proposal、不重放模型或工具 |

公共 AI 直接复用 `SessionResolver::agent_session` 在同一锁下返回的 `(HostSession, CancellationToken)`；虽然现有名称带 agent，其状态切换取消语义已可作为本地账户 lease。保留 `agent_lease/agent_session/close_agents` 现有名称、其他调用者和 P2 接口，不做全仓命名重构、不加重复别名。P1-H 只增加 AI 取得/校验该 token 和清理 run 的必要接线；退出沿现有失效点附加 AI 清理。LAN 使用其认证绑定的失效信号，与账户结束的 remote revoke 链共同取消，不把当前桌面账户作为远程请求身份。

## 5. 事务边界、并发与恢复

### 5.1 审计归属和数据设计

优先复用 `workbench_tasks`、skill_refs/tool_refs、Provider/Skills/MCP usage logs，不为模块创建 chat_sessions/chat_messages。模块运行使用 `kind=single`（当前数据库仅允许 single/chat）、`app_id` 为宿主绑定 module_id，运行 id 为宿主生成 request_id；既有 workbench 列表/record/cancel 加来源约束，不能只按 user 命中模块任务。

新增最小伴随表 `ai_run_bindings`，仅模块 AI run 需要，字段建议：`task_id`（PK/FK）、`user_id`、`module_id`、`module_version`、`module_integrity`、`runtime_id`、`request_id`（唯一）、`authorization_epoch`、`terminal_reason`、`result_unknown`。增加 `(user_id,module_id,task_id)` 查询索引；创建/结束时间及 Provider/模型从关联任务读取，供 `listRuns` 在 Started 丢失后定位。它记录不可伪造的来源与未知结果，不存 route、lease token、提示词、工具参数、模型完整输出。runtime_id/authorization_epoch 仅用于审计，不是恢复授权。另新增 §4.1.1 的最小授权代次表。最终 DDL 和 migration 号码由 DB 唯一写入者登记；不修改 m005 或已执行的 chat migration。

开始事务将任务、binding、选中 skill/tool refs 一起写入；失败前不得发外部请求。终态事务 CAS `running`，同时更新任务状态和 binding 的 terminal_reason/unknown；公共 wire cancelled 映射为既有 task interrupted + 明确原因。历史 running 由现有恢复流程收敛，配套更新 binding，不自动新建请求。无新账本/队列/通用工作流系统。

FK 与清理必须随 migration 同批交付：binding.task_id → workbench_tasks.id 使用 ON DELETE CASCADE；同时以 `(task_id,user_id)` 关联任务复合唯一键/FK，避免 task 与 owner 分离。binding 的 module/version/runtime 是历史来源，不向可卸载的模块/临时 runtime 建级联 FK，避免卸载抹去待核实历史。授权代次墓碑也不随模块卸载级联删除。新表账户归属沿现有用户域 purge 链处理，不虚构尚未核对的账户父表名；最终 DDL 由 P1-C 对齐现有 schema。

账户删除先失效账户 lease、撤路由并取消旧运行，随后在现有可恢复 UserDataDomain purge 流程中删除绑定、所属任务/refs 和授权代次行；顺序与 FK 一致，同一账户数据清理失败保留 deletion marker 供重试。旧 worker 只能 CAS 更新已存在且 owner 匹配的任务/binding，不得 upsert 被清理的数据或重建 epoch；这样有界清理超时后迟到结果也不会复活已删除账户。账户注销/切换不是账户删除，不删历史或 epoch。

普通历史清理沿既有任务保留策略，仅删除可清理的终态任务并由 FK 清 binding，活跃/待恢复的 running 不作为孤儿删除；清除后列表明确不再保证可核实，不能自动重放。启动恢复先把遗留 running 与 binding 原子收敛，再做孤儿核对；binding 无 task 是不变量损坏，不据此创建 task 或发请求。异常修复仅清理已确认无父任务的 binding，记录计数，不清仍被 grant 或存量运行引用的 epoch 墓碑。P1-C 必须覆盖 foreign_keys 开启、父任务删除级联、账户删除中断重入、迟到 finalizer、卸载后历史保留及跨账户 FK 拒绝的验证资产；这些是计划，本轮不执行。

业务结果由模块所有；P1 模块内存结果不进入 audit。`listRuns` 在 Started 丢失或重载后找回运行标识，`getRun` 核实已完成、失败或未知；两者都不能从审计读回结果正文。UI 必须如实说结果内容未保留，不把“状态成功”当作能重放输出。需要长期保存的后续模块通过其 `storage.*` 授权持久化自己的资产。

### 5.2 并发控制

| 冲突点 | 控制方式 | 失败策略 |
| --- | --- | --- |
| module call 重复投递 | 现有 router `admit_once(route, attachment, call_id)`；一个 BoundModuleCall 持有至终态 | 拒绝重复，绝不重复 Provider/MCP |
| 同 run approve/deny/cancel 竞态 | 沿 ToolSession 的 `Mutex<Option<context>>` 原子 take；token/终态 CAS | 只有一次批准或终态胜出；后到输入失效 |
| 两模块/两 document 并发 | 运行 registry 按 run_id 与可信 owner/module/runtime 绑定，复用每 runtime 在途上限 8 | 不沿用 Workbench 的“同 user 只有一个 tool task”限制到所有模块；一个模块不得取消另一个 |
| ChatManager per-user 生成槽 | 原聊天领域保持一用户一个生成槽 | 模块不借用聊天槽或聊天授权；资源限额仍由 module router/Provider 限流负责 |
| 账户切换与 await 后继续 | owner+token 原子取得；每步检查同一 token，单次 finalizer 排斥取消/成功竞态 | 旧 lease 永不复活；晚到结果不发新页面 |
| 权限/revision/schema 更新 | 固定 authorization_epoch；权限变更与派发准入共用短期 gate，revoke 事务单调增代；外发前比较快照 | revoke→grant 不使旧提议复活；先获得 permit 的在途调用不承诺跨网络撤回，后续步骤禁止 |
| 终态数据库失败 | 不重发外部请求；可沿聊天已有方式仅重试本地 terminal 写一次（200ms） | 失败返回 persistence_failed + 实际 unknown/audit 状态；重启恢复，不声称成功落账 |

锁序：模块派发/授权变更先 module gate，再短事务或短期 registry/slot；不得反向持锁等待 gate。任何 network、用户等待或外部进程操作都在 DB 事务和 slot/gate 锁外。ActivityPermit 覆盖完整 run 和 terminal 写，沿已有共享维护门禁。

### 5.3 幂等与重试

模块 call_id 去重只保证同次传输不重复执行，不将两个用户主动点击合并；UI busy 和同 document 的 active run 防双击。公共 run 的宿主 request_id 关联审计，不接受客户端选择另一个模块的任务 ID。保留聊天原 begin_generation/find_replay 事务规则，纯模块不套用聊天 message ID。

Provider/MCP 不自动重试；取消、超时、丢失回应、unknown 均先核实状态，不再次执行。读取目录/状态是独立只读操作，可以由用户刷新。重启不得从审计重构提示词或批准；原 run 无法续跑时用户显式新建。

## 8. P1 端到端验收设计

### 8.1 必须成立的真实闭环

1. **模块真实消费。** Given 无 Codex/Claude 安装、从未挂载 ChatWorkbench、已启用 provider-console 新版本并显式授予三种能力，当前账户已有获准使用的真实 Provider、可用内容 Skill 和已连接 MCP；When 从 `/apps/provider-console/documents/<id>` 选择服务/模型/技能/工具并发起请求；Then 模型请求实际包含固定技能内容，工具提议经宿主逐次确认并实际执行，再得到模型最终结果；Provider/Skills/MCP 来源均为 module，同一 request_id 可关联，聊天表没有新增会话/消息。
2. **真正增量。** Given 同一模块选择无工具的文本请求；When Provider 逐步返回；Then UI 在终态前展示多个实际 delta、可取消；工具模式展示真实阶段/提议/最终文本，不宣称 token streaming。
3. **AI 会话复用。** Given 无 CLI、聊天 React 页面未挂载；When 通过生产应用服务创建/发送内置 AI 会话；Then 同一 executor 完成文本流和选定技能/获准 MCP 路径，正确写回原 ChatManager 消息；另用实际聊天页面回归原用户行为。不能以 module 调用替代 AI 会话路径验收。
4. **权限与调用者隔离。** Given 模块 A/B 或两个 document、聊天同时存在；When A 无 grant、grant 在批准前撤销、伪造 run_id、旧 route 或换账户；Then 无越权外发，无批准复用、无误取消其他 run、无结果串入其他 view。
5. **生命周期。** Given 等待确认/流中/工具已发出；When 用户取消、明确关闭 document、账户切换或退出重启；Then 拒绝未发工具，已发未知结果如实标记，终态唯一，旧 lease/批准不恢复。设置覆盖、切标签不停止，不重发业务请求。
6. **业务资产归属。** Given 模块完成生成；When 查询聊天、workbench 历史和模块状态；Then 模块结果只在所属模块，宿主审计只保留运行元信息；查询不得读其他账户/模块的 run，也不能把状态查询当结果重放。

## 10. 外部调用与补偿、安全与日志

外部 Provider/MCP 均在事务外；超时、取消和未知结果无自动补偿写入外部系统，没有通用 rollback 承诺。需核实时只查原 run/连接/既有外部记录，不自动再次运行工具。调用超时取 §4.3 固定宿主上限。

凭据只由现有 managers/vault 解析；不得进 DTO、module package、审计、错误、日志。日志仅 run/request ID、允许的来源元信息、固定状态/错误类别、用量及耗时。提示词、技能完整正文、tool args/results、reasoning 和 upstream error body 不进入普通日志。用户可见 module result 是所属业务输出，和审计存储分开。
