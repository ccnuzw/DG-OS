## 1. 目标与定位

把能够对话和受控调用工具的内置 AI 助手持续完善为能够可靠理解上下文、按需使用技能和工具、清楚说明执行过程与结果、可安全继续工作的助手产品。

产品价值分三层：

1. **可靠可用**：发送不重复、停止不误发、失败可解释、未知结果不伪装成功；账户和权限边界在全过程有效。
2. **日常好用**：长对话不突然遗忘重要约束，附件能合理参与上下文，技能和工具不要求用户每次重新理解配置细节。
3. **持续做事**：复杂任务能分步执行、保留可核实进度、在中断后由用户安全继续，而不是无边界地自动运行。

不以“按钮更多”“支持更多模型名称”或“测试数量增加”作为成熟度指标。每个阶段必须改善真实用户场景，并保留失败、取消和权限边界的证据。

### 1.1 复用而不是重建

- 保留 `ChatManager` 的聊天历史、附件归属、目标确认和消息终态事务。
- 复用 `dgos-workbench` 的共享 execution 核心与 `dgos-application` 的可信上下文能力，不新建第二套 Agent loop、审批中心或运行状态真相源。
- Provider 协议适配、Skill 包安装、MCP 连接和凭据继续归各自领域管理；聊天只消费公开接口。
- CLI Agent 继续使用原生运行时；聊天不借其进程、工作目录或隐含权限获得能力。
- 不为统一类名强制把所有入口改成 `AiService::run_builtin`；先消除实际授权、生命周期、终态语义差异，再决定最小接线方式。

### 1.2 不纳入本轮主线

默认不做：多 Agent 团队、无人值守后台调度、任意本机目录扫描、内置 Shell／浏览器自动化、Skill 脚本／Hooks 执行、跨会话永久记忆、向量数据库、云同步、语音实时通话，以及 CLI 工作台功能复制。

OpenAI Responses API、PDF／Office 解析、并行工具调用和多会话并发生成保留为独立候选；只有真实场景证明现有接口不足，且对应契约、权限和预算明确后才进入。未纳入不是永久否定，也不允许借“完善体验”顺带实现。

| 阶段 | 用户收益 | 交付重点 | 进入条件 | 阶段出口 |

| CHAT-P5 长任务与恢复 | 中断后知道做了什么、下一步怎么继续 | 有界步骤、检查点、只读核实、显式继续 | P1～P4 对应依赖稳定；数据与恢复设计批准 | 已完成副作用不重放；旧权限不复活；未核实步骤不能作为成功继续 |

P1 优先；P2 是增强主轴。P3 的手选体验、P4 的执行状态展示可在 P1 后独立推进；自动加载／资源读取／大工具结果必须复用 P2 的预算规则。P5 不应抢在前面几项之前。P6 是贯穿各阶段的验收工作，不是最后一次“大验收”。

不承诺日历工期或虚构完成百分比。以可独立验收的切片滚动安排，每次只冻结下一批可执行任务；已解决的前置条件不重复评审。

### 4.2 不变量

- 一个逻辑发送只有一个持久请求身份；回执丢失只核实原请求，不通过新 ID 自动补发。
- 取消是停止意图，不等于上游撤销或未计费；任务成功、正文保存与审计成功分别准确表达。
- 终态唯一，晚到 delta／审批／回执不复活旧会话；生命周期退出先失效再清理。
- 不为修复聊天而破坏单任务、模块 `host.ai` 或 LAN 消费者。共享契约修改时同批更新调用方，LAN 不顺带获得桌面工具权限。
- 保留每账户一个生成槽、逐次 MCP 审批等现行限制；不在可靠性修复中扩大并发或权限。

## 5. CHAT-P2：上下文成为可管理的能力

### 5.1 分两步交付

**第一步：可解释的预算与准入。**

- 明确区分模型窗口、宿主文本预算、保留输出、Skills、历史、附件和工具结果占用；估算值与上游实际 usage 不混同。
- 用户发送前能知道哪些资料将进入请求、是否会淘汰历史，以及为什么拒绝；导入成功但不能发送时应在发送前给出可操作说明。
- 不只把 24 KiB 调大。先确定文本、工具与图片的计量方式、能力来源和 unknown 窗口的保守策略；未知模型不能按最大窗口处理。
- 让用户能移除本轮资料或缩小选取范围；不静默截断当前问题、固定指导或用户明确要求保留的内容。

**第二步：受控会话摘要。**

- 建议先提供用户显式触发的整理上下文，再评估自动触发；摘要涉及额外模型调用，必须说明目标、成本和失败语义。
- 建议摘要保存目标、已确认约束、重要结论、未完成事项与来源消息范围；不把摘要当事实授权，也不删除原消息。
- 摘要绑定会话、来源消息范围和修订；重新生成、来源变化或历史删除后必须失效或重算，不能继续使用过期摘要。
- 摘要与技能／工具结果均作为不可信内容，不能进入宿主权限指令。图片不伪装已提取文字，未知工具结果不总结成已完成。
- 失败或取消保留原上下文与原文，不循环自动重试；原请求仍放不下时明确阻断，不能偷偷降级发送。

### 5.2 验收场景

- Given 连续多轮资料讨论且早期存在必须保留的约束，When 触达预算并明确整理，Then 后续回答仍满足检查清单，原文可查、摘要来源可定位。
- Given 大文本附件或图片模型能力未知，When 准备发送，Then 在外发前说明限制，不出现“上传成功所以必能分析”的误导。
- Given 摘要生成失败、模型切换、小窗口或历史修改，When 再次发送，Then 预算重新核算，过期摘要不被使用，原对话不损坏。

实现落点优先为现有上下文装配和附件准备路径；若需提取独立预算模块，只保留一个权威计算实现。暂不引入向量检索或跨会话记忆。

## 6. CHAT-P3：从手选正文走向按需技能消费

### 6.1 推荐递进顺序

1. **显式使用先可靠**：清楚显示已绑定版本、顺序及失效原因；技能所需能力不可用时在发送前解释，不将管理页安装成功当作可执行保证。
2. **候选推荐**：先提供与任务相关的技能建议，由用户选择；推荐失败不阻断普通聊天，不自动安装、启用或更新。
3. **渐进加载**：批准后，在用户授权的已安装且启用集合中先提供最小描述目录，按需读取正文；固定本轮版本／哈希，记录实际加载项，而非仅记录候选列表。
4. **资源读取**：批准后，允许读取该固定技能包内受支持资源；通过资产身份和包内相对路径定位，校验大小、哈希、路径穿越、符号链接及跨包访问，纳入同一上下文预算。

模型提出的“需要某技能”只是一项选择请求，不授予权限。读取正文／资源时重新核验账户与技能可用性；包内文字不得授权工具、扩大目录或执行脚本。

### 6.2 验收场景

- Given 任务确实需要某技能中的参考资料，When 获准加载，Then 运行记录能证明加载了对应版本的正文／资源，并用随机标记或可核对产物证明消费，不以模型口头声称“已使用”作为证据。
- Given 无关任务或用户禁用自动加载，When 发送，Then 不把整个技能库注入请求，不增加隐式资源读取。
- Given 资源缺失、包被篡改、技能禁用或资源越界，When 请求加载，Then 明确拒绝、无文件越界、无脚本执行；不能静默换版本继续。

自动推荐、自动加载及资源读取分别交付、分别验收，不用一次“自动化开关”打包所有权限。`required_tools` 解析与授权另行明确，不从技能文字直接映射成许可。

## 7. CHAT-P4：工具执行过程可理解、可控制

### 7.1 优先补齐体验与结果处理

- 展示真实阶段：请求模型、等待审批、调用工具、处理结果、生成答复；显示工具来源、精确参数、耗时、错误与停止入口，不伪造百分比。
- 工具选择与工具授权分离：可讨论保留会话常用工具集合，但每轮重验连接和 schema，且保留现行逐次审批；“记住选择”不是“永久批准”。
- 大结果采取有界预览、明确截断标记及受控读取方案；不得把未展示部分伪装成模型已经读取。若持久化工具结果，先解决敏感数据、保留期限、删除和权限模型。
- 工具返回正文、链接或资源均不可信；不自动跟随外部链接，不将 MCP 图片 JSON 当作已完成视觉理解。
- 工具业务错误、协议错误、调用未发出、调用结果未知和审计失败分别表达；未知或审计异常不能驱动下一步有副作用调用。

### 7.2 流式工具协议作为独立切片

建议在阶段事件和失败语义稳定后再接入。两种 Provider 协议分别处理参数增量、调用身份、结束边界和 reasoning；JSON／schema 完整验证前不得提供可执行批准，更不得提前执行部分参数。最终助手正文尽可能沿已有流式呈现，不通过动画模拟模型 token。

仍保持串行执行。并行调用只在存在实际收益、工具独立性和副作用顺序可证明后另行设计，不能信任模型或 MCP annotations 的“只读”声明直接自动批准。

### 7.3 验收场景

- Given 一个需要两次工具调用的真实任务，When 依次批准，Then 每次参数与执行一致，结果确实回到模型，最终回答包含可核对结果且来源清楚。
- Given 审批期间 schema 变化、拒绝、过期或账户结束，When 尝试继续，Then 原批准失效、无工具派发。
- Given 已派发工具后断连／取消，When 无法核实结果，Then 呈现未知并停止自动推进，不自动重试或生成“操作成功”的回复。
- Given 流式工具参数未结束或已损坏，When 用户尝试操作，Then 无可执行批准；完整合法提案才进入原审批机制。

## 8. CHAT-P5：有边界的长任务与显式恢复

这不是恢复旧进程内存，也不是把聊天变成无人值守自动化。

### 8.1 推荐设计边界

- 计划／步骤属于当前会话运行，可显示目标、完成证据和下一步；不要求每句普通聊天都生成任务计划。
- 明确模型调用、工具调用、总时长、输出和费用预算；usage 缺失时显示未知，不把零当作实际消费。
- 检查点优先保存步骤身份、状态、结果引用和副作用回执；敏感正文是否持久化必须先决策。流式部分正文保存是独立持久化切片，不高频逐 token 写库。
- 重启后先只读核实；用户显式继续时建立新有效运行身份、重新验证 Provider／Skill／MCP、重新授权未执行操作。旧审批和旧租约不能复活。
- 有明确完成证据的副作用不得重放；结果未知的步骤先核实，无法核实则暂停并要求用户处理。不能以“继续任务”绕过 unknown。
- 只有批准继续后的新动作才进入执行器；不后台自动恢复、不自动换模型、不自动扩大预算。

### 8.2 验收场景

- Given 第一步外部写入完成、第二步前进程退出，When 重启并明确继续，Then 第一步不再执行，第二步在新授权下执行，历史与结果可核实。
- Given 写入已派发但回执丢失，When 恢复，Then 显示待核实而非重试；上游不支持查询／幂等时，不承诺恰好一次。
- Given 原账户结束、权限撤销或技能版本失效，When 尝试继续，Then 明确阻断，不能沿旧快照恢复执行权。

跨会话长期记忆、多 Agent、后台定时任务和多会话并发不属于本阶段默认范围。

## 9. CHAT-P6：用固定用户场景持续验收

### 9.1 场景集

| 场景 | 检查重点 | 证据要求 |
| --- | --- | --- |
| 普通写作与问答 | 首次配置、流式、修改指导、切标签、停止、再生成 | 生产界面＋真实宿主；获准真实模型单列 |
| 多轮资料分析 | 早期约束、附件、预算、摘要与原文追溯 | 固定资料和事实清单；模型产物人工核对，不只验证接口返回 |
| Skill 指导任务 | 手选／建议／加载／资源消费、版本变化 | 按阶段实际支持范围执行；无关技能不被加载 |
| MCP 连续任务 | 发现、选择、两次审批、调用、最终答案 | 回环确定性场景与真实模型＋受控真实 MCP 分别记录 |
| 失败与未知结果 | 首字前取消、断流、审批过期、工具断连、落库／审计失败 | 有界故障注入；检查派发次数、持久终态及用户反馈 |
| 生命周期与恢复 | 账户结束、窗口销毁、崩溃重启、显式继续 | 新进程及同一隔离库；不以重建对象代替进程重启 |

### 9.2 指标与交付标准

- **确定性安全指标**：重复派发、越权执行、旧事件串会话、未知副作用自动重放，目标均为零；发现一项即阻断相应路径交付。
- **任务完成质量**：每个固定任务有具体产物／事实检查清单；区分首次成功、用户干预后成功、失败和无法核实，不用“回复非空”代替完成。
- **上下文质量**：记录关键约束保留、来源引用准确性、压缩后遗漏与误导；至少覆盖中文长文本、英文、代码和混合附件。
- **操作负担**：记录完成场景需要的选择、审批和恢复动作；以真实减少无效操作为目标，不为减少点击取消安全确认。
- **性能与成本**：测首字延迟、取消到本地终态耗时、每任务模型／工具调用次数、已报告 usage；注明模型、服务、网络、样本数与代码版本，先建立基线再批准阈值，不虚构当前数值。

真实兼容矩阵至少分别列 OpenAI-compatible、Anthropic，以及 stdio／Streamable HTTP MCP 的实际测试来源。两种协议指向同一网关时注明，不计作两个独立厂商。官方服务、第二网关、安装版、跨平台与辅助技术缺口沿现有发布门禁维护，不要求每个局部切片重跑全量验收。

不得读取正式聊天、真实凭据或调用收费服务来“自动补齐证据”。使用隔离账户／库和明确获准的端点、模型、凭据及额度；缺授权只阻断该外部场景，其余本地工作继续。

## 10. 滚动执行与任务交接

### 10.1 每个任务包的固定内容

1. 用户场景与问题证据：复现事实、静态风险或新能力，三者明确区分。
2. 对应阶段与权威依据：已有功能／决策，或本次待批准范围。
3. 改动范围与不改什么：生产入口、共享契约、调用方、数据／权限影响。
4. 可执行完成判定：成功、拒绝、取消、未知结果、重复请求和生命周期中适用的分支。
5. 验证入口与隔离条件：复用现有 suite／example／WebView；新测试只保留能捕获消费者可见回归的行为断言。
6. 交付回写：对应实现状态条目、真实命令／结果、未覆盖范围、可继续的下一项。

同一阶段可拆多个小闭环，但每个都必须从输入到真实结果或真实拒绝贯通，不能交付仅有接口、模拟成功或未接线控件。共享 execution、DTO 和数据库变更指定一个集成责任人，避免多个任务各维护一套契约；独立界面／适配器切片可同时推进，集中集成验证。

### 10.2 评审与验证节奏

- 用户已授权全部批次：先落实P1公共边界，按依赖推进P2～P5，P6贯穿；采用D140保守取舍，不把无需进一步裁决的工程选择反复交回用户。
- 每完成一个用户场景闭环，集中执行受影响验证；涉及公共执行器时覆盖聊天、单任务、模块及 LAN 的受影响路径，不机械跑全仓库。
- 只有真实 WebView 行为受影响时运行对应桌面 smoke；真实 Provider/MCP 在首次接入、协议变化和阶段验收时按获准矩阵执行。
- 每个阶段出口检查目标、证据和剩余风险，更新下一批任务；用户提出真实阻断时优先回到相应阶段修复，不强行按表推进新功能。
- 正式状态和运行证据只写入 [V1实现状态](当前版本/V1-实现状态.md)；后续若批准其他版本归属，使用该版本指定的唯一状态入口。本文只维护目标、次序和待决边界。
- 对外契约／数据结构变化先明确兼容或迁移，迁移失败保留原数据；禁止用回滚代码重复外部副作用。

## 11. 已授权的保守取舍与保留边界

用户授权全批次实施后，由助手采用下表推荐起点，记录于D140；扩大审批、并发、脚本权限或自动后台执行仍不在授权范围。额外模型调用必须在产品中明确提示并由用户触发，开发验收外部端点与额度授权另行取得。

| 取舍 | 推荐起点 | 主要代价／风险 | 触发时机 |
| --- | --- | --- | --- |
| 上下文预算与压缩 | 先可解释预算，再显式摘要；自动压缩后置 | 摘要额外调用、费用、信息遗漏、个人数据持久化 | P2 第二步前，调整 D075 相关契约 |
| 技能自动化 | 建议选择 → 授权集合内按需加载；默认保留手选／空技能 | 选择误判、包内容注入、额外上下文消耗 | P3 自动加载前，明确对 D016/D018 及 V7 规划的增量 |
| 技能资源读取 | 仅固定包内已支持资源，无脚本／任意路径 | 资源敏感性、大小与预算、撤权竞争 | P3 资源切片前 |
| 工具选择与审批 | 可讨论记住选择；继续逐次批准，不默认扩大权限 | 高频审批的操作负担；扩大授权会增加副作用风险 | P4 工具集合行为变化前 |
| 工具结果保留 | 先内存有界处理；持久化按业务需要显式设计 | 原始结果敏感、存储保留／删除、摘要失真 | P4 大结果或 P5 检查点前 |
| 长任务恢复 | 只读核实＋用户显式继续；不自动重放 | 无查询能力的工具可能只能人工处理未知状态 | P5 数据／状态机设计前 |
| 并发 | 先保持每账户一个活动生成 | 等待审批阻塞其他会话，但避免提前引入预算和状态复杂度 | 真实场景证明阻塞严重后单独评审 |
