# DGOS 版本路线图

## 1. 文档目标

本文档是 DGOS 产品版本规划的权威索引，定义版本编号、范围边界、依赖关系和进入条件。

产品、研发、测试和运营讨论版本范围时，以本文档的版本矩阵为准；跨版本查看同一项能力如何增强时，使用[功能演进矩阵](功能演进矩阵.md)；各版本 PRD 负责展开详细的功能、接口、数据、业务规则和验收用例。

## 2. 版本命名规则

统一使用 `V1` 到 `V8` 作为产品版本编号。

**不使用**小数点版本号（例如不使用 V1.1、V1.2、V2.1）。每个版本是独立的产品阶段，有明确的业务目标和技术边界。

**版本编号**：V1、V2、V3、V4、V5、V6、V7、V8

**版本内阶段**：如果需要分阶段交付，使用发布门禁或阶段标记（例如 V1-P1、V1-P2），但对外仍然是 V1。

## 3. 业务术语口径

PRD 中业务概念优先使用中文名。英文只在第三方协议/API 名称、接口路径、数据库表字段、示例代码中保留。

| 中文术语 | 含义 |
| --- | --- |
| Provider 适配器 | 统一适配各厂商 AI 模型 API 的接口层，提供模型列表、调用、分类等能力 |
| Skills | DGOS 技能中心管理的 `SKILL.md` 内容包：官方内置库、第三方来源、本地版本与场景绑定；内容作为任务上下文使用，不执行（D016 取代早期“LangChain Tools”定义） |
| MCP | Model Context Protocol（Anthropic），DGOS 连接 MCP 服务器，桥接工具调用 |
| 应用模块 | 可热更新的独立功能单元，如 AI 工作台、无限画布、文件管理等 |
| 统一设计系统 | 所有模块强制复用的主题、色彩、字体、间距和 UI 组件规范 |
| 本地优先 | 数据存储在本地 SQLite，本地管理功能离线可用；调用云端模型或联网工具仍需网络；云端为可选增强 |
| 局域网模式 | 一台电脑启动 DGOS 后，局域网内其他设备可通过浏览器访问使用 |
| 发布门禁 | 某版本对外发布或进入下一版本前必须补齐的质量、安全、文档项 |
| 模型分类标签 | 内置维护的模型能力标签，如 text-generation、image-generation 等 |

## 5. 跨版本范围决策

### 5.1 V1 冻结决策

V1 聚焦底层能力框架，不求功能完整，只求架构正确、可扩展。

**核心能力（必须）**：
- Provider 适配框架：统一接口、OpenAI 适配器、模型分类标签
- 技能中心：官方内置库离线可用、至少 1 个第三方来源、工作台按固定版本使用（D016）
- MCP 管理：服务器连接、工具列表、调用桥接
- 模块系统：受信任的本地模块包动态加载、热更新、权限管理（Module Federation 只作为受信任代码加载方式，不加载任意远程 JS，见 D025/D028）
- 统一设计系统：主题系统、色彩规范、UI 组件库（10+ 组件）

**基础应用（必须）**：
- AI 工作台：简单对话、Provider 选择、历史记录
- 系统设置：Provider 管理、Skills 管理、MCP 管理、模块管理

**运行模式（必须）**：
- 单机模式：SQLite 本地存储，本地管理功能离线可用
- 局域网模式：HTTP 服务自动启动、简单认证、远程只读

**明确不包含**：
- ❌ 无限画布（V2）
- ❌ 应用市场（V3）
- ❌ 云端账号（V3 起，D040）
- ❌ 跨设备同步（V4）
- ❌ 实时协同编辑（V4）
- ❌ 组织管理（V5）
- ❌ 移动端（V6）
- ❌ Windows 支持（V1 先保证 macOS，Windows 作为 V1 发布门禁后首周补齐）

**技术债务上限**：
- 单个 Rust 文件不超过 1000 行（CI 检查）
- 单个 TypeScript 组件不超过 500 行
- 核心功能单元测试覆盖率 > 60%
- 文档覆盖率 > 80%

详见 [V1 冻结决策](../06-决策记录/V1-冻结决策.md)（D001 起，后续追加的决策同样适用）。

### 5.2 V1 发布门禁

V1 功能完成后，正式发布前必须通过发布门禁。发布门禁不扩大 V1 主范围，只补齐上线安全项：

**必须完成**：
- [ ] 所有 P0 功能验收通过
- [ ] 应用启动时间 < 2 秒
- [ ] 模块加载时间 < 1 秒
- [ ] API 响应时间（P95）< 200ms
- [ ] 零 P0/P1 安全漏洞
- [ ] 核心功能单元测试覆盖率 > 60%
- [ ] 用户文档完成度 > 80%
- [ ] 开发者文档完成度 > 80%
- [ ] macOS 安装包构建成功
- [ ] 安装测试通过（全新环境）

**可延后但需记录**：
- Windows 支持（发布门禁后首周补齐）
- Linux 支持（V2）
- 性能监控系统（V2）
- 完整的崩溃报告（V2）

### 5.3 画布系统边界

无限画布是 DGOS 的核心价值功能，但复杂度高，单独作为 V2 完整交付：

**V2 画布系统（完整版本）**：
- 画布视口（缩放、拖拽、平移）
- 完整节点类型（10+ 种：Image、Prompt、LLM、Generator、Loop、Conditional、Transform、Function 等）
- LLM 节点可选择 Skills
- 节点连线系统
- 实时执行（用户操作立即执行）
- 循环节点（LoopNode）
- 工作流 JSON 格式定义
- 工作流导入导出
- 布局算法（自动排版）
- 工作流模板库

**从老项目学习**：
- ✅ 保留交互体验（拖拽手感、连线交互）
- ✅ 保留节点类型设计（经过验证的节点类型）
- ✅ 兼容老项目工作流格式（可选，便于用户迁移）
- ❌ 不复制单体架构（避免单文件巨石）
- ❌ 不复制耦合设计（画布独立模块）

**V2 不拆分子版本**：画布系统作为一个完整版本交付，内部可以分阶段开发，但对外只有一个 V2。

### 5.4 应用市场边界

应用市场让第三方开发者发布模块，作为 V3 完整交付：

**V3 应用市场（完整版本）**：
- 云端账号基础：注册（邮箱/手机号）、登录、个人资料（D040）
- 应用浏览（分类、搜索、筛选）
- 应用详情（截图、描述、评分、评论）
- 应用安装（从市场下载）
- 应用更新（自动推送、手动确认）
- 应用卸载
- 开发者提交（表单、资料、截图）
- 人工审核流程（审核队列、审核标准）
- 版本管理（多版本共存、回滚）
- 评分评论系统
- 下载统计

**市场模式**：
- 中心化（官方服务器）
- 必须登录云端账号（D010）；账号基础能力（注册、登录、个人资料）随 V3 交付（D040）
- 人工审核（V3），自动化检查（V4+）
- V3 全部免费，V4+ 支持付费

**V3 不拆分子版本**：应用市场与其依赖的账号基础能力作为一个完整版本交付。未登录时本地功能、本地模块包与局域网协同照常可用。

### 5.5 云端与协同边界

云端功能为可选增强，不影响本地优先原则，作为 V4 完整交付：

**V4 云端与协同（完整版本）**：
- 账号扩展（在 V3 账号上绑定本地用户、多设备管理，D040）
- 官方 Provider（积分制、按 token/张/秒计费）
- 跨设备数据同步（选择性同步）
- 实时协同编辑（画布、工作流）
- 指针显示和锁机制
- CRDT/OT 冲突解决
- 充值支付系统
- 用量统计和账单

**协同细节**：
- A 用户移动节点，B 用户实时看到
- 显示其他用户指针（带用户标记）
- 编辑节点时锁定，其他用户只读
- 冲突自动合并或提示用户选择

### 5.6 企业化边界

企业功能服务团队和组织，作为 V5 完整交付：

**V5 企业化（完整版本）**：
- 组织管理（创建组织、组织设置）
- 成员管理（邀请成员、角色权限）
- 组织 Provider（组织级别配置）
- 项目分组（组织内项目分组；不提供任务、看板等项目管理功能，见[产品蓝图](产品蓝图.md) 2.4 节）
- 企业账单（组织用量统计）
- 审计日志（操作记录、合规审计）

**不做的企业功能**：
- 企业 SSO（V6+）
- 细粒度 RBAC（V6+）
- 私有化部署（V7+）

### 5.7 移动端边界

移动端扩展到 iOS 和 Android 平台，作为 V6 完整交付：

**V6 移动端（完整版本）**：
- iOS 应用（Swift/SwiftUI）
- Android 应用（Kotlin/Jetpack Compose）
- 移动端 UI 适配
- 触摸手势优化
- 离线同步
- 推送通知

**依赖**：V4 云端同步必须稳定，否则移动端数据无法同步。

## 6. 版本主链路

```
V1 (3个月)       底层框架 + 基础应用
    ↓
V2 (2个月)       画布系统（完整）
    ↓
V3 (2个月，含账号基础，门禁时重估)  应用市场（完整）
    ↓
V4 (3个月)       云端与协同（完整）
    ↓
V5 (3个月)       企业化（完整）
    ↓
V6 (3个月)       移动端（完整）
    ↓
V7 (4个月)       AI Agent（完整）
    ↓
V8 (持续)        开发者生态（持续完善）
```

**总计时间线**：
- V1-V3：约 7 个月（第一年）
- V4-V5：约 6 个月（第二年上半年）
- V6-V8：持续迭代（第二年下半年+）

## 7. 跨版本依赖与进入条件

| 进入阶段 | 必须已经稳定的底座 | 本阶段解锁的能力 | 缺失时的阻塞 |
| --- | --- | --- | --- |
| V1 对外发布 | Provider 框架、Skills/MCP 管理、模块系统、基础应用、通过发布门禁 | 最小可用框架正式开放 | 不得扩大用户开放或进入 V2 |
| V2 画布系统 | V1 稳定，模块系统验证通过 | 画布视口、完整节点、工作流 | 模块系统不稳定会导致画布无法独立开发 |
| V3 应用市场 | V1 模块系统稳定；账号服务在本版本内先行交付 | 云端账号基础、应用浏览、安装、提交、审核 | 模块加载不稳定会导致应用市场不可用；账号未就绪时市场下载与提交不可用 |
| V4 云端与协同 | V2 画布稳定，V3 应用市场与账号稳定 | 账号绑定与多设备、跨设备同步、实时协同 | 本地功能不稳定会导致同步冲突频繁 |
| V5 企业化 | 账号系统稳定（V3 交付、V4 扩展） | 组织管理、成员权限、企业账单 | 账号系统不稳定会导致权限混乱 |
| V6 移动端 | V4 云端同步稳定 | iOS/Android 应用 | 云端同步不稳定会导致移动端数据丢失 |
| V7 AI Agent | V2 画布稳定，V4 云端稳定 | 自主任务、多 Agent 协作 | 画布和云端不稳定会影响 Agent 执行 |
| V8 开发者生态 | V3 应用市场稳定，V4 云端稳定 | 开发者门户、API 市场 | 市场和云端不稳定会影响生态建设 |

## 8. 研发推进建议

### 8.1 V1 最小 MVP

先冻结并交付 V1，通过发布门禁后再进入 V2。

**理由**：Provider 框架、Skills/MCP 管理、模块系统是所有后续功能的共同底座。如果 V1 的架构、接口、数据模型不稳定，后续版本会产生较高返工成本。

**V1 开发节奏**（12 周）：
```
Week 1-2:   核心框架骨架（Tauri + Rust + React）
Week 3-4:   Provider 框架（OpenAI 适配器）
Week 5-6:   Skills/MCP 管理（连接、调用）
Week 7-8:   模块系统（Module Federation）
Week 9-10:  基础应用（AI 工作台、系统设置）
Week 11:    局域网模式（HTTP 服务、认证）
Week 12:    测试、文档、发布准备
```

### 8.2 V2 画布系统完整交付

V2 作为独立版本交付画布完整功能，不拆分子版本。

**理由**：画布是核心价值，拆分会导致用户体验不完整。一次性交付完整画布系统，用户可以立即获得完整价值。

**V2 开发节奏**（8 周）：
```
Week 1-2:   画布视口、基础节点（5 种）
Week 3-4:   完整节点（10+ 种）、实时执行
Week 5-6:   循环节点、工作流导入导出
Week 7-8:   测试、优化、文档
```

### 8.3 V3-V8 滚动推进

V3 到 V8 按版本顺序滚动推进，每个版本独立立项、独立验收、独立发布。

**原则**：
- 不允许两个大版本并行开发
- 每个版本通过发布门禁后才进入下一版本
- 紧急 Bug 修复不占用版本号

## 9. 维护规则

1. 新增或调整版本范围时，先修改本文档，再同步版本 PRD 和功能规格。
2. V1 功能使用稳定编号（V1-FR-001 到 V1-FR-010）；V2+ 功能在通过版本进入开发门禁前不分配正式编号。
3. 版本范围迁移必须同时标注原位置、目标位置和历史材料角色，避免两个版本同时宣称同一范围。
4. 当前完成度只链接实现状态和执行证据，不用路线图或演进矩阵替代验证。
5. 图表只可视化本文档已有事实；调整图中版本、状态或依赖时，必须同步对应表格。
6. 新增功能或调整主责能力时，必须同步[功能演进矩阵](功能演进矩阵.md)。

## 10. 风险与应对

| 风险 | 概率 | 影响 | 缓解措施 |
| --- | --- | --- | --- |
| V1 时间估算不准 | 高 | 高 | 每周回顾，及时调整范围；保持 MVP 最小化 |
| V2 画布功能范围蔓延 | 中 | 中 | 严格按版本边界开发；完整功能列表冻结 |
| V3 应用市场安全问题 | 中 | 高 | 人工审核；代码扫描；安全测试 |
| V4 协同编辑冲突频繁 | 中 | 中 | 完善冲突解决；用户测试；逐步放量 |
| 团队规模不足 | 高 | 高 | 优先交付 V1-V2；后续版本根据团队规模调整 |

## 11. 后续规划

V8 之后的版本规划将根据以下因素动态调整：
- 用户反馈和需求优先级
- 技术发展趋势
- 竞品动态
- 团队规模和能力

可能的后续方向：
- V9：多语言支持
- V10：插件市场（不同于应用市场，更轻量）
- V11：嵌入式版本（可嵌入其他应用）
