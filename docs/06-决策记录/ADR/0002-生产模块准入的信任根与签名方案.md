# ADR-0002 生产模块准入的信任根与签名方案

- **状态**: Accepted（范围限于 V1 内置首方模块；由助手按任务指令选定，仓库与会话中没有用户逐条评审记录，评审结果待定）
- **日期**: 2026-10-29
- **决策者**: 助手起草并采用，评审结果待定
- **关联**: D041、D047、D049、D052、D057（摘要 v2）、D058、D061（发布构建门禁）、V1-FR-004

## 背景

D041 规定模块执行的唯一准入边界是编译进宿主的固定清单；D047 冻结了清单来源、信任根、轮换与撤销的边界但未给出落地方案；D049 已有产物比对门禁，但 `BUILTIN_PINS` 为空，仓库没有随包模块目录，生产中没有任何模块可执行。需要一个 V1 内可落地、不开放用户任意信任、不引入远程 URL 或第三方未签名包的方案。

## 决策

采用方案 A：`BUILTIN_PINS` 编译进宿主，宿主二进制及其平台代码签名是唯一信任根。随包模块放在 `bundled-modules/<module_id>/<version>/`，宿主启动时对资源目录重算摘要并与 `BUILTIN_PINS` 比对，通过后才发布到模块存储。版本替换、撤销、轮换全部经由重新构建宿主完成。V1 不实现模块签名、签名清单、远程清单或用户信任入口。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. 编译进宿主的 pin，信任根是宿主二进制及平台代码签名 | 无新密钥管理；pin 与代码同时审计、同时发布；撤销与轮换语义简单；可被门禁机器检验 | 更新模块必须重新发布宿主；撤销在重启后才生效；平台代码签名本仓库未实现 | 采用 |
| B. 宿主内置公钥，加载随包或下载的签名清单 | 可不重建宿主更新模块；支持运行中撤销 | 需先定义密钥生成与保管、轮换与双钥过渡、反回滚计数、过期、撤销分发；这些属于发布与市场流程，V1 没有基础设施 | 不采用；前置条件见下 |
| C. 用户本地确认后加入清单 | 开发者体验好 | 违背 D041：把同 realm 执行的准入交给用户点击 | 不采用 |

## 后果

- 正面：生产清单可以非空；准入判定只依赖宿主二进制内的数据；运行期的目录复核补上“解包后包内容被改”的检测。
- 负面：模块与宿主同周期发布；撤销需要重启；信任根的真实性依赖平台代码签名，而本仓库未实现，因此在签名落地前，“可信”只表示“与构建一同发布”。
- 风险与缓解：
  - ~~摘要排除 `manifest.json`~~ → 已由 D057 解决：摘要 v2 覆盖 manifest 的全部安全字段（`permissions`、`requires`、`entry`、`name`、`id`、`version`）和包内全部文件，`pin` 变为 `v2:` 加十六进制；校验与执行绑定同一次读取。旧值只作为一次性迁移的输入，不能执行。
  - 运行期复核可被拥有本机写权限的攻击者与二进制一并替换 → 这超出本地应用的威胁模型，由平台代码签名与操作系统保护承担，不在本仓库声称解决。
  - 复核失败时的行为 → 随包模块整体不供给，宿主其余功能继续，错误写入日志。

## 方案 B 的前置条件

实现签名清单之前必须先另行决策并有评审记录：密钥生成与保管位置、轮换与双钥过渡流程、反回滚计数的存储与重置策略、清单过期时间、撤销分发与离线行为、清单与 `package_digest` 的绑定、密钥泄露后的应急流程。

## 遵守方式

- `BUILTIN_PINS` 的每一项必须通过 `cargo test -p dgos-modules`（`the_shipped_bundle_equals_the_builtin_pins` 与 `every_builtin_pin_is_a_canonical_binding`）。
- 新增、替换或移除 pin 与随包目录必须在同一次变更中完成。
- `npm run release:build` 在 Tauri 构建后对构建产物内的 `bundled-modules`（`.app` 资源目录，存在 `.dmg` 时再挂载比对一次）运行 `verify_release_bundle`，失败即非零退出（D061）。`npm run release:verify -- <目录>` 供未来流水线对解包后的安装产物运行。仍未覆盖：平台代码签名与公证、签名清单、公证后安装包的字节比对、Windows/Linux 产物；本仓库没有 CI，这些记录为发布阶段门禁（D056）。
- 放宽任何一条或改为方案 B，新建 ADR 并把本条改为 `Superseded by ADR-{NNNN}`。
