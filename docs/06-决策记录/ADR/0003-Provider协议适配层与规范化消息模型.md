# ADR-0003 Provider 协议适配层与规范化消息模型

## 背景

D-待编号-A 把 Anthropic Messages 协议和任意三方兼容服务的接入纳入 V1：用户选择厂商（首批 OpenAI、Anthropic、自定义）和适配器、填写 base_url 和 API Key。现有宿主契约（`dgos-types/src/provider.rs` 的 `ChatRequest`、`ChatResponse`、`ChatChunk`、`ToolChatRequest`、`ToolMessage`）是 OpenAI Chat Completions 的形状，已被三条调用链消费：桌面 `call_provider` 命令、工作台文本与 D022 工具循环（`dgos-workbench`）、模块 `providers.call`（D048/D051，入参已冻结）。`ProviderManager::create_adapter` 只按 `provider_type` 字符串分派到唯一的 `OpenAIAdapter`，未知类型返回 `1000000`。

两种协议的差异集中在：system 的位置；Anthropic 必填 `max_tokens`、要求 user/assistant 交替；工具调用参数是 JSON 字符串还是对象；工具结果是独立 `tool` 角色还是 user 消息里的 `tool_result` 块；思考块带签名，工具循环里要原样回传；SSE 是单一 `data:` 流还是带类型的事件序列；错误体与状态码（如 529）。三方服务之间的差异集中在：鉴权头、是否有模型列表端点、推理字段名、结构化输出支持级别、个别参数名。用户自填的 base_url 无法穷举，所以宿主不能假定服务的具体行为，必须对未知服务保守发送、宽容读取。

## 决策

保留现有 DTO 作为宿主规范契约，只追加可选字段；每种协议一个适配器（`openai_compatible`、`anthropic`），只在发送前和接收后做双向转换。用户添加 Provider 时选择**厂商**，厂商是编译进宿主的数据条目，下面有一个或多个**端点**，端点对应适配器、默认 base_url、官方主机和**兼容画像**（首批 OpenAI、Anthropic 和“自定义”；“自定义”有两个端点，没有默认地址，供 Ollama、LM Studio、网关和暂无内置条目的服务使用；新增厂商只加数据，复用适配器）。base_url 的主机属于该端点的官方主机时用官方画像，否则用该适配器的保守通用画像，只发送标准字段，响应宽容读取，被上游点名拒绝的可选参数降级重试一次。适配器按画像字段决定请求形状，不为厂商写分支代码。模型的分类（`kind`）由宿主按规则计算，能力只作为提示，宿主不据此拦截请求，哪些场景可用哪些模型留给后续的场景绑定设计。追加字段、映射规则、错误归一、重试和超时的具体口径登记在 D-待编号-B，设计细节见 [FR-001 技术设计](../../03-功能规格/V1/01-底层能力/01-Provider适配框架-技术设计.md)。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. 现有 OpenAI 形状 DTO 作规范契约，追加可选字段，协议适配器双向转换 | 三条调用链和模块 `providers.call` 入参不破坏；旧 JSON 照常解析；改动集中在 `dgos-providers` | Anthropic 适配器转换分支多（system 提升、同角色合并、参数字符串与对象互转）；规范契约带有 OpenAI 命名 | 采用 |
| B. 新建中立内容块中间表示，边界处转换 | 对两种协议对称；以后加图片、文件输入更自然 | 三条调用链、工作台工具循环、前端 store、IPC 契约和 OpenAPI 都要改；V1 不做图片输入，收益不足 | 不采用：成本高于 V1 需求 |
| C. 每个厂商一个 `provider_type` 和适配器 | 厂商差异处理最直接 | 类型和代码量随厂商增长，测试面成倍扩大；D-待编号-A 已由用户排除 | 不采用 |
| D. 在方案 A 之上加用户可见的“厂商”选择：厂商下是端点列表，选端点才确定适配器并预填 base_url，官方画像挂在端点下；另设“自定义”厂商 | 已知服务开箱即用；一个厂商可以同时提供 OpenAI 兼容和 Anthropic 兼容两种地址（如 DeepSeek）；新增厂商只加数据；没有内置条目的服务有明确入口 | 厂商表需要维护，每个新厂商要按官方文档登记并用真实 Key 验证；用户自填的未知服务仍要有保守通用画像 | 采用（用户要求保留厂商选择，先选厂商再选兼容适配器，首批 OpenAI、Anthropic）。过程中我先后把它判断为多余的一层、又设计成厂商与适配器一一对应，用户两次纠正后改为端点列表加“自定义” |

## 后果

- 正面：现有调用方无需修改即可用新协议；新增厂商只加一行厂商表数据和画像数据；协议适配器可以用请求和响应 golden fixture 独立测试。
- 负面：规范契约里出现只对一种协议有意义的字段（如思考块的 `opaque`），需要在 D-待编号-B 的映射表中逐项说明；未来若加入图片输入，可能仍要转向方案 B，届时另立 ADR。
- 风险与缓解：
  - 三方服务偏离协议 → 通用画像保守发送、宽容读取，已知差异写成画像并登记官方文档来源与核实日期；真实 smoke 按服务分别记录；偏差在画像数据里修，不在适配器里加特判。
  - 画像匹配被域名欺骗或用于把凭据发往其他主机 → 按完整域名标签匹配；画像只决定请求形状，不能改变目标主机、放宽 HTTPS 或接触凭据；不跟随重定向。
  - 自动分类误判（名称特殊的非对话模型被归为对话）→ 分类规则表带用例，增补规则必须增补用例；V1 不提供远程模型的用户覆盖（D014），手动模型可以指定类别。
  - 推理内容丢失导致下一轮工具调用被上游拒绝（Anthropic 的签名思考块；DeepSeek、Kimi、智谱要求回传的 `reasoning_content`）→ `ToolMessage.reasoning` 原样保存，上游返回什么推理字段，下一轮就带回什么字段；工作台保留整条 assistant 消息，不按单个工具调用重建（技术设计 B01-51、B01-66）。
  - 规范契约逐步膨胀 → 新字段必须至少对应一种协议的明确映射，并登记在 D-待编号-B；不能映射的能力不进契约。

## 遵守方式

- 公共类型只在 `dgos-types` 定义一份；新增字段必须是 `Option` 或带 `serde(default)`，并有“旧 JSON 可反序列化”的测试。
- `ProviderManager` 只按 `provider_type` 分派协议适配器；适配器内不出现按厂商名称的分支，差异读取画像字段。
- 每个协议适配器有请求与响应 golden fixture 测试，覆盖技术设计中登记的分支 ID。
- 新增或修改画像必须附官方文档来源和核实日期；增补分类规则必须同时增补用例。
- 宿主不信任前端提交的模型分类、能力和主键（AGENTS.md §3），保存时一律重算。
