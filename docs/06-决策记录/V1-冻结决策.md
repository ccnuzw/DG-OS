# V1 冻结决策

本表记录影响范围、协议和架构的一致性决策；新证据到达后追加新编号，不改写历史结论。

**当前解释规则**：D016 取代 D003/D005 中“Skills 必须是 HTTP/CLI 或 LangChain Tools”的定义，并限定 D006 的模块授权不能被技能内容继承为任意执行权限。旧条目原文保留用于追溯；MCP、轻量运行时及应用市场边界不变。

## D001 使用 Rust + Tauri 而非 Node.js + Electron

- 状态：已冻结
- 日期：2024-01-XX
- 背景：老项目 infinite-canvas-ccnuzw 使用 Python + FastAPI，单文件 19,038 行，无法维护。需要选择能强制模块化、性能好的技术栈。
- 决策：采用 Rust + Tauri 2 作为核心技术栈
  - 后端：Rust + Axum + SeaORM
  - 桌面：Tauri 2
  - 前端：React + TypeScript + Vite
- 理由：
  - Rust 编译期强制模块化，不可能写单文件巨石
  - Tauri 轻量（<10MB），Electron 过重（>100MB）
  - Rust 所有权系统防止内存泄漏
  - 零成本抽象，性能优于 Node.js
  - 类型安全，编译期捕获大部分错误
- 后果：
  - 学习曲线较陡，但有强制模块化保证
  - Rust 生态成熟度低于 Node.js，但核心需求已满足
  - 团队需要学习 Rust，但可避免重蹈老项目覆辙
- 替代方案：
  - Node.js + Electron：生态好但无法强制模块化，容易重复老项目错误
  - Go：性能好但缺少桌面框架支持

## D002 使用 SQLite 而非 PostgreSQL

- 状态：已冻结
- 日期：2024-01-XX
- 背景：项目定位为本地优先工具，需要零配置、易备份的数据库。
- 决策：采用 SQLite 作为唯一数据库
- 理由：
  - 本地优先：单文件数据库，无需独立进程
  - 零配置：无需安装和配置数据库服务
  - 易备份：复制单个文件即可
  - 性能足够：读取速度接近 PostgreSQL，写入对单用户足够
  - 体积小：整个库只有几百 KB
- 后果：
  - 不支持多进程并发写入，但单机模式不需要
  - 无内置用户权限系统，但通过应用层控制
  - 局域网协同时只有主机有写权限
- 替代方案：
  - PostgreSQL：功能强大但需要独立进程，违背本地优先原则
  - 嵌入式 PostgreSQL（libpq）：仍然过重

## D003 不使用 QuickJS/Node.js 作为 Skills/MCP 运行时

- 状态：已冻结
- 日期：2024-01-XX
- 背景：初期误以为需要实现 Skills/MCP 执行引擎，考虑嵌入 QuickJS 或 Node.js。
- 决策：不嵌入任何 JavaScript 运行时，Skills/MCP 自己运行
- 理由：
  - Skills 和 MCP 是现有标准，有自己的运行环境
  - DGOS 只需要管理（安装/配置）和调用（HTTP/CLI），不需要执行
  - 类比：Chrome 管理扩展但不实现扩展引擎
  - 避免增加 50MB+ 的运行时体积
  - 简化架构，减少维护负担
- 后果：
  - Skills 必须提供 HTTP API 或 CLI 接口
  - 无法在沙箱中执行不可信 JavaScript 代码
  - 需要依赖外部 Skills/MCP 服务的稳定性
- 替代方案：
  - 嵌入 QuickJS：轻量但需要实现完整的 Skills 执行引擎，过度设计
  - 嵌入 Node.js：生态好但体积大，违背轻量化原则

## D004 使用 Module Federation 实现模块热更新

- 状态：已冻结
- 日期：2024-01-XX
- 背景：应用模块需要独立开发、独立版本管理、热更新（无需重启）。
- 决策：使用 Webpack Module Federation（或 Vite 版本）实现模块系统
- 理由：
  - 成熟方案：已在生产环境大规模使用
  - 真正的运行时加载：不是预打包，而是动态 import
  - 共享依赖：React、Zustand 等只加载一次
  - 独立构建：每个模块可以独立开发和发布
  - 版本管理：支持多版本共存
- 后果：
  - 需要配置 Webpack/Vite 插件
  - 模块必须暴露标准入口点
  - 共享依赖版本需要协调
  - 打包体积略大于单体应用
- 替代方案：
  - iframe 隔离：隔离性好但通信复杂，性能差
  - Web Components：标准但生态不成熟
  - 动态 import：简单但无法共享依赖

## D005 Skills 和 MCP 使用现有标准协议

- 状态：已冻结
- 日期：2024-01-XX
- 背景：需要让 DGOS 能够使用 AI 工具和能力扩展。
- 决策：直接使用现有 Skills（LangChain Tools）和 MCP（Model Context Protocol）标准，不自定义协议
- 理由：
  - Skills 已有成熟生态（LangChain、LlamaIndex 等）
  - MCP 是 Anthropic 主导的标准协议
  - 不重复造轮子，复用现有生态
  - 降低学习成本，开发者熟悉标准
  - 自动兼容未来协议演进
- 后果：
  - Skills 调用方式：可选增强，非必选
  - MCP 工具调用：通过标准协议桥接
  - 需要维护 Skills/MCP 远程仓库连接
  - 受标准协议限制，无法自定义特殊能力
- 边界说明：
  - Skills：AI 增强工具（文本生成、图像处理等）
  - MCP：系统集成工具（文件操作、搜索、外部 API 等）
  - 在 LLM 节点中，Skills 是可选的，用户可以直接调用 Provider

## D006 权限模型采用粗粒度模块级权限

- 状态：已冻结
- 日期：2024-01-XX
- 背景：模块需要申请权限才能调用系统能力（Provider、Skills、MCP、存储等）。
- 决策：V1 采用粗粒度权限，后续版本细化
  - 权限类型：`providers.call`、`skills.execute`、`mcp.call`、`storage.read`、`storage.write`、`network.local`
  - 授予对象：整个模块，不区分模块内的具体功能
  - 授权时机：模块安装时用户一次性授权
- 理由：
  - V1 简化实现，快速交付
  - 模块通常需要完整的能力集合，细粒度意义不大
  - 官方模块自动授予所有权限
  - 避免频繁的权限请求打断用户
- 后果：
  - 模块获得权限后可以调用所有 Provider（不能限制特定 Provider）
  - 模块更新增加权限时需要用户重新授权
  - 无法实现细粒度审计（例如模块 A 调用了哪个具体 Provider）
- 后续细化：
  - V2.0 可以细化为 `providers.call:openai`、`storage.read:projects/own` 等

## D007 局域网 HTTP 服务始终开启

- 状态：已冻结
- 日期：2024-01-XX
- 背景：用户希望一台电脑启动 DGOS 后，局域网内其他设备可以访问使用。
- 决策：桌面应用启动时自动启动 HTTP 服务，监听 `0.0.0.0:3000`（可配置端口）
- 理由：
  - 简化用户配置，无需手动开启"共享模式"
  - 端口可配置，避免冲突
  - 只监听局域网，不暴露到公网
  - 提供简单认证（用户名/密码）
- 后果：
  - 占用一个端口
  - 需要防火墙配置（macOS 会弹窗询问）
  - 需要简单认证机制防止未授权访问
  - 远程设备只读模式，不能修改 Provider 配置
- 安全措施：
  - 默认生成随机密码
  - 强制认证，无认证不能访问
  - 远程设备权限受限（只能使用，不能配置）
  - 可在设置中关闭服务

## D008 所有模块强制使用统一设计系统

- 状态：已冻结
- 日期：2024-01-XX
- 背景：用户明确要求"系统的整体样式管理和组件管理需要统一化，不能每个应用一个主题"。
- 决策：建立统一 Design System，所有模块必须复用，禁止自定义样式
  - 主题系统：亮色/暗色主题，全局切换
  - 色彩规范：主色、辅助色、语义色（固定）
  - 字体规范：字体家族、字号、字重（固定）
  - 间距规范：4px 基准，固定间距档位
  - UI 组件库：基于 Shadcn/ui，封装为 `@dgos/ui`
- 理由：
  - 保持视觉一致性
  - 降低开发成本（不需要重复实现组件）
  - 主题切换全局生效
  - 避免混乱的用户体验
- 后果：
  - 模块开发者必须使用 `@dgos/ui` 组件库
  - 禁止使用 inline styles 或自定义 CSS 覆盖主题变量
  - 模块审核时检查样式合规性
  - 需要维护完整的组件文档和示例
- 强制机制：
  - CI 检查：扫描模块代码，禁止出现 `style={{}}` 或自定义 CSS 变量
  - 审核阶段：人工检查视觉一致性
  - 模块示例：提供模板项目，强制使用正确方式

## D009 无限画布分多版本实现，不阻塞 V1

- 状态：已冻结
- 日期：2024-01-XX
- 背景：无限画布是核心价值功能，但复杂度高。用户要求"重点是搭建底层能力和底层框架"。
- 决策：无限画布功能拆分到 V1.2-V1.5 分步实现，V1 聚焦底层框架
  - V1.0：底层能力（Provider/Skills/MCP/模块系统）+ 基础应用（AI 工作台、系统设置）
  - V1.2：画布核心（视口、缩放、拖拽）+ 5 种基础节点
  - V1.3：10+ 种节点类型，节点连线系统
  - V1.4：实时执行，循环节点
  - V1.5：工作流导入导出，布局算法优化
- 理由：
  - 底层框架搭好，后续快速迭代
  - 避免 V1 范围过大，延期风险高
  - 可以先验证框架可扩展性
  - 画布功能独立性强，不阻塞其他模块
- 后果：
  - V1 无法展示核心价值（画布），但可以展示框架能力
  - 需要在 V1.2 前保持用户兴趣
  - 画布模块需要提前设计接口，避免 V1 架构不兼容
- 从老项目学习：
  - 保留交互逻辑（拖拽、连线、缩放手感）
  - 重做架构（避免单文件巨石）
  - 节点执行方式：实时执行（用户操作立即执行）
  - 支持循环节点（LoopNode）

## D010 应用市场采用中心化模式，人工审核

- 状态：已冻结
- 日期：2024-01-XX
- 背景：需要应用市场让开发者发布模块，用户下载安装。
- 决策：应用市场中心化设计，V1.5+ 实现
  - 中心化：官方服务器托管，不支持第三方源
  - 审核方式：人工审核（V1.5），自动化检查（V2.0+）
  - 下载权限：必须登录云端账号
  - 收费模式：V1 全部免费，V2.0+ 支持付费应用
- 理由：
  - 中心化保证应用质量和安全性
  - 人工审核初期质量高，后续自动化
  - 避免三方源带来的安全风险
  - 与云端账号系统集成
- 后果：
  - 开发者必须提交到官方市场
  - 审核周期可能较长（初期）
  - 无法安装未审核的应用（除非开发者模式）
  - 需要维护审核团队和流程
- 审核标准（V1.5）：
  - 代码安全性检查（无恶意代码）
  - 权限合理性检查（申请的权限必须有使用场景）
  - 视觉一致性检查（使用统一设计系统）
  - 功能完整性检查（不能是空壳应用）
  - 文档完整性检查（必须有使用说明）

## D011 官方 Provider 采用积分制，按类型计费

- 状态：已冻结
- 日期：2024-01-XX
- 背景：云端账号需要提供官方 Provider 能力，使用积分消耗。
- 决策：积分计费模式（V2.0 实现）
  - 文本生成：按 token 数量 * 倍率计算积分
  - 图片生成：按张数计算积分
  - 视频生成：按秒数计算积分
  - 音频生成：按秒数计算积分
- 理由：
  - 透明计费，用户可预期成本
  - 不同类型资源成本不同，分别计费合理
  - 倍率可根据模型质量调整
- 后果：
  - 需要维护模型价格表
  - 需要实时计算和扣除积分
  - 需要积分充值系统
  - 需要用量统计和账单
- 自配置 Provider：
  - 用户自己配置的 Provider（自己的 API Key）无需积分
  - 云端账号和自配置 Provider 可并存
  - 默认优先使用自配置 Provider（排序第一）

## D012 Provider 支持同类型多配置和排序机制

- 状态：已冻结
- 日期：2024-01-XX
- 背景：用户可能有多个 OpenAI 账号，或同时使用官方 Provider 和自配置 Provider。
- 决策：支持配置多个同类型 Provider，通过排序和默认选择机制使用
  - 同类型多个：可配置多个 OpenAI、Claude 等
  - 排序机制：用户可拖拽调整 Provider 顺序
  - 默认选择：没有明确指定时，使用排序第一的 Provider
  - 手动选择：在需要选择模型的地方，用户可以明确选择 Provider
- 理由：
  - 灵活性：用户可以根据需要切换账号
  - 容错性：一个 Provider 失败可以切换到备用
  - 成本优化：可以配置免费额度的多个账号轮换使用
- 后果：
  - Provider 列表需要显示排序序号
  - 调用时需要明确使用哪个 Provider
  - 错误重试时可以尝试同类型其他 Provider
- UI 行为：
  - 系统功能（无选择界面）：使用默认排序第一个
  - 用户界面（有选择控件）：用户可以选择或使用默认

## D013 局域网协同需要简单认证和实时状态显示

- 状态：已冻结（认证方式部分已被 [D053](#d053-局域网远程认证采用随机访问凭据加会话不使用用户名密码) 取代，其余仍有效）
- 日期：2024-01-XX
- 背景：局域网协同时需要识别用户身份，并实时显示在线状态。
- 决策：实现简单的用户名/密码认证
  - 认证方式：HTTP Basic Auth 或 JWT
  - 用户管理：主机创建临时账号或使用主机本地用户
  - 实时显示：WebSocket 连接，显示在线用户列表
  - 权限控制：远程用户只读模式，不能修改配置
- 理由：
  - 简单认证足够局域网场景
  - 无需复杂的 OAuth 或 SAML
  - 实时状态提升协同体验
- 后果：
  - 需要维护 WebSocket 连接
  - 需要心跳检测断线重连
  - 认证信息不加密（局域网内认为安全）
- 协同细节（V2.0）：
  - 画布协同：A 用户移动节点，B 用户实时看到
  - 指针显示：显示其他用户的鼠标指针和标记
  - 锁机制：编辑节点时锁定，其他用户只读
  - 冲突解决：CRDT 或 OT 算法（待设计）

## D014 模型分类标签内置维护，不自动提取

- 状态：已冻结
- 日期：2024-01-XX
- 背景：需要给模型打标签（文本/图片/视频/音频），供不同场景使用。
- 决策：模型分类标签由 Provider 适配器内置维护
  - 标签类型：`text-generation`、`image-generation`、`video-generation`、`audio-generation`、`text-to-image` 等
  - 维护方式：在 Provider 适配器代码中硬编码
  - 不自动提取：不从 Provider API 的 metadata 自动提取（大多数 Provider 没有统一格式）
- 理由：
  - 各 Provider 的模型能力描述格式不统一
  - 自动提取容易出错，需要人工校准
  - 内置维护保证准确性
  - 模型能力相对稳定，不需要频繁更新
- 后果：
  - 新模型发布后需要更新适配器代码
  - Provider 适配器需要维护模型能力映射表
  - 用户无法自定义模型标签（V2.0 可支持）
- 示例：
  ```rust
  // OpenAI 适配器中维护
  match model_id {
      "gpt-4" | "gpt-3.5-turbo" => vec![Capability::TextGeneration],
      "dall-e-3" => vec![Capability::ImageGeneration],
      "whisper-1" => vec![Capability::AudioToText],
      _ => vec![],
  }
  ```

## D015 模块更新自动推送，图标显示版本提示

- 状态：已冻结
- 日期：2024-01-XX
- 背景：应用市场上的模块更新后，需要通知用户。
- 决策：自动检测更新并推送通知
  - 检测频率：每次启动 + 每天一次后台检测
  - 通知方式：图标小红点 + 版本号显示
  - 更新方式：用户手动点击更新（不自动静默更新）
  - 更新提示：显示更新日志（Changelog）
- 理由：
  - 自动推送让用户及时获得新功能
  - 手动更新给用户控制权
  - 避免静默更新带来的兼容性问题
- 后果：
  - 需要维护模块版本比对逻辑
  - 需要显示 Changelog 的 UI
  - 需要处理更新失败的回滚
- 更新流程：
  1. 后台检测到新版本
  2. 图标显示小红点，版本号变化
  3. 用户点击查看更新日志
  4. 用户确认更新
  5. 下载新版本模块
  6. 热重载模块（无需重启）

## D016 Skills 定位为官方优先的本地技能中心

- 状态：已冻结（产品定义；具体接口、物理表和执行权限细节须在实现前完成技术评审）
- 日期：2026-10-27
- 来源：用户明确要求“自己的官方内置 Skills 分类库、内置部分技能、预置大型第三方来源、供本地不同应用场景使用”，并确认本地技能中心方案。
- 背景：旧版 V1-FR-002 依赖单个硬编码远程地址，把技能等同于 HTTP/CLI 工具包，无法表达官方内置内容、Agent Skills 与多场景使用。
- 决策：以 `SKILL.md` 型 Agent Skills 为主，DGOS 统一分类和内容身份；核心官方技能随应用提供，官方精选保留第三方署名与许可，第三方生态通过预置适配器按需获取。来源预置不等于整站打包。
- 决策：目录、版本化本地内容、用户启用状态、应用/会话绑定、任务实际加载彼此独立；安装不执行脚本，已安装不等于已授权，运行任务固定内容版本。

## D021 MCP V1 客户端边界与安全默认值

- 状态：已冻结（V1-FR-003 实施基线）
- 日期：2026-10-27
- 来源：用户确认采用 MCP 技术设计中的默认方案，先冻结 V1 最小可交付边界，再开始实现。

- 决策：新 artifact 未通过 manifest、版本、完整性和来源验证时不得写入当前版本指针；旧版本在新版本可启动前保留。热更新必须可重复执行且不自动重放模块副作用。

## D029 模块 manifest 是能力上限，授权 broker 只授予交集

- 日期：2026-10-28

## D030 Application Service 是跨入口用例编排边界

- 状态：已冻结（V1 前置架构优化）
- 日期：2026-10-28
- 决策：Tauri command、未来 LAN handler 和模块 runtime 不直接组合 Repository、Capability Gateway 与 Domain Manager；跨入口业务流程必须通过 transport-independent Application Service / Use Case。Transport 只解码业务 DTO、绑定宿主上下文并映射协议错误；Application Service 负责用例编排、授权调用、幂等/取消/审计和错误语义；Domain Manager 继续负责资源归属、状态机和领域不变量。
- 决策：先从 Provider 调用和模块发布两个高风险路径抽取最小服务；不得以一次性重写所有 Manager 为前提，也不得把当前已抽取的服务误认为全部应用服务层已完成。

## D031 模块发布互斥采用可恢复 lease

- 状态：已冻结（发布一致性切片）
- 日期：2026-10-28
- 背景：当前发布器已在实例 mutex 外增加 `module_release_locks` 数据库 lease，可保护两个独立 Publisher 的正常并发；但 TTL 过期、进程强杀、释放失败和跨平台 SQLite 锁语义尚未形成稳定契约。
- 决策：V1 先保持全局 `modules` 发布锁，避免不同 Publisher 同时改写版本目录、current pointer 和 DB 指针；每个发布操作带唯一 `operation_id` 与随机 `owner_id`。lease TTL 为 60 秒、续租间隔不超过 15 秒；续租失败或发现 owner 不再持有 lease 时停止提交并进入 `recovery_pending`。旧 lease 过期后由下一次操作清理。释放失败只记录告警，不覆盖原始发布结果。
- 决策：发布按 `(module_id, version, integrity)` 幂等；相同摘要的重复请求返回既有结果，不同摘要不得覆盖同一版本；同一 `operation_id` 重试不得重复执行文件切换或数据库写入。lease 只提供操作互斥，不替代文件系统 fsync/rename、DB 事务或启动恢复。
- 验证要求：等待未过期 lease、过期 lease 清理、错误 owner 不能释放、强杀后恢复、重复发布、DB/指针故障注入，以及 macOS/Windows/Linux 的 SQLite/文件系统行为分别验证；在这些证据前不得宣称跨进程 crash consistency 完成。

## D033 模块 runtime supervisor 第一阶段：本地受信任加载与热更新回滚

- 状态：已冻结（FR-004 runtime supervisor 第一阶段切片；不启动 Federation、远程加载或 renderer 模块 IPC）
- 日期：2026-10-28
- 背景：Publisher 已能签发 `ModuleRuntimeHandle`，但谁驱动生命周期、加载 smoke 如何只接触已验证 artifact、draining 与能力 dispatch 如何原子协调、在途请求终态、热更新切换与回滚失败语义尚未冻结；直接编码会让 dispatch、更新和卸载各自定义终态。
- 决策：`dgos-modules::ModuleRuntimeSupervisor` 是 runtime 生命周期的唯一驱动者，状态为 `starting → ready → draining → stopped`，`starting/ready/draining` 可进入 `failed`，`failed` 在在途请求清零后可进入 `stopped`。handle 只由 Publisher 依据启用的 DB 当前行、current pointer 和包摘要签发；`mark_ready`/`begin_draining`/`stop`/`fail` 仅 crate 内可用，外部只能读状态和申请请求准入。每个 handle 带宿主生成的 `runtime_id`，同一版本重启不复用旧实例身份。
- 决策：加载器端口 `ModuleLoader` 只接收 Publisher 构造的 `VerifiedModuleArtifact`（规范化的本地包目录与入口、module/version/integrity），不接收 URL、任意路径或 renderer 输入。入口必须是包内规范相对路径，只允许 ASCII 字母数字与 `. _ - /`，拒绝 `..`、绝对路径、scheme（如 `https:`/`data:`/`file:`）、查询/片段、反斜杠和百分号编码；包内不得含 symlink，canonical 入口必须仍位于包目录内。`LocalArtifactLoader` 的 smoke 仅在宿主侧验证入口为非空、UTF-8、≤16 MiB 的普通文件，start 前重算包摘要；它不执行 JavaScript，不证明 Federation 可用。未来 Module Federation adapter 只能实现该端口，并只作为受信任同 realm 包的加载技术，不是安全沙箱。
- 决策：请求准入与状态转换在同一锁内完成；只有 `ready` 接受新请求，`draining/failed/stopped/starting` 立即拒绝且不执行操作。对外仍映射现有 `PermissionDenied`（1004004），不新增错误码；精确原因保留在 `ModuleRuntimeError::NotAccepting`。每个已准入请求恰好结算一次：`succeeded`、`failed`、`denied`（授权未通过，操作未运行）或 `interrupted`（future 被丢弃，外部结果未知）。宿主不自动重试、不在新 runtime 重放；新的尝试必须是新的请求和新的 request_id。drain 最多等待 30 秒；超时则 runtime 进入 `failed`，不取消、不伪报结果，在途请求清零后才释放加载器资源。
- 决策：热更新只作用于当前 `ready` 且与 DB 当前发布行一致的 runtime：stage（manifest/路径/摘要/来源校验）→ 对 staged artifact 执行加载 smoke → commit（指针与 DB）→ 签发并启动新 handle → ready 后切换注册表 → drain/stop 旧 runtime。commit 前任一失败不改变指针、DB 和旧 runtime，并清除 staging。commit 后新 runtime 启动失败时，依据 commit 前快照（版本、摘要、DB manifest、entry）以 CAS 回滚指针和 DB，记录 `activation/failure` 与 `rolled_back/success` 事件，旧 runtime 保持 `ready`；回滚失败时旧 runtime 进入 `failed`，模块 `is_enabled=false`、移除 current pointer 并记录 `disabled/failure`，需重新发布后才能启动。相同 `(module_id, version, integrity)` 的重复更新返回 unchanged，不重启 runtime；已存在但非当前的版本不会因重复发布被重新激活。
- 决策：commit 到切换之间，旧 runtime 的新授权因身份不再匹配 DB 当前行而 fail-closed；已通过授权的在途请求按原 runtime 结算。能力调用唯一入口仍是 `ModuleCapabilityDispatchService` → `HostCapabilityService`，旧的 `authorize_handle`/`dispatch_handle` 捷径删除；每次 dispatch 派生新的 request_id，但模块/版本/摘要/用户只来自 handle。
- 影响：无 migration、无新 IPC/command；`module_update_events` 新增阶段值 `load_smoke`、`activation`、`rolled_back`、`disabled`。supervisor 尚未接入桌面宿主 wiring，也没有 renderer 加载、生命周期钩子、状态保存/恢复或 UI；这些属于后续 FR-004 切片。已知限制：`update`/`start` future 不具备取消安全，commit 后被调用方丢弃时旧 runtime 无法再通过授权，需显式 stop/start 或启动恢复收敛；接入 transport 前须由调用方保证运行到完成或另行冻结取消语义。
- 验证要求：Rust 单元/集成测试覆盖状态转换、draining 拒绝、在途终态与 interrupted、drain 超时、加载失败、远程/逃逸/未验证/摘要不匹配拒绝、更新成功、smoke 失败、启动失败回滚、回滚失败禁用、重复更新幂等和 hot swap 不重放；这些证据不等同真实 WebView/Federation 加载或桌面 E2E。
- 后续修订（D041～D046）：本条“`LocalArtifactLoader` 的 smoke……不执行 JavaScript，不证明 Federation 可用”仍然成立，但它不再是生产装配的加载器；真实执行、准入与加载器截止时间见 [D041](#d041-v1-可执行模块包的准入来源宿主固定清单摘要不等于可信)～[D045](#d045-js-缓存共享依赖与资源释放的实际限制)。本条已知限制“`start` future 不具备取消安全”不变，宿主层由 D034 规避；加载器 future 的丢弃现在只发生在 supervisor 的截止时间内，加载器必须取消安全（D044）。

## D034 模块宿主操作编排：operation ID、取消语义、并发与 renderer 信任边界

- 状态：已冻结（FR-004 宿主接入与生命周期编排切片；不启动 Module Federation、WebView、UI 或远程加载）
- 日期：2026-10-28
- 背景：D033 的 `ModuleRuntimeSupervisor` 已能驱动 runtime，但 `start`/`update` future 不具备取消安全（commit 后被丢弃会让旧 runtime 无法授权），且旧 runtime 释放失败后已离开注册表、`stop` 无法重试。接入 Tauri command 前必须冻结谁拥有操作、取消意味着什么、并发如何排队、失败如何恢复，以及 renderer 能提交什么。
- 决策（所有权与 operation）：`dgos-application::ModuleOperationManager` 是 transport 唯一入口，统一持有 `ModulePublisher` 与 `ModuleRuntimeSupervisor`。`start`/`stop`/`update` 同步完成受理（校验、冲突检查、登记、派发），随后在脱离调用方的后台任务中执行，并立即返回宿主生成的 UUID `operation_id`；renderer 不能提供或指定 operation ID。同一个 ID 贯穿 `update` 的 staging 目录与 `module_update_events` 审计。状态为 `queued → running → succeeded | failed`，终态不再改变；结果只有 `started/stopped/updated/updated_pending_release/unchanged` 与稳定错误类别。操作与 runtime 状态通过 `get_module_operation`/`get_module_runtime_status` 轮询，进程内保留最近 64 条已结束操作，更早的返回 `operation_not_found`，进程重启后不保留。
- 决策（取消语义）：command future 被取消、窗口关闭或等待超时只停止等待，不取消已受理的宿主 operation；`wait` 对丢弃安全。已开始的 `start`/`update`/`stop` 含 commit、回滚和释放等外部副作用，不提供协作式取消，也不提供“取消排队中操作”的接口。后台任务内再隔离一层任务，loader 或 supervisor panic 只使该操作以 `internal` 失败，队列继续推进。
- 决策（并发）：宿主内所有生命周期操作按受理顺序严格串行（后一个等待前一个终态）；同一模块同时最多一个未结束操作，冲突的新请求被拒绝为 `operation_in_progress`（可重试），不排队、不合并。`recover()` 是启动步骤，只在 `uninitialized`/`unavailable` 时可执行，`recovering` 时拒绝，已 `available` 时拒绝；`recover()` 被丢弃会回到 `unavailable`，可重试。
- 决策（失败恢复与 fail-closed）：启动恢复调用 `ModulePublisher::recover_registered`（指针/行/包摘要核对，不一致则禁用模块行并移除指针），随后才允许 `start`/`update`；恢复失败不使桌面应用崩溃，但 `start`/`update` 以 `host_unavailable` 拒绝直至恢复成功，`stop` 始终受理以便释放加载器资源。恢复不自动启动任何 runtime。supervisor 增加待释放（retired/pending release）注册表：热更新切换后释放失败或 drain 超时的旧 runtime、以及激活失败且释放失败的候选 runtime 不再丢失，保留到释放确认；`stop(module_id)` 在停止当前 runtime 之外重试全部待释放实例（尝试全部、返回首个失败），`start` 在注册新实例前先结算旧实例，失败则 fail-closed 保持旧实例可重试。待释放实例只有到达 `stopped` 才离开列表，因此中途被丢弃不会丢失。`update` 返回 `updated_pending_release` 表示新版本已生效而旧实例释放待重试。
- 决策（renderer 信任边界）：命令只接受 `module_id` 选择器与查询用 `operation_id`；`module_id` 不是授权依据，须通过发布器同一规则（ASCII，且不能是 `.`/`..`，已修复此前对 `.`/`..` 的放行）并仍需通过发布器的启用/指针/摘要核对。用户身份由宿主经 `host::module_session`（窗口 `main`、可信来源、`Settings` 路由、`ModulesRead`/`ModulesManage` 能力）派生为 `HostSession`；Workbench 与 Module 来源不得调用。renderer 不能构造 runtime handle、执行上下文、版本、摘要、路径或 URL。`update` 的来源只能是宿主拥有的 `module-sources/<module_id>` 目录：目录名必须等于合法 module id，必须是真实目录（拒绝 symlink 与非目录），规范化后仍位于根内；包本身仍由发布器再次校验 manifest、entry、symlink 与摘要。不接受远程 URL，首次发布仍不经 renderer 命令。`npm run contracts:check` 对模块命令改为禁止 `user_id/caller/runtime*/handle/context/session/version/integrity/digest/path/source/url/manifest/permission` 参数并要求 `host::module_session` 入口。
- 决策（错误映射）：面向 transport 的错误只暴露 `ModuleOperationErrorKind` 的稳定码和固定文案，不含路径、URL、SQL 或 loader 细节；映射对 `ModuleSupervisorError` 全覆盖（无通配符分支）。复用 `1004001`（module_not_found）、`1004002`（already_loaded）、`1004003`（load_failed）、`1004006`（version_conflict）、`1004007`（unload_failed，释放失败/drain 超时，可重试）、`1004009`（disabled，回滚失败且模块已禁用）、`1004013`（update_failed，已回滚）；新增 `1004015` package_invalid、`1004016` not_running、`1004017` operation_in_progress、`1004018` operation_not_found、`1004019` host_unavailable、`1004020` internal。未启用/未发布的模块 `start` 目前归入 `package_invalid`（发布器返回的是非结构化 manifest 错误），不细分。`1004004` 在代码里是 `PermissionDenied` 的既有线上码，与错误码文档的 `invalid_manifest` 登记冲突，本决策不改动也不复用，冲突待单独决策。
- 影响：无 migration；新增 5 个 Tauri command（`start_module`、`stop_module`、`update_module`、`get_module_operation`、`get_module_runtime_status`），均仅限 Settings 路由；应用启动时用 `ModuleOperationManager::recover` 取代此前恢复失败即 panic 的 `ModuleReleaseService::recover_registered`（该方法随之删除）。已知限制：操作历史仅在内存；没有取消接口；不自动启动 runtime；runtime 与能力 dispatch 尚未接入真实模块调用者；运行时只加载 `LocalArtifactLoader`，不执行 JavaScript，也没有 Federation/WebView、生命周期钩子、状态恢复、UI。`update` 的来源解析与 `update` 执行之间存在窗口，目录内容可被宿主侧进程替换，包校验在 staging 阶段完成，因此不放宽包完整性要求。
- 验证要求：Rust 测试覆盖待释放重试（切换后 stop 失败、drain 超时后在途清零、候选激活失败且释放失败、`start` 先结算旧实例）、后台启动与状态、等待超时与整任务 abort 后继续完成、同模块冲突拒绝与跨模块 FIFO、释放失败可重试、本地来源更新与待释放结果、无来源失败且不泄漏路径、路径/URL 形 module id 不创建 operation、恢复前拒绝与恢复后放行、恢复失败保持不可用、恢复中途丢弃可重试、篡改包恢复后 fail-closed、loader panic 隔离、历史有界、错误映射全覆盖，以及来源解析的遍历/symlink/非目录拒绝和 Settings 路由能力限制。这些证据不等同真实 WebView/Federation 加载、桌面 E2E 或真实 Tauri 窗口调用。

## D036 operation 历史的重启语义

- 状态：已冻结（记录当前限制，不新增持久化；跨重启查询需要新的 migration 与新决策）
- 日期：2026-10-29
- 背景：D034 写明操作历史仅在内存，但没有说明应用重启后调用方能查到什么、未完成的操作如何处理。
- 决策（内存）：operation 记录只在宿主进程内存中保存：所有未结束操作，加最近 64 条已结束操作。应用重启（正常退出或崩溃）后全部丢失，重启前的任何 `operation_id` 查询都返回 `1004018`。`1004018` 只表示“宿主不记得这个操作”，不表示它成功或失败。
- 决策（不恢复）：重启后不恢复、不重放、不自动重试任何未完成操作。所有 runtime 状态为 `not_loaded`，启动恢复不自动启动 runtime。调用方要继续就在恢复成功后重新提交 `start` 或 `update`；两者对已满足状态的请求按既有语义幂等或以明确错误返回。
- 决策（持久部分）：重启后仍然存在的只有已发布的包、版本行、当前指针，以及 `update` 写入 `module_update_events` 的审计行（以同一个 `operation_id` 为键）。`start` 与 `stop` 不写持久记录，因为 runtime 本来就不跨重启。目前没有查询审计行的 command，审计只供排查。
- 决策（中断的 update）：`update` 在 commit 阶段被进程崩溃打断时，由启动恢复负责收敛：发布器核对指针、数据库行与包摘要，一致则保留，不一致则禁用该模块并移除指针（fail-closed），并清理孤儿目录。调用方通过 `get_module_runtime_status` 与重新 `start` 判断结果，不通过旧 `operation_id`。
- 限制（明确不做）：不提供跨重启的 operation 查询或恢复；未完成操作在崩溃后的最终结果只能从发布状态与审计行推断；不得把当前行为描述为跨重启可靠。
- 影响：无 migration、无新 command。若后续要支持跨重启查询，必须新增 operation 表并新增冻结决策，同时定义保留期、崩溃后 `running` 记录的收敛状态和与 `module_update_events` 的关系。
- 验证要求：Rust 测试通过“同一数据库与存储上的第二个管理器”模拟重启，断言旧 `operation_id` 返回 `1004018`、runtime 为 `not_loaded`、恢复不启动 runtime、`module_update_events` 行保留、已发布版本可重新 `start`。该测试不是真实进程重启，真实进程重启未验证。

## D037 Settings 路由由宿主校验与真实 WebView 验证边界

- 状态：已冻结（补全 D034 的宿主入口门禁；不引入 UI、Federation 或模块执行）
- 日期：2026-10-29
- 背景：D034 规定模块 command 仅限 Settings 路由，但 `host::module_session` 固定以 `BuiltinCaller::Settings` 调用 `context`，从不读取窗口 URL。任何在 `main` 窗口、可信来源上的路由（例如 Workbench）都能调用这 5 个 command。真实 WebView smoke 的反向验证（关闭路由检查后 6 项失败）证实了这是可观测的缺口。
- 决策（路由）：`module_session` 在窗口、来源与能力检查之后，额外要求窗口当前 URL 的路径等于 `/settings` 或以 `/settings/` 开头，否则返回 `PermissionDenied`（`1004004`）。5 个 module command（含只读的 `get_module_operation`、`get_module_runtime_status`）都经此入口。其他领域 command 的门禁不变。
- 决策（性质）：路由校验是宿主自有页面的策略，不是沙箱：与宿主共享 JavaScript realm 的脚本可以用 `history.pushState` 改变路径。它防止的是内置页面（如 Workbench）误用，不是恶意脚本。
- 决策（来源）：来源信任判断提取为纯函数 `trusted_origin`：打包来源（`tauri://localhost`、`http://tauri.localhost`）以及仅 debug 构建的 `localhost`/`127.0.0.1:1420`。
- 验证边界：Rust 单元测试验证来源与路由纯函数。真实 WebView smoke（`npm run smoke:tauri`，`webview-smoke` feature）在真实 Tauri 应用与平台 WebView 中验证入口门禁、`operation_id`、查询、页面销毁后操作继续完成、恢复与 fail-closed、update 来源、禁用字段忽略和释放失败重试。实测的拒绝层：非 `main` 窗口在可信来源的 `/settings` 上，Tauri 仍把调用交给 handler，由宿主 `label != main` 检查返回 `1004004`；远程来源窗口在到达宿主前被 Tauri 自身的 ACL 拒绝，宿主的来源检查对它只是纵深防御，仅有单元测试证据。
- smoke 未覆盖：Windows WebView2 与 Linux WebKitGTK；开发服务器来源（`localhost:1420`，该端口在验证机上被占用）；真实进程重启；真实模块代码执行（loader 是脚本化替身，`LocalArtifactLoader` 不执行 JavaScript）；任何 UI。smoke 使用隐藏窗口，是本机的本地验证，不是发布验收。
- 影响：无 migration、无新 command；`1004004` 现在也表示“不在 Settings 路由”。
- 后续修订：本条 smoke 未覆盖的“真实模块代码执行”由 [D041](#d041-v1-可执行模块包的准入来源宿主固定清单摘要不等于可信)～[D046](#d046-模块宿主桥接命令对-d034-命令边界的最小扩展) 的真实加载纵切片处理（独立 smoke 目标 `webview_smoke_real`）；本条的生命周期 smoke 仍使用脚本化 loader，结论不变。

## D041 V1 可执行模块包的准入来源：宿主固定清单，摘要不等于可信

- 状态：已冻结（FR-004 真实加载切片；由助手按 D017 先例选定，用户授权）
- 日期：2026-10-29
- 背景：发布器校验的是包内部一致性：manifest 里 `artifact.sha256` 与包内文件重算值相等。该摘要由包自带，只能证明“包没有被改动、与自己声明的一致”，不能证明发行者可信；任何放进 `module-sources/<id>` 的目录都能自带一个自洽的摘要。把“摘要通过”或“位于宿主目录”当作准入，会让任何能写该目录的同用户进程获得 WebView 内的代码执行。
- 决策（准入来源）：V1 唯一的可执行准入来源是编译进宿主的固定清单，元素为 `(module_id, version, integrity)`，与 D017 对官方内容包固定发布摘要的做法一致。不在清单中的包不得被执行型加载器预检、加载或提交为当前版本。用户本地导入、`module-sources` 目录、manifest 自带摘要、用户授权（`module_permissions`）都不构成准入；权限授权只决定已准入模块能调用什么（D029），不决定它能不能运行。
- 决策（默认空清单）：生产构建的清单默认为空，因此没有任何模块可在生产中执行，直到发布流程提供真实清单。这是有意的 fail-closed，不是缺陷。测试与 smoke 在构造时显式传入 fixture 清单，该清单不进入生产装配。
- 决策（强制位置）：准入是 Application/Supervisor 层的策略，由 `ModuleRuntimeSupervisor` 在预检之前、`start` 之前以及热更新 commit 之前强制执行，不放在加载 adapter 里。加载器通过 `executes_module_code()` 声明自己会不会执行模块代码；执行型加载器没有配置准入策略时，supervisor 对所有 start/update 以 fail-closed 拒绝。热更新中未准入的 staged 包在 commit 前被拒绝，指针和数据库不变。
- 决策（错误码）：新增 `1004021` module_not_admitted（HTTP 403，不可重试，固定文案 `Module is not admitted for execution`）。未准入不归入 `package_invalid`，因为包本身可以完全有效。
- 未覆盖：清单的签名、轮换、撤销，以及发布流程如何产出清单；V1 不提供用户可操作的“信任此模块”入口。

## D042 模块执行位置：宿主 WebView 的同一 JS realm，不是沙箱

- 状态：已冻结（沿用并具体化 D023/D025/D028；不引入 Module Federation 插件、远程加载或隔离执行）
- 日期：2026-10-29
- 背景：D025/D028 已写明同 realm 的 Federation remote 只是受信任代码加载技术。本切片需要真实执行模块代码，必须明确代码实际在哪里运行、能做什么。
- 决策（位置）：模块入口源码由宿主在 Rust 侧读取并校验，通过宿主下发的 load 指令交给主窗口页面，页面用宿主创建的 Blob URL 做原生动态 `import()`，在主窗口主 realm 内执行并渲染。V1 本切片不使用 `@originjs/vite-plugin-federation`，不加载任何 URL。Federation 仍可作为后续对 `ModuleLoader` 端口的另一个 adapter，不改变本条安全结论。
- 决策（边界）：被加载代码与宿主页面共享 `window`、DOM、存储和全部 Tauri IPC（凡窗口 ACL 允许的命令都能直接 `invoke`），也能伪造发给宿主的回执。因此 Settings 路由门禁、桥接命令门禁、Error Boundary、帧或 Shadow DOM 都不是安全边界；唯一的安全边界是 D041 的准入。不为本切片引入 iframe、Worker 或独立 WebView；需要不受信第三方代码时仍按 D025 采用独立进程或 WASM。
- 决策（入口形态）：入口是单文件 ES module。Blob 模块没有基址，因此不支持相对 `import` 和裸说明符，包内其余文件本切片不被加载。模块契约为默认导出工厂函数 `createModule(host)`，返回 `{ Component, onLoad?, onUnload? }`；`host` 是冻结对象，只含 `React`（宿主单例）、`apiVersion`、`moduleId`、`version`。模块不接收 runtime 句柄、用户身份或任何能力 token；能力调用仍须经 D026 的 Host Capability API，本切片不提供。

## D043 预检查、真实加载与激活是三件事；不得静默回退

- 状态：已冻结（FR-004 真实加载切片）
- 日期：2026-10-29
- 决策（预检）：`ModuleLoader::smoke` 是宿主侧无副作用预检：入口为包内非空 UTF-8 普通文件、不超过 16 MiB、包摘要与已校验值一致、准入通过。它不导入、不执行任何模块代码，不证明模块可以运行，也不得被表述为“加载成功”。热更新在 commit 前只做预检。
- 决策（加载）：`start` 才是真实加载：页面导入入口、校验导出契约、把组件真正挂载并提交到 DOM、执行 `onLoad`，随后页面回执。热更新的候选版本在 commit 之后才首次真实加载，因此候选加载失败按 D033 走指针回滚，旧 runtime 保持 ready。
- 决策（激活）：runtime 只有在宿主收到对应当前 ticket 的有效 `loaded` 回执后才转为 `ready`；回执缺失、超时、失败、页面丢失都不是 ready。
- 决策（禁止静默回退）：页面未附着（没有已建立的 attachment）时，执行型加载器的 `start` 返回 `HostNotAttached`，不回退到 `LocalArtifactLoader`，不返回成功。`LocalArtifactLoader` 保留为 `executes_module_code() == false` 的宿主侧校验器，只用于预检和测试；生产装配使用页面加载器。`ModuleRuntimeStatusView` 增加 `executes_module_code`，让“ready”是否来自真实执行可被查询和测试，而不是靠假设。
- 决策（组织）：业务编排（准入、超时、失败清理、回滚、重试语义）留在 Application/Supervisor；页面指令、attachment、ticket、回执状态机作为 adapter 无关的 `PageModuleLoader` 放在 `dgos-modules`，经 `ModulePageTransport` 端口发送；Tauri `Channel`、命令、页面加载事件只在 `src-tauri` adapter。

## D044 页面代次、runtime 绑定、回执幂等、超时与失败清理

- 状态：已冻结（FR-004 真实加载切片；桥接命令对 D034 命令边界的扩展见 [D046](#d046-模块宿主桥接命令对-d034-命令边界的最小扩展)）
- 日期：2026-10-29
- 背景：真实执行把“宿主认为 runtime 活着”建立在一个可被刷新、销毁、迟到回执干扰的页面上。必须说明每个回执绑定到谁、迟到或重复时怎么办、超时如何取消、失败后怎样清理并重试。
- 决策（绑定）：宿主生成三个标识。`attachment_id`：页面每次附着时由宿主签发，绑定窗口 label 与当时的页面代次。`generation`：每个窗口一个单调计数器，由 WebView 的页面加载开始事件递增，覆盖整页导航与刷新，不由 SPA 的 `pushState` 路由切换递增。`ticket`：每条 load/unload 指令一个，单次有效，宿主内部映射到 `runtime_id`。页面回执只携带 `attachment_id`、`ticket` 和结果枚举，不携带 `runtime_id`、`module_id`、版本、路径或用户，宿主不接受回执里的这些声明。
- 决策（回执处置）：回执按宿主状态分为 `applied`、`duplicate`（ticket 已结算）、`stale`（attachment 已被取代或代次已变）、`abandoned`（ticket 已因超时或取消被放弃）、`unknown`（宿主从未签发）。只有 `applied` 改变状态；其余只记录日志并返回给页面，不得产生 ready，也不得复活已失败或已停止的 runtime。迟到的 `loaded` 不会被接纳；其 runtime 在失败清理时已经收到 unload 指令，页面按 `runtime_id` 记墓碑，迟到的加载在下一个 await 点自行中止并回收。
- 决策（页面丢失）：页面加载开始、窗口销毁或同窗口被新 attachment 取代时，旧 attachment 失效：其所有待处理 ticket 以 `PageLost` 失败，其上已 `loaded` 的实例通过 `report_runtime_lost` 汇报给 Application，经 `ModuleRuntimeSupervisor::report_failure` 转为 `failed`。旧 JS realm 已不存在，其 unload 视为已完成。宿主不自动重启；恢复方式是显式 `stop` 后 `start`，得到新的 `runtime_id`、新的 ticket、新的真实加载（D036 的“重启后不自动启动”在页面刷新上同样适用）。
- 决策（超时）：三层。页面层：`onLoad`/`onUnload` 各有页面侧超时（默认 5 秒），超时按失败回执。Supervisor 层：对加载器的 `smoke`（默认 5 秒）、`start`（默认 15 秒）、`stop`（默认 10 秒）各设截止时间，只丢弃加载器自己的 future，不丢弃 supervisor 的 future，随后 supervisor 走既有的 `abort_start` 或释放路径；`ModuleLoader` 的所有方法必须取消安全。超时映射为 `ModuleLoadError::Timeout`，对外沿用 `1004003`（start）与 `1004007`（stop，可重试）。第三层是 drain 超时（D033，30 秒），不变。
- 决策（清理与重试）：启动失败、超时、页面回执失败都进入既有 `abort_start`：runtime 标记 `failed`，加载器 `stop` 向页面发 unload；页面确认（或 attachment 已失效）后才算释放。无法确认时保留为待释放，由后续 `stop` 重试（D034）。`unload` 回执中 `onUnload` 钩子失败仍视为已释放，因为页面总会卸载 React root 并移除容器，钩子失败只写日志。重试的 `start` 总是新的 runtime、新的 ticket。
- 已知限制：同步死循环或持续阻塞主线程的模块代码会冻结整个共享 realm，包括宿主 UI 与超时计时本身，宿主侧只能表现为回执缺失而超时失败，无法抢占；只能由用户关闭或刷新窗口恢复。页面侧超时只对异步钩子有效。在途请求 drain（D033）与页面卸载互不感知，本切片没有模块调用宿主能力的路径。
- 验证要求：`dgos-modules` 单元测试覆盖回执五种处置、迟到回执、页面丢失、取消安全；supervisor 测试覆盖超时不占用生命周期锁和失败清理；真实 WebView smoke 覆盖整页刷新、重复与迟到回执、失败后再次加载。

## D045 JS 缓存、共享依赖与资源释放的实际限制

- 状态：已冻结（记录限制，不承诺超出平台能力的释放）
- 日期：2026-10-29
- 决策（缓存与求值）：每次加载使用新的 Blob URL，因此浏览器的模块映射中每次是一个新记录，入口代码会重新求值；不依赖 HTTP 缓存，也不存在“热更新读到旧缓存”的路径。
- 决策（释放的实际能力）：宿主能做并验证的是：卸载 React root、移除容器节点、`URL.revokeObjectURL` 释放 Blob 字节、丢弃宿主侧引用。宿主不能做的是：JS 引擎没有卸载已求值 ES module 记录的 API，该模块的闭包与它在求值时产生的全局副作用（全局变量、定时器、事件监听、store 订阅、`window` 上的写入）在页面重载前不会被回收，`onUnload` 是模块自行清理的唯一机会。因此反复加载同一模块的内存是单调增长的，直到整页刷新；本切片不设加载次数上限，也不宣称内存已释放。
- 决策（共享依赖）：只有 React 通过 `host.React` 注入，保证模块与宿主使用同一个 React 实例（hook 可用）。react-dom、zustand、router 不共享，模块不得 `import` 它们。manifest 的 `requires.react` 语义版本检查（AC02/AC03 的完整语义）本切片未实现，以 `host.apiVersion` 作为唯一兼容标识。
- 决策（资源上限）：入口源码 ≤16 MiB 且整份经 IPC 复制到页面一次；没有 CPU、内存、网络限制，D042 已说明这些在共享 realm 中无法强制。

## D046 模块宿主桥接命令对 D034 命令边界的最小扩展

- 状态：已冻结（由助手按推荐方案选定；仓库与会话中没有用户对本条的授权或评审记录，此前标注的“用户授权”无依据，已更正。评审结果待定。这是本切片对既有冻结边界的唯一突破；若评审否决，回退方式是删除两条桥接命令与 `PageModuleLoader` 装配，模块恢复为只做宿主侧预检，不能真实执行）

- 方案：A 用 Tauri 事件（`emit`）回传：同样是新增 renderer 到宿主通道，而且没有逐命令的 ACL、窗口和来源门禁，更弱。B 新增两条桥接命令，独立门禁：`attach_module_host`（建立 attachment，绑定一个 `Channel`，返回 `attachment_id`）与 `report_module_host`（提交回执）。C 不加通道，保持加载器为替身：违背本切片“真实执行”的目标。选 B。
- 决策（范围）：两条命令是页面生命周期的 transport 扩展，不是通用模块 IPC：模块代码不能经它们调用宿主能力，也不能借它们携带任何数据出入。两条命令只服务页面生命周期，不执行生命周期操作，不返回模块数据，不接受 `module_id`、用户、版本、摘要、路径、URL、权限、manifest。`attach_module_host` 的全部入参是一个 `Channel`；`report_module_host` 的入参是 `attachment_id`、`ticket`、`receipt`。ticket 由宿主签发、单次有效、由宿主映射到 runtime。5 个生命周期命令仍只在 Settings 路由（D037），本条不放宽它们的门禁。
- 决策（门禁）：桥接命令只校验窗口 label 为 `main` 且来源可信（宿主 `module_host_window`，复用 `trusted_main_window` 谓词），不要求 Settings 路由，也不经过 `context` 的 caller/capability 策略：Settings 或 `ModulesRead` 策略的改动既不能打开也不能关闭页面生命周期通道。该门禁是页面生命周期通道的校验，不是授权。`contracts:check` 对桥接命令使用独立规则：窗口门禁必须存在、入参只能是上述名称、禁止出现身份类参数，并静态禁止 `module_host_window` 引用 `context`、`BuiltinCaller`、`Capability`、`allows` 或 Settings 路由判断。
- 性质：与 D037 相同，这些门禁防止的是内置页面误用，不防同 realm 恶意脚本。回执可以被同 realm 脚本伪造，所以回执只决定“宿主是否把 runtime 标为 ready”，不授予任何权限；安全边界是 D041 的准入。

## D047 可信准入闭环：清单来源、绑定、信任根、轮换、撤销与构建产物验证

- 状态：已冻结（由助手按任务指令“先记录冻结决策”选定；用户未逐条评审，评审结果待定。本条只冻结边界与门禁，签名与发布流程未实现）

- 后果：生产清单继续为空，没有模块可在生产中执行；FR-004 整体仍未完成。

## D048 运行时绑定的模块能力调用：`providers.call` 纵切片

- 状态：已冻结（由助手按任务指令选定；用户未逐条评审，评审结果待定）
- 日期：2026-10-29
- 背景：D033 已有 `ModuleCapabilityDispatchService` 与运行时句柄，D026 要求模块经 Host Capability API 调用能力，但此前只有用脚本化加载器的单元测试，没有把真实准入、真实页面加载器、真实 `ProviderManager` 串起来的证据，也没有具体的能力适配器。
- 决策（范围）：只增加一个能力适配器 `ModuleCapabilityDispatchService::call_provider`，对应权限 `providers.call`。不新增 Tauri 命令，不新增通用模块 IPC，不修改 D042 的 `host` 对象，因此模块 JS 目前没有任何路径触发它；触发方只能是持有 supervisor 签发句柄的宿主 Rust 代码。
- 决策（绑定）：调用必须携带 supervisor 签发的 `ModuleRuntimeHandle`，runtime、`module_id`、版本、integrity 取自句柄中经准入与发布校验的 artifact；用户取自宿主会话；`request_id` 由每次 `begin_request` 生成。调用方不能提供其中任何一项。
- 决策（授权与撤权）：准入发生在 `start`/更新 commit，授权在**每次**调用前重新检查（发布者身份、manifest 声明、持久授权、模块启用）。撤权后的下一次调用在到达 Provider 之前被拒绝；撤权不取消已在途调用（D033）。
- 决策（错误映射）：准入失败、句柄非 `ready`（draining、stopped、failed、已被取代）与授权失败统一为 `PermissionDenied`（`1004004`）；Provider 自身的失败保持其原有错误码，作为 `failed` 结算，不改写成权限错误。
- 决策（重复与并发）：每次调用是独立的外部副作用，宿主不去重、不重试、不重放；相同请求连续或并发发出就是多次 Provider 请求，各有不同的 `request_id`。并发数不设上限，限流与幂等键**未实现**。
- 决策（审计与脱敏）：Provider 使用日志记录 `caller=module` 与每次调用的 `request_id`；每次调用前的授权检查只在拒绝时写一行权限审计（用户、模块、权限、动作、`request_id`），通过时不写；授权与撤权操作本身仍各写自己的审计行（既有行为）。两处都不含提示词、响应正文、API Key。测试对提示词、密钥、响应正文逐项做了不泄露断言。
- 证据等级：Rust 集成测试，使用真实 supervisor、发布器、SQLite、`PageModuleLoader`、`ProviderManager` 与 mockito HTTP fixture；页面由脚本任务应答回执，没有运行真实 WebView 内的模块 JS，也没有真实 Provider。
- 未实现与后续门禁：模块到宿主的调用通道（需要新决策，不能是携带 `module_id` 的 Tauri 命令，也不能放宽 D028）、该适配器在 `src-tauri` 的生产装配、`mcp.call`、`skills.execute` 等其他能力、限流。
- 后续：模块到宿主的调用通道的边界与语义见 [D050](#d050-模块到宿主能力调用通道的边界与语义) 与 [ADR-0001](ADR/0001-模块到宿主能力调用通道.md)；本条的适配器仍未在 `src-tauri` 装配，模块 JS 仍无触发路径。

## D049 发布产物比对门禁：对随包目录重算摘要并逐项比对 pin

- 状态：已冻结（落实 D047 “构建产物验证”一项；由助手按任务指令选定，评审结果待定。门禁已实现，但生产 `BUILTIN_PINS` 仍为空，签名与发布流水线未实现）
- 日期：2026-10-29
- 背景：D047 要求第一个真实 pin 进入 `BUILTIN_PINS` 之前必须有产物比对门禁，此前只有 pin 形状检查，没有对真实目录的重算比对。
- 决策（输入）：门禁只有两个输入：编译进宿主的 pin 列表，和随包交付的模块目录，布局为 `<根>/<module_id>/<version>/`，每个版本目录是一个完整包。不读取 manifest 自报摘要、`modules` 表、用户目录或 `module-sources`、授权、renderer 参数。manifest 只被解析来证明该目录就是 pin 所指的包。
- 决策（比对）：宿主对每个版本目录用发布器同一个 `package_digest` 重算，与 pin 的 integrity 逐项比对（pin 必须是 64 位小写十六进制，门禁内不做大小写归一）。违规类别：非法 pin（空或不安全的 id/版本、integrity 格式不对）、重复 pin（同一 `(module_id, version)`，id 大小写折叠后相同也算，不论摘要是否相同）、缺包、多包（目录里有 pin 未列出的包或版本）、根目录下的非目录项或符号链接、包不可读、manifest 的 id/版本与 pin 不一致或入口不是包内普通文件、重算摘要与 pin 不一致、重算摘要等于 pin 但 manifest 声明了别的摘要（发布器安装时会拒绝这种包）。违规按确定顺序返回；空列表才算通过。
- 决策（空清单）：pin 为空时，缺失的根目录视为空包集合，门禁通过；根目录里出现任何包即为“多包”违规。这样空清单不会掩盖被误放进发布目录的代码。
- 决策（执行位置）：`dgos-modules::verify_release_bundle` / `verify_builtin_release_bundle`；`cargo test` 中的 `the_shipped_bundle_equals_the_builtin_pins` 对仓库根的 `bundled-modules/` 运行；发布流水线用 `cargo run -p dgos-modules --example verify_release_bundle -- <解包后的发布目录>` 对**实际交付的目录**运行（退出码 0 通过、1 有违规、2 用法错误）。仓库根的 `bundled-modules/` 目前不存在，也尚未映射进 Tauri 资源。
- 决策（第一个真实 pin 的前置条件）：pin 进入 `BUILTIN_PINS` 的同一个变更里必须同时：把包放入随包目录并映射进安装包资源；对**解包后的发布产物**（而不是仓库目录）运行该示例并留存输出；在实现状态登记命令、环境、结果。缺任何一项，不得合入真实 pin。
- 已知缺口（登记，不在本条解决）：
  1. 摘要对 `manifest.json` 的排除不区分层级，子目录里的同名文件也不进摘要，因此子目录 `manifest.json` 的改动不会改变摘要。门禁把“随包目录含子目录 `manifest.json`”报为违规来绕开，但发布器的 stage 仍接受这种包。收窄为只排除根 manifest 会改变摘要，需要摘要算法版本，另行决策。
  2. 摘要拼接为 `路径 + NUL + 内容`，没有长度前缀。按代码阅读，内容中含 NUL 字节时，不同的文件划分理论上可拼出相同字节流；本条没有构造出实例，也没有测试证明。入口按 UTF-8 文本读取，实际风险低，但改为长度前缀同样需要摘要算法版本。
  3. 门禁验证的是目录；安装包、签名、公证后的产物与该目录字节一致，需要流水线在解包后重跑，本仓库没有流水线。
  4. 平台代码签名与签名清单（D047 方案 B）未实现，信任根仍是宿主二进制。
- 后果：门禁使“第一个 pin”可被机器检验；生产仍无可执行模块，FR-004 整体未完成。

## D050 模块到宿主能力调用通道的边界与语义

- 状态：已冻结（边界与语义；由助手按任务指令选定，评审结果待定）。传输方案见 [ADR-0001](ADR/0001-模块到宿主能力调用通道.md)，后续修订：该 ADR 已由 [D051](#d051-模块能力调用通道的传输采用-adr-0001-方案-a限值与错误映射) 采用（范围限首方内置模块），本条“ADR 被接受前不得新增命令”的限制随之解除，禁止项与语义不变。
- 日期：2026-10-29
- 背景：D048 只有 Rust 内部入口，模块 JS 无触发路径，且明确“需要新决策，不能是携带 `module_id` 的 Tauri 命令，也不能放宽 D028”。
- 决策（身份绑定）：每次调用绑定下列全部由宿主得出的值，调用方（页面或模块）一概不提供：supervisor 签发的 runtime（`ModuleRuntimeHandle`）、该句柄中经准入与发布校验的 `(module_id, version, integrity)`、页面附着（`attachment_id`）与页面代次（`generation`）、宿主在 `begin_request` 时生成的 `request_id`。页面唯一能提供的定位信息是宿主签发的 runtime 路由键，它只定位 runtime，不含也不代表 module、用户、权限或能力。
- 决策（禁止项）：不新增携带 `module_id` 的普通 Tauri command；不提供通用 renderer/module IPC，也不提供“能力名 + 任意 JSON”的转发入口；不接受远程 URL；不接受用户自报身份；路由键不是能力令牌，不能授予、缩小或持久化任何权限，出示它不改变授权结果。每种能力一条类型化命令，入参只含附着、路由键和该能力的业务字段。
- 决策（授权）：通道准入只证明“调用来自某个 ready runtime 的当前页面实例”。随后每次调用都由 `ModuleCapabilityDispatchService` 重新检查发布者身份、manifest 声明、持久授权与模块启用（D048），不缓存授权结果。
- 决策（撤权）：撤权在**下一次**调用前生效，调用在到达能力之前被拒；不取消已在途调用，在途调用按原授权结算并把结果送回发起它的页面实例。
- 决策（旧 runtime 与页面重载）：路由键只对签发它的 runtime、附着和页面代次有效。runtime 进入 draining/stopped/failed、被热更新取代、页面整页重载（代次加一）、附着被取代、窗口销毁，路由都在下一次调用时失效；重启得到新 `runtime_id`，旧路由不会指向它，必须重新签发。失效路由的调用被拒，不会复活。页面重载时在途调用：宿主侧调用继续到自己的终态，因为外部副作用可能已经发生；结果已无接收方，记录为“已结算但未送达”，不重放、不替新页面重发。
- 决策（并发）：每次调用是独立的外部副作用，各有不同 `request_id`，宿主不去重、不重试、不信任模块提供的幂等键。实现前必须为每个 runtime 与每种能力定义在途上限，超限拒绝并可重试；数值在实现时登记。`draining` 的 runtime 不再准入新调用，在途调用由 D033 的 drain 等待。
- 决策（取消）：取消必须由宿主可验证地绑定到同一路由键与 `request_id`，只是协作式：外部调用派发之前取消，调用不执行；已派发之后取消只能停止等待，结果记为未知，不得声称外部效果被撤销。页面重载或 runtime 失败不自动取消在途调用（D033/D044）。
- 决策（超时）：由宿主按能力设定总期限，模块不能延长，页面侧计时不作为依据。超时后外部调用可能仍会完成，结果记为未知（`Interrupted`），不得映射为“失败可安全重试”，不自动重放。
- 决策（未知外部结果）：future 被丢弃、超时、页面丢失导致无人接收，一律结算为 `Interrupted` / 未知，沿用 `ModuleRequest` 的终态计数；通道不把未知结果伪装为成功或失败。
- 决策（错误与审计）：通道准入失败（路由未知、附着不符、页面已失效、runtime 非 ready）统一映射为 `1004004`，原因只留在宿主侧，不返回给模块；能力自身的失败保持原错误码（D048）。路由键、提示词、响应正文、密钥不得写入日志、审计或错误文本。
- 决策（安全定性）：同 realm 不是安全沙箱（D042）。模块能读取页面里的路由键并冒用同页其他模块（混淆代理），也能绕过通道直接 `invoke` 窗口 ACL 允许的任何命令。通道提供归因与按模块授权，不提供隔离；D041 的固定准入清单仍是唯一的执行准入边界。V1 因此只适用于清单内的首方代码；纳入第三方或用户导入的模块之前，必须采用独立 WebView 或进程（ADR-0001 方案 C）并新增决策。
- 本轮落地：`dgos-modules::ModuleCallRouter`（`issue`/`admit`/`forget`）与 `PageModuleLoader::loaded_binding`，仅 Rust 内部，8 条单元测试；没有 Tauri command，没有 `src-tauri` 装配，`host` 对象不变，`call_provider` 不暴露给模块页面。
- 未实现：实际传输命令、路由键下发到页面、取消命令、能力超时与在途上限、“已结算但未送达”的记录、`src-tauri` 装配、`mcp.call`/`skills.execute` 等其他能力、`contracts:check` 的模块调用命令规则。

## D051 模块能力调用通道的传输：采用 ADR-0001 方案 A，限值与错误映射

- 状态：已冻结（由助手按本轮任务指令“遇到 L2/L3 冲突先记录冻结决策/ADR，再编码”选定；仓库与会话中没有用户对 ADR-0001 的逐条评审记录，评审结果待定。若评审否决，回退方式是删除 `module_call_provider` 命令、`Route` 指令与 `ModuleReadyObserver` 装配，`host` 对象恢复为无调用函数）
- 日期：2026-10-29
- 背景：D050 冻结了通道语义，ADR-0001 的传输方案停在 Proposed，导致模块 JS 无法调用任何宿主能力，FR-004 的 AC05 只能在 Rust 内部验证。本切片需要真实 WebView 中的真实模块 JS 触发 `providers.call`。
- 决策（采用范围）：采用 ADR-0001 方案 A，仅限 D041 固定清单内的首方模块。方案 C（独立 WebView 或进程）仍是纳入任何第三方或用户导入代码的前置条件。ADR-0001 状态改为 Accepted，范围限定为本条所列内容。
- 决策（命令）：新增一条类型化命令 `module_call_provider`，入参只有 `attachment_id`、`route`、`provider_id`、`model_id`、`request`（聊天请求业务字段）。门禁沿用 D046 的 `host::module_host_window`（`main` 窗口与可信来源），不要求 Settings 路由，不经过 caller/capability 策略。不得出现 `module_id`、`runtime_id`、`user_id`、版本、摘要、路径、URL、权限或令牌类入参。`contracts:check` 为模块调用命令使用独立白名单规则，白名单之外的入参使检查失败。
- 决策（路由键下发）：路由键只在 runtime 经 `mark_ready` 后由宿主签发，并通过该附着已有的指令通道以新指令 `route`（携带 `runtimeId` 与 `route`）推送；页面把它存在对应实例上。`ModuleRuntimeSupervisor` 增加可选的 `ModuleReadyObserver`，在 `activate` 的 `mark_ready` 之后调用（`start` 与 `update` 的候选 runtime 都经过这里）。推送是尽力而为：失败不影响 runtime 状态，只是该实例没有路由，调用被拒。热更新时，候选 runtime 的路由先于旧 runtime 退役签发；回滚或退役使旧路由在下一次调用时按 D050 失效。`onLoad` 期间没有路由，因此 `onLoad` 内调用 `host.providers.call` 会被拒；这是有意的，因为此时 runtime 尚不是 `ready`。
- 决策（`host` 对象）：D042 的 `host` 增加一个冻结的 `providers.call(request)`；页面从自己实例上读取路由并调用上述命令，不暴露路由键、附着 ID 或任何 Tauri 对象。被拒、失败与超时以带宿主错误码的 rejected promise 返回。
- 决策（限值，登记 D050 要求的数值）：每个 runtime 的在途模块调用上限为 8（当前只有一种能力，因此等于该能力的上限；加入第二种能力时必须重新登记每能力上限）。上限在 `begin_request` 内原子检查，超限时不计入 `admitted`，返回 `1001005`（`rate_limit_exceeded`，可重试），不新增错误码。`providers.call` 的总期限为 120 秒，由宿主 `tokio::time::timeout` 执行，超时返回 `1001006`，请求按 `Interrupted` 结算（外部结果未知，不重放）。
- 决策（错误映射）：通道准入失败（路由未知、附着不符、页面已失效、runtime 非 `ready`）与授权失败统一为 `1004004`，原因只留在宿主侧日志（不含路由键）；Provider 自身失败保持原码。
- 决策（取消）：本切片不实现取消命令。D050 的取消语义（绑定路由键与 `request_id`、协作式）保持冻结，但没有任何入口，页面重载与 runtime 失败不取消在途调用。这是已知缺口，不是已实现行为。
- 决策（“已结算但未送达”）：不新增存储。在途调用在宿主侧运行到终态，终态进入 `ModuleRequestStats` 计数与 Provider 使用日志（`caller=module`、独立 `request_id`）；页面丢失时结果无人接收，不重放。
- 性质：与 D046 相同，门禁防止内置页面误用，不防同 realm 恶意脚本；路由键可被同页脚本读取并冒用，通道提供归因与按模块授权，不提供隔离。

## D052 生产准入方案：信任根、版本替换、撤销、轮换与签名（ADR-0002）

- 状态：已冻结（由助手按本轮任务指令选定；用户未逐条评审，评审结果待定）。完整方案见 [ADR-0002](ADR/0002-生产模块准入的信任根与签名方案.md)，落实并收窄 D047 的“未实现”项。
- 日期：2026-10-29
- 背景：D047 冻结了边界，但生产清单为空，既没有真实 pin，也没有随安装包交付的模块目录，更没有说明签名、轮换和撤销在 V1 具体怎么做。
- 决策（方案）：V1 采用 D047 的方案 A。`BUILTIN_PINS` 编译进宿主，宿主二进制及其平台代码签名是唯一信任根；不引入模块签名密钥、签名清单、远程清单、用户信任入口或第三方未签名包。
- 决策（随包模块）：宿主自带模块放在仓库根 `bundled-modules/<module_id>/<version>/`，入口是单文件 ES module，源码即产物，没有构建步骤，因此构建天然可复现；摘要由 `package_digest` 重算。该目录经 `tauri.conf.json` 的 `bundle.resources` 映射为安装包资源 `bundled-modules/`。
- 决策（启动时复核）：宿主每次启动，在发布随包模块之前，对资源目录运行 `verify_builtin_release_bundle`；任何违规（缺包、多包、摘要不一致、符号链接等）都使随包模块的供给整体失败并记录错误，不发布、不启动，其他宿主功能不受影响。这是对 D049 的“解包后重跑”的运行期补充，不替代流水线中对安装产物的比对。
- 决策（供给）：通过复核的随包模块，经 `ModuleReleaseService::publish` 发布到宿主模块存储；同一 `(module_id, version, integrity)` 已是当前发布版本时不重复发布。发布只让包可被 `start`，不自动启动、不授予任何权限；权限仍须用户逐项授予。
- 决策（版本替换）：新版本新增 pin、保留旧 pin 以支持 D033 回滚；退役一个版本 = 在下一个构建移除其 pin 与随包目录。pin 不在清单中的版本不能被预检、启动或作为更新 commit 目标（D041/D047）。
- 决策（撤销）：V1 的撤销就是下一个构建移除 pin。已运行的进程持有旧清单，撤销在重启后生效；运行中撤销不在 V1 范围（需要外部清单，属于方案 B）。
- 决策（轮换与签名）：宿主二进制的平台代码签名与公证密钥由发行流水线管理，其轮换不在本仓库实现范围内，也不由任何模块代码参与。本仓库未实现代码签名，因此“包可信”只意味着“与发布时的宿主构建一同发布”。签名清单（方案 B）的前置条件见 ADR-0002，满足前不得实现。
- 决策（已知摘要缺口，不在本条修复）：摘要排除任意层级的 `manifest.json`，因此 manifest 中的 `permissions` 声明不被摘要覆盖。其影响被限定为：声明只决定“可被授予什么”，授予仍需用户操作（D006/D026），篡改 manifest 不能自行获得权限。修复会改变摘要，需摘要版本与新决策。
- 后果：生产清单从此可以非空；FR-004 整体仍未完成。

## D053 局域网远程认证采用随机访问凭据加会话，不使用用户名密码

- 状态：已冻结（由用户选定；D013 的认证方式部分被取代）
- 日期：2026-10-29
- 背景：[D013](#d013-局域网协同需要简单认证和实时状态显示) 写“用户名/密码认证（HTTP Basic Auth 或 JWT，主机创建临时账号或使用主机本地用户）”；[FR-010](../03-功能规格/V1/03-系统功能/10-局域网协同.md) 草案写“随机访问 token → 会话 token，可再选用户输入密码”；[V1 接口契约](../04-技术架构/当前版本/V1-接口契约.md) 与 [OpenAPI](../04-技术架构/当前版本/V1-openapi.yaml) 仍写用户名密码登录与 JWT。[D023](#d023-fr-004-前置收口采用宿主身份与能力边界) 规定 V1 目前只有宿主派生的 `default-user`，FR-008 本地用户管理仍是规划中，不是前置依赖。
- 方案：A 随机访问凭据 + 会话；B 用户名/密码，使用本地用户（FR-010 因此依赖 FR-008，与 D023 相悖）；C 两层（访问凭据加用户密码，两层都要设计轮换与撤销，且依赖 FR-008）。选 A。
- 决策（认证）：服务启动时由主机生成随机访问凭据，通过地址或二维码交给远程设备；远程设备提交凭据，换取有期限、可撤销的会话；之后请求携带会话。无凭据或会话的请求一律拒绝。凭据只在主机显示，不写日志、不进普通 DTO，存放位置遵守 D023 的凭据规则。
- 决策（身份）：远程会话没有独立的用户身份，使用主机的 `default-user` 数据，权限为 D039 的“只能使用、不能改配置”。V1 不创建用户名/密码账号，也不创建 JWT 登录。FR-008 实现后是否让远程设备选择用户，作为新决策另议，不在 V1 范围。
- 决策（取代范围）：D013 的“用户名/密码认证”“HTTP Basic Auth 或 JWT”“主机创建临时账号或使用主机本地用户”由本决策取代。D013 的 WebSocket 实时状态、心跳和“认证信息不加密”不变，其中“局域网内认为安全”的前提仍需在 FR-010 安全默认值中重新评估；“远程用户只读模式”由 D039 继续沿用。
- 仍未决：访问凭据的生成长度与格式、会话期限、轮换与撤销入口、是否限制来源网段、绑定地址、CORS，仍按 FR-010 §2.4“安全默认值”待技术设计冻结。
- 影响：FR-010 的认证流程去掉“选择用户并输入密码”步骤，AC05/AC06 的“token”表述保持为“访问凭据”，AC 编号与原文不变；V1 产品需求、版本总览、总体架构中的“用户名/密码”表述同步改为访问凭据。[V1 接口契约](../04-技术架构/当前版本/V1-接口契约.md) §13～§14 与 [OpenAPI](../04-技术架构/当前版本/V1-openapi.yaml) 的 `/auth/login`、`LoginResponse`、`ERR_AUTH_*` 和 JWT 描述与本决策冲突，属于 FR-010 技术设计时统一重写的接口，本决策不改接口文件，也不能据此认为这些接口已实现。FR-010 尚未实现，无代码、migration 或 command 变化。

## D054 模块调用的传输层重复投递：页面为每次调用生成调用标识，宿主按路由去重

- 状态：已冻结（由助手按任务指令选定，评审结果待定）。修订 D051 的命令入参清单，不放宽 D050 的任何禁止项。
- 日期：2026-10-29
- 背景：真实 WebView smoke（`webview_smoke_call`）在“调用在途时整页重载”场景中观察到同一次页面调用在宿主产生两次独立受理（两个不同 `request_id`、两次 Provider 请求、两条使用日志）。页面侧记录显示只发出一次 `fetch`，随后出现 Tauri 的 `IPC custom protocol failed, Tauri will now use the postMessage interface instead` 警告。依据 Tauri 2.12.5 的 `scripts/ipc-protocol.js`：自定义协议的 `fetch` 失败后，同一条消息经 `postMessage` 重发。原请求已被宿主受理，重发又被受理一次。这是传输层造成的重复，不是模块或宿主的重试，但它违反 D050 的“不重放”：外部副作用被执行了两次。该现象只在 macOS WKWebView 上观察到，其他平台未验证；`fetch` 失败与第二次受理之间的因果由页面侧记录和宿主侧计数共同支持，没有抓到 WebKit 内部的取消事件。此前一次 37/37 的通过是时序侥幸，不是该问题不存在的证据。
- 决策（命令入参）：`module_call_provider` 增加入参 `call_id`，由页面在每次 `host.providers.call` 调用时生成（随机字符串，长度 1～64，仅 ASCII 字母数字与 `-`、`_`），同一次调用的传输层重发携带相同值。`contracts:check` 白名单相应加入 `call_id`。
- 决策（宿主语义）：`ModuleCallRouter::admit_once` 在路由与附着校验通过之后、`begin_request` 之前，按路由记录 `call_id`；已见过的值被拒绝，不受理、不计入 `admitted`，映射为 `1004004`。记录与检查在同一把锁内完成，两次并发投递最多一次通过。每条路由最多保留最近 1024 个 `call_id`，超出时淘汰最旧的；路由失效时随路由一起丢弃。格式不合规的 `call_id` 同样按 `1004004` 拒绝。
- 决策（与 D050 的关系）：D050 禁止“信任模块提供的幂等键”。本决策不信任它：`call_id` 不合并不同调用，宿主不据此返回缓存结果；它只让宿主丢弃**同一路由上完全相同的重复投递**。模块可以自行生成新的 `call_id` 发起新调用，这与它本来就能再次调用没有区别，因此它不授予权限，也不能用来伪造身份。
- 决策（失败语义）：被去重丢弃的重复投递返回 `1004004`，原调用的结果仍送回发起它的页面实例。若原页面已被导航销毁，结果无人接收，沿用 D050 的“已结算但未送达”。重发不会被替新页面重新执行。
- 已知限制：淘汰窗口之外的重放不会被拦截（重发发生在毫秒级，1024 的窗口足够，但这是启发式上限）；同 realm 脚本可以读取路由并重放（D050 已记录）；其他平台 WebView 是否出现同类重发未验证；跨路由、跨重启的去重未做。

## D055 模块管理、版本兼容、热更新状态交接与崩溃处理的 V1 口径

- 状态：已冻结（由助手按任务指令选定，评审结果待定）。落实 FR-004 AC02/AC03/AC04/AC07/AC09/AC10/AC11/AC13/AC15 的实现口径；不新增远程来源、不改 D041/D052 的准入边界，不放宽 D050/D051/D054。
- 日期：2026-10-29
- 背景：规格 §3.2 写“模块把状态保存到 localStorage”、§3.4 写“清除模块缓存”、AC04 写“安装模块时显示权限列表”。V1 没有模块市场、没有远程来源、也没有用户可导入的包（D041/D052），这些字面描述需要落到现有边界内的具体做法。
- 决策（“安装”的含义）：V1 的“安装”就是对随包模块的“启用并确认权限”。随包模块由 D052 的供给流程发布，**默认禁用**；用户在管理页逐项确认其 manifest 声明的权限后才授予并启用。没有“从路径/URL 安装”入口。更新沿用 D034 的宿主本地更新源，卸载只对非随包模块有效；随包模块只能禁用（`1004023`）。供给把随包模块标记为 official 并以禁用状态写入。
- 决策（管理命令）：均属 Settings 路由门禁下的生命周期命令族，只接收 `module_id` 与权限枚举字符串，不接收用户、版本、摘要、路径、URL、令牌。`list_modules`（只读）；`enable_module`、`disable_module`、`uninstall_module`（返回 operation，沿用 D034 的排队与查询）；`grant_module_permission`、`revoke_module_permission`（入参 `module_id` 与 D006 权限字符串，宿主重新读取 manifest 并拒绝未声明的权限，返回更新后的模块摘要）；`list_module_crashes`（只读）。禁用与卸载先停止 runtime 再改状态。
- 决策（版本兼容，AC02）：manifest 增加可选字段 `requires: { "api": <整数>, "react": "<semver 范围>" }`。宿主常量 `HOST_API_VERSION` 与 `HOST_REACT_VERSION`；`api` 必须等于宿主的 `host.apiVersion`，`react` 用 semver 范围匹配宿主 React 版本。不满足时 stage、start、update 返回 `1004022 module_incompatible`，模块不加载，管理页显示警告。字段缺省表示未声明约束（放行）。宿主常量与 `package.json` 的 React 主版本由 `contracts:check` 比对，防止漂移。启动恢复只做完整性校验，不因兼容性禁用已发布模块，不兼容的模块保持已发布且在 start 时被拒。这是兼容性提示，不是安全边界。
- 决策（共享依赖，AC03）：只共享 React，由宿主注入 `host.React`（D045 已冻结）。模块的裸 `import` 在 Blob 入口下无法解析，因此无法自带第二份 React。证据是模块拿到的 `host.React` 与宿主 React 是同一对象，以及裸 `import 'react'` 的入口在 import 阶段失败。react-dom、zustand、router 不共享。
- 决策（状态交接，AC07/AC08）：规格的 localStorage 做法**不采用**：状态只在页面内存中交接，不落盘、不经过 Rust、不进日志，因此页面重载会丢失交接状态。生命周期契约增加可选 `onBeforeUpdate()`（返回可 JSON 序列化的状态）与 `onAfterUpdate(state)`。宿主在新 runtime 加载时由 `PageModuleLoader` 把同一模块已加载的旧实例作为被替换者告知页面。页面顺序：旧实例 `onBeforeUpdate` → 新实例 `onLoad` → 新实例 `onAfterUpdate(state)`。状态经 JSON 往返，上限 256 KiB。保存失败（抛错、超时、不可序列化、超限）只意味着没有状态交接，更新继续，不调用 `onAfterUpdate`；恢复失败（`onAfterUpdate` 抛错或超时）使新实例加载失败，沿用 D033 的更新回滚，旧版本继续运行并保持原状态。
- 决策（崩溃上报，AC09/AC10/AC15）：Error Boundary 只能捕获渲染阶段的错误；事件处理器与异步错误不被捕获，也无法可靠归因到模块（共享 realm），**不声称覆盖**。挂载后被 Boundary 捕获的渲染错误通过类型化命令 `report_module_crash`（入参 `attachment_id`、`route`、`call_id`、`source`、`error_name`、`stack`）上报；宿主按路由解析 runtime，不接受 `module_id`。宿主清洗后再记录：`error_name` 只保留 `[A-Za-z0-9_]{1,64}`；`stack` 只保留形如 `函数名@文件:行:列` 或 `at 函数名 (文件:行:列)` 的帧行，文件部分替换为 `module`，不含错误消息、URL、路径；总长不超过 8 KiB，最多 50 帧。新增表 `module_crash_logs`（id、user_id、module_id、module_version、runtime_id、source、error_name、stack、created_at），新 migration；每个模块最多保留最近 100 条。崩溃使该 runtime 记为 failed，管理页提供“重新加载”（stop 后 start）与“卸载”。同一模块同一版本在 10 分钟内崩溃满 3 次，宿主自动禁用并提示（规格 §5.2“3 次重新加载都崩溃”）。
- 决策（模块视图位置）：模块的 UI 与崩溃横幅位于 `/settings/modules/:moduleId`，侧边栏入口由当前已 ready 的实例驱动，模块停止、禁用或卸载后入口、路由内容与 DOM 一并消失（AC11）。这样“重新加载/卸载”可直接使用 Settings 路由下的生命周期命令，不需要为非 Settings 路由放宽门禁。
- 决策（启动自动加载，AC01/AC14）：页面附着后，宿主对所有“已发布、已启用”的模块并发提交 start；每个模块独立成败，一个失败不影响其他模块。该自动加载只在启用状态下发生，因此随包模块在用户启用前不会运行。
- 已知限制：页面重载丢失交接状态；兼容性只比较声明值；崩溃清洗是启发式，保守地丢弃消息文本；事件处理器与异步错误不被上报；自动加载不覆盖页面重载后的重新启动之外的恢复策略。

## D057 模块包摘要 v2：绑定 manifest 与全部文件，校验与执行绑定同一内存快照

- 状态：已冻结（由助手按任务指令“涉及摘要兼容或数据迁移时先记录方案与决策”选定；评审结果待定）。取代 D049 登记的“摘要算法两处缺口”，不改变 D041/D052 的准入边界（准入仍是宿主内置 pin 列表），不放宽 D050/D051/D054。
- 日期：2026-10-29
- 背景：V1 摘要排除任意层级的 `manifest.json`，因此 `permissions`、`requires`、`entry`、`name` 不受摘要保护：只改 manifest 就能扩大声明权限或改入口而摘要不变；摘要拼接为 `路径 + NUL + 内容`，没有长度前缀；校验读取文件与加载器执行时再次读取文件之间存在窗口（先读入口，再重算整包摘要），校验的字节与执行的字节不保证相同。
- 决策（算法，版本 v2）：`SHA-256( "dgos-module-digest\0v2\0" ‖ frame(manifest_canon) ‖ u64be(文件数) ‖ 对每个文件按相对路径 UTF-8 字节序：frame(路径) ‖ frame(内容) )`，`frame(x) = u64be(len(x)) ‖ x`。`manifest_canon` 按固定顺序拼接：`frame(id) frame(name) frame(version) frame(entry) frame(artifact.version)`、`u64be(权限数) ‖ 按声明顺序 frame(权限)`、`requires`（`0x00` 缺省；`0x01` 后接 `api`（`0x00` 缺省或 `0x01 ‖ u32be`）与 `react`（`0x00` 缺省或 `0x01 ‖ frame(范围)`））。manifest 使用 `deny_unknown_fields`，因此除 `artifact.sha256` 外没有未被覆盖的字段；`artifact.sha256` 自身不能进入自己的摘要，不再是权威值。文件集合为包内全部普通文件，只排除**根目录**的 `manifest.json`（子目录同名文件按普通文件计入）；符号链接与非普通文件拒绝。
- 决策（完整性字符串）：v2 的 `integrity` 为 `v2:` 加 64 位小写十六进制。不带前缀的 64 位十六进制是 v1（遗留）值。宿主只从自己持有的 `integrity`（pin、数据库）判断版本，**从不信任 manifest 自报**，因此不存在由 manifest 触发的降级。v1 值不能通过准入、不能签发 runtime 句柄、不能执行；它只作为迁移的输入。manifest 的 `artifact.sha256` 对新包必须等于 v2 十六进制（构建工具一致性检查），运行时不再据此判断；迁移后的遗留包保留旧值，不改写已安装文件。
- 决策（快照绑定）：发布器对一个包只读取一次：在同一次遍历中读取 manifest 与全部文件、流式计算 v2 摘要，并保留入口字节与已解析的 manifest。`VerifiedModuleArtifact` 携带这份已验证的入口源码（有上限，UTF-8），加载器和页面只使用它，**不再按路径重新读取磁盘**。因此“校验的字节”就是“执行的字节”，校验后改动磁盘不影响本次执行，只会让下一次快照失败。签发句柄时还要求 `modules.manifest` 与快照 manifest 一致（忽略 `artifact.sha256`）。包总大小上限 128 MiB，入口上限沿用 16 MiB，超限拒绝。
- 决策（既有模块迁移）：`migrate_legacy_integrity` 在发布随包模块之前运行（`provision_builtin` 内部先调用，`recover_registered` 在校验前也调用），幂等，在发布器锁与租约内逐模块执行：只有同时满足 ① 磁盘文件的 v1 摘要等于库中旧 `integrity`，② 磁盘 manifest 与库中保存的 manifest 语义一致，才在**单个事务**中把该模块 `modules.integrity` 与其当前版本的 `module_versions.integrity` 改写为 v2 值，并写入 `integrity_migrated` 事件。文件从不改写，所以不存在“文件已改、库未改”的半状态；事务未提交即仍是 v1，下次启动重试。任一条件不满足：该模块禁用（fail-closed）、保留旧值、记录 `integrity_migration` 失败事件（已禁用的模块不重复记录），不执行。只迁移**当前版本**：非当前版本的 `module_versions` 行库中没有 manifest 记录，无法做第二项核对，因此保持 v1，不能被回滚或重新激活，再发布同一版本号会因“版本已存在且摘要不同”失败，需要新版本号。
- 决策（发布提交）：`commit` 在目录改名后再快照一次，摘要不符则撤销改名并失败。版本目录已存在但没有 `module_versions` 行（中断的提交遗留）时：摘要一致则接管续做，不一致则按孤儿删除后重做；有行且摘要不同仍为错误。
- 后果：所有 pin、manifest 与既有数据库摘要在升级时一次性变化；随包模块 `provider-console@1.0.0` 的 pin 重新生成，已安装副本在迁移后得到同一个 v2 值。v1 与 v2 在同一版本内不并存执行。不引入签名；信任根仍是宿主二进制（ADR-0002 方案 A）。
- 已知限制：能写应用数据库的攻击者可以同时改库与文件，这超出本地文件篡改的威胁模型；摘要不覆盖空目录与文件权限位；Windows/Linux 的文件系统语义未验证。

## D059 崩溃处理的可靠性：先记宿主事实，再写日志；自动禁用必须被受理或持续重试

- 日期：2026-10-29
- 背景：`report` 先写日志、日志失败即返回，宿主从未把该 runtime 标记为 failed，管理页仍显示 ready；自动禁用的 `disable` 结果被丢弃，操作被拒（例如该模块有进行中的操作）时没有后续崩溃再触发它，模块保持启用。

- 已知限制：页面端重试全部失败且宿主没有其他信号时，宿主仍不知道该实例已崩溃；启动评估只看库内日志；进程内计数在重启后清零。

## D060 React 兼容性使用锁定的构建依赖精确版本

- 状态：已冻结（由助手按任务指令选定；评审结果待定）。修订 D055 中“宿主常量与 `package.json` 的 React 主版本比对”。
- 日期：2026-10-29
- 背景：`HOST_REACT_VERSION` 是手写的 `19.1.0`，只比对主版本；锁文件与安装的 React 已经是 `19.3.1`，`^19.1.0` 之类的范围会被误判，`>=19.2` 会被错误拒绝，`<19.2` 会被错误放行。
- 决策：`dgos-modules` 的构建脚本从 `package-lock.json` 读取 `node_modules/react` 的精确版本，编译进 `HOST_REACT_VERSION`；锁文件缺失或版本不是精确 semver 时构建失败。`contracts:check` 与前端构建前检查要求 `node_modules/react`、`node_modules/react-dom` 的安装版本等于锁文件版本；前端测试要求运行时 `React.version` 等于锁文件版本。因此判断所用版本、真实打包的版本与锁文件三者一致，minor/patch 漂移会使检查失败。
- 后果：升级 React 必须同时更新锁文件，Rust 在下次编译时自动跟随；不再有手写版本常量。

- 决策（错误归一）：新增 9 个错误码 1001017～1001025，拟用语义见 FR-001 §8.1（`provider_request_rejected`、`context_length_exceeded`、`provider_permission_denied`、`request_not_supported`、`structured_output_invalid`、`unsupported_provider_type`、`insecure_endpoint`、`provider_quota_exhausted`、`provider_response_invalid`），1001014 `upstream_server_error` 在实现后改为发出（登记状态仍为预留）。上游错误只提取类别字段，不把错误正文写入错误消息或日志。创建 Provider 时上游 401 返回 1001002。
- 决策（重试、超时与降级）：只重试连接失败、408、429（非额度类）、5xx 与 529，遵守 `retry-after`；400、401、402、403、404、413、422 与响应解析失败不重试，保持原码，只有配置了重试且至少重试过一次才返回 1001008。超时分三层：连接 10 秒、模型列表 30 秒、非流式总期限 120 秒、流式空闲 120 秒且不设流式总期限（推断）。响应体上限 8 MiB，单个 SSE 事件上限 1 MiB。上游以 400 点名 `stream_options`、`parallel_tool_calls`、`tool_choice` 或 `max_tokens`/`max_completion_tokens` 之一时，去掉或互换该参数重试一次，不持久化，不记录上游错误正文。
- 决策（端点与重定向）：scheme 只允许 http 与 https；回环地址和私网字面 IP 允许明文 HTTP，其他主机需用户设置 `allow_insecure_http`；保存和每次调用都检查。HTTP 客户端不跟随重定向，3xx 一律 `provider_response_invalid`，凭据头只发往 base_url 的主机。
- 决策（推理与结构化输出）：推理档位原样交给上游，宿主不维护按模型的档位目录；画像没有该档位映射时本地拒绝。官方 Anthropic 画像用 `adaptive` 加 `output_config.effort`；通用 `anthropic` 画像用 `thinking: enabled` 加 `budget_tokens`，`low`/`medium`/`high` 映射为 2048/8192/16384（推断）。推理内容在工具循环中按上游返回的字段名原样回传（`reasoning_content`、`reasoning`、`reasoning_details`），Anthropic 的思考块原样回传。结构化输出：`openai_compatible` 默认 `json_schema`，官方 Anthropic 画像用 `output_config.format`，通用 `anthropic` 画像用 system 指令；返回内容一律由宿主按 schema 校验，不合规返回 `structured_output_invalid`，不自动重试。不用强制工具调用模拟结构化输出。
- 决策（流式）：流式事件按 SSE 规范解码（字节缓冲、按空行切分、多行 `data:` 拼接），流结束时只写一次使用记录；桌面端新增流式命令与取消命令，事件只推送到调用方传入的 Tauri Channel，取消只对本窗口发起的流有效。

- 备选方案：
  - 并发：
    - A. 每用户同一时刻只允许一个活动生成。内存注册表为主，数据库部分唯一索引（`status = 'generating'`）兜底。简单、与工具任务一致；代价是不能同时在两个会话里生成。
    - B. 每会话一个。用户体验更好；代价是并发流占用多个连接，单连接池下终态写入排队。
    - C. 不限制。不可取，资源和计费不可控。

    - B. 每隔数秒或每若干 KiB 做检查点写入。覆盖强杀；代价：十分钟生成可能产生数百次提交，单连接池下读写互相排队，要处理检查点与删除会话的竞态。

  - 离开页面：
    - A. 离开或重载窗口即取消，已收到部分保存为中断。与现有页面卸载取消一致，行为可预期，没有后台计费。

## D076 重新生成与历史搜索的语义

- 状态：已冻结（2026-10-30 用户对 Q1～Q3 选择了推荐方案，由助手记录；300 毫秒阈值为自选值）
- 日期：2026-10-30
- 背景：
  - FR-006 AC13 写"删除旧响应，重新调用"。若先删除再调用，调用失败、取消或重启会让用户同时失去原回复和新回复。
  - AC15 写按内容搜索会话；FR-006 §4.2 用 `LIKE`。仓库没有 FTS 表；FTS5 通过依赖链被编译进来，但依据源码判断，未运行 `PRAGMA compile_options` 验证。FTS5 默认分词器对中文无词边界，trigram 分词器无法匹配少于三个字符的查询，而一到两个字的中文词是常见查询。
  - SQLite 的 `LIKE` 默认只对 ASCII 不区分大小写。
  - 单连接池下，长时间扫描会阻塞生成的终态写入（依据源码判断）。
- 备选方案：
  - 重新生成：
    - A. 新回复成功后替换：新建带 `replaces_id` 的助手消息，成功时在一个事务内删除旧回复并清除 `replaces_id`；取消、失败、重启则丢弃新半成品，保留旧回复。
    - B. 先删后调用，即 AC13 字面。实现最简；失败即丢失。
    - C. 保留全部版本并分页切换。丰富；历史膨胀，搜索要去重，"已删除"的内容仍在库中，与 D072 的删除口径冲突。
  - 搜索：
    - A. `LIKE` 子串匹配加转义，限定当前用户，标题与消息正文，分页，片段由 Rust 计算。中文可用，简单；线性扫描，规模大时变慢。
    - B. FTS5 trigram。大规模快；短查询匹配不到，仍需 `LIKE` 回退，且删除要同步索引，影子表残留增加物理删除不确定性。
    - C. 先 A，设置阈值再评估 B。

## D081 Provider 使用记录区分“用量未知”与“用量为零”

- 状态：已冻结（2026-10-31 用户同意助手推荐的方案）。关闭 D074 的“通知 FR-001”开放项中关于用量未知的部分；取消与网络中断在 Provider 层仍不区分。
- 日期：2026-10-31
- 背景：`provider_usage_logs` 的 `request_tokens`、`response_tokens`、`total_tokens` 为 `NOT NULL DEFAULT 0`。中途取消、网络中断、上游不回报用量时一律写 0，与“没有花费”无法区分。2026-10-31 真实运行中，一个 Anthropic 兼容端点不执行 `max_tokens`，输出约 3 万 tokens（推断）被宿主 64 KiB 上限截停，使用记录仍是 0。`list_usage_logs` 命令已注册，但前端没有调用方。
- 备选方案：
  - A. 追加可空列 `usage_reported`（1 已回报，0 未回报，NULL 为旧行），token 列不变。
  - B. 把 token 列改为可空。代价：SQLite 改 `NOT NULL` 需要重建表，风险更大；所有读取方要处理 NULL。
  - C. 再加一个错误码区分取消与网络中断。代价：新增错误码并改所有写入路径；聊天任务行已能区分（`task_cancelled`），使用记录目前没有读取方。

  - `UsageLog` DTO 增加 `usage_reported: Option<bool>`，加法变更，旧调用方不受影响。
  - 取消与网络中断在使用记录里仍都是 `1001007`；以后做用量界面时再按需要决定。
- 影响：
  - 数据：migration `m20261031_000017_usage_reported`（forward-only，`ALTER TABLE ADD COLUMN`，带 `CHECK (usage_reported IN (0,1))`）；旧行为 NULL，不回填。
  - 代码：`dgos-db` 的实体与 `UsageLogRepository::create_with_provenance`（新增参数）；`dgos-providers` 的同步、工具与流式写入；`dgos-types` 的 `UsageLog`。

  - 文档：FR-001 §4.3、数据模型 provider_usage_logs、接口契约 `list_usage_logs`。

## D082 画布运行的生命周期：运行归宿主持有，离开页面不取消

- 状态：草案（2026-10-31 由助手起草，待用户确认）。只约束 V2 画布的运行服务，不改 D074 对聊天的任何规定。
- 日期：2026-10-31
- 背景：
  - D074 规定聊天离页即取消：页面重载或窗口销毁时，`ChatManager::cancel_window` 和 `ProviderStreams::cancel_owner` 取消该窗口的全部生成（`src-tauri/src/module_host.rs` 的页面生命周期钩子，已读代码）。运行按窗口标签归属，每用户同时一个活动生成。
  - V2 画布的一次运行可能包含几十个节点和数分钟的视频生成。照搬 D074，用户切换页面就会取消整次运行，而已经发出的上游调用可能已经计费。
  - 模块走不通聊天这条路：聊天命令对模块上下文一律拒绝（D073）；`ProviderCallService::execute_stream` 对模块身份返回 `PermissionDenied`；模块唯一的能力 `providers.call` 是一次性非流式调用，总期限 120 秒，没有取消入口（D051）。
  - 所有模块都运行在 `main` 窗口里，按窗口标签归属分不清是哪个模块发起的运行。
- 备选方案：
  - A. 运行归宿主持有，与页面解耦：页面只订阅事件，离开后可以重新接上；运行只在显式取消、模块被卸载或禁用、应用退出时结束。优点是长工作流能跑完，也是 V7 Agent 执行和 V4 多端协同的前提；代价是要新增运行结果存储、事件序号、重新接入，并让用户看得到后台运行。
  - B. 沿用 D074，离页即取消。优点是实现简单，与聊天一致；代价是长工作流不可用，计费更加不透明。
  - C. 默认离页即取消，用户可以把某次运行显式标为"后台运行"。优点是灵活；代价是两套生命周期，测试面和语义都翻倍。
- 决定（推荐 A，待确认）：
  - 归属：运行属于"用户 + 发起模块"。发起模块由宿主从模块路由（runtime、route、attachment，D050）推出，不用窗口标签，也不接受页面自报。
  - 页面重载、附着被取代：只断开事件通道，不取消运行。
  - 结束：显式取消；发起模块被卸载、禁用，或热更新排空（D033）；应用退出。退出时未完成的节点按 D074 的重启恢复规则标为中断，不自动重发。
  - 撤权：沿用 D050，撤权在下一次调用前生效，已在途的调用按原授权结算；运行里尚未派发的节点不再派发，整次运行以失败结束。错误码在技术设计中登记（D038）。
  - 事件：事件带递增序号。重新接入时带上最后收到的序号，宿主补发之后的事件，再接续实时事件。每次运行只有一个终止事件，携带落库后的运行快照，页面以快照为准。
  - 持久化：每个节点到达终态时各自落库。进程被强杀最多丢失在途节点的结果，已完成的节点不受影响。
  - 可见性：宿主提供"正在运行"列表，用户不打开画布页也能看到并停止自己的运行。
  - 时限与配额：按能力类别定时限。长任务（如视频生成）采用"提交、推送进度、取结果"，不占用一次同步调用。并发按"用户 × 模块 × 能力"计数，超出时排队。数值在技术设计中登记，不沿用聊天的每用户一个、10 分钟。
- 理由：
  - 画布的价值在于能跑完整个工作流。离页即取消使长工作流不可用，用户还会在不知情时为被取消的调用付费。
  - V7 Agent 自动执行和 V4 多端协同中，发起人都可能不在页面上。只有宿主持有运行，这两项才成立。
  - C 带来的灵活性不足以抵消两套语义和翻倍的测试面。
- 影响：
  - 功能：V2 画布；V1-FR-004 需要新增模块能力命令和取消入口（D050 的取消语义首次有入口）；V1-FR-009 的权限按模块计。
  - 接口：新增运行类能力的类型化命令与事件通道，先在 `contracts:check` 登记入参规则（ADR-0001）。
  - 数据：新增运行表与节点结果表（forward-only migration），表结构在技术设计中定。
  - 不变：D074 对聊天的规定。
- 落实：
  - [ ] 用户确认
  - [ ] V2 门禁前完成运行服务技术设计：命令、事件结构、表结构、时限与配额数值、错误码

## D083 画布运行的 MCP 授权：运行开始时一次性授权一个范围

- 状态：草案（2026-10-31 由助手起草，待用户确认）。只约束画布运行，不改 D022、D075 对聊天的逐次确认。
- 日期：2026-10-31
- 背景：
  - 聊天中每次 MCP 调用都要用户逐次确认（D022）：每任务至多 8 个工具，提案 120 秒过期，整轮 15 分钟，参数与结果不入库。D075 在聊天里沿用这一规则。
  - 画布的一次运行可能含多个 MCP 节点，参数由上游节点的输出决定，开始运行时还看不到。逐次确认会在运行中反复弹窗，V7 的 Agent 自动执行也无法实现。
  - AGENTS.md 要求 MCP 等外部能力只能通过明确的宿主策略和授权路径调用，不能由普通文本或模型自行授予权限。
- 备选方案：
  - A. 运行范围授权：开始运行前，宿主列出本次运行会用到的服务器、工具、调用次数上限和有效期，用户确认一次；之后每个节点调用前，宿主按这个范围复核，不再逐次确认参数。
  - B. 沿用逐次确认。最安全；代价是无法自动执行，长工作流需要用户一直守着。
  - C. 文档级常驻授权：某个画布一旦授权，以后每次运行都不再询问。体验最好；代价是风险最高，协作者新加的节点会以授权人的身份执行。
- 决定（推荐 A，待确认）：
  - 范围从运行开始时的图快照静态推出：服务器、工具、`schema_hash`、调用次数上限、有效期。授权绑定这份快照的摘要。
  - 运行中图被修改（包括协作者修改）后新出现的工具不在范围内，调用被拒绝，需要重新授权。
  - 授权的是工具和次数，不是参数。确认界面必须明确告诉用户：参数由上游节点生成，确认时看不到。
  - 每次调用前，宿主复核服务器与工具仍启用、`schema_hash` 一致、次数和有效期未超。复核不通过，该节点失败，不弹窗重新授权。
  - Agent 发起的运行同样需要用户确认范围。模型输出不能授予或扩大范围。
  - 参数与结果是否入库沿用 D022：不入库，不进普通 DTO 和日志。
  - 局域网或协同中发起的运行，由文档所有者（主机）的用户确认范围。这与 2026-10-31 选定的"局域网可编辑，运行需主机授权"方向一致；该方向尚未成为冻结决策。
- 理由：
  - 开始前能静态确定的内容（服务器、工具、次数、有效期）都经过用户显式确认，满足 AGENTS.md 的授权要求，同时运行中不再打断用户。
  - 绑定图快照的摘要，可以防止运行中被修改的图（尤其是协同时）借用已有授权。
- 影响：
  - 功能：V2 画布；V1-FR-003（新增"运行范围授权"的宿主入口）；V1-FR-006 不变。
  - 数据：授权记录是否持久化，在运行服务技术设计中定。
- 落实：
  - [ ] 用户确认
  - [ ] 运行服务技术设计中定义范围对象、复核点与失效规则

## D084 官方模块可以有构建步骤：源码与产物分开、可复现构建，样式检查扫描源码

- 状态：草案（2026-10-31 由助手起草，待用户确认）。确认后修改 D052"随包模块源码即产物、没有构建步骤"一句，D052 的信任根、pin 与启动复核不变。
- 日期：2026-10-31
- 背景：
  - D052 规定随包模块的入口是单文件 ES module，源码即产物，没有构建步骤，构建天然可复现。目前唯一的随包模块 `provider-console` 是手写的 `entry.js`。
  - V2 画布模块要把渲染引擎、Yjs 和节点定义打成一个单文件入口。D042 不支持相对 import 和裸说明符，D045 只共享 React，所以不可能手写，必须有构建步骤。
  - D068 的 R1 扫描 `bundled-modules/**/entry.js`。扫描构建产物会把打包进来的第三方库代码一起扫进去，报出的位置也不是源码位置。
  - 准入依赖编译进宿主的 `BUILTIN_PINS`，每个新版本都要新 pin 并重新构建宿主。这与蓝图故事 3"模块独立迭代、热更新"不符；在 ADR-0002 的签名清单（方案 B）落地前无法改变。
- 备选方案：
  - A. 官方模块的源码放在仓库内的独立目录，用锁定版本的工具链构建成单文件入口，要求可复现：同一份源码和锁文件得到相同的产物摘要，CI 重新构建并与随包目录逐字节比对。样式检查扫描源码，不扫描产物。
  - B. 源码和产物都提交，但不要求可复现。最简单；代价是无法证明随包产物确实来自仓库源码，D049、D061 的产物比对失去意义。
  - C. 坚持没有构建步骤。代价是画布引擎必须手写成单文件，且不能依赖 Yjs 等库，不可行。
- 决定（推荐 A，待确认）：
  - 产物仍放在 `bundled-modules/<module_id>/<version>/`，摘要、pin、启动复核按 D052、D057、D061 不变。
  - 可复现是门禁：CI 从源码重新构建并与随包目录比对，不一致则构建失败。
  - `design:check` 的扫描对象从 `bundled-modules/**/entry.js` 改为模块源码目录（ESLint 与 Stylelint 同时扫描），产物不再扫描。这与 D068"扫描的是仓库源码"的原则一致。
  - 这条构建流程是 V8 `dgos-cli` 的雏形，先只服务官方模块。
  - 在 ADR-0002 的签名清单落地之前，官方模块仍随宿主发布，不能独立发布。蓝图故事 3 的"独立迭代"在此之前不成立，V2 门禁时要如实写明。
- 理由：
  - 可复现构建保留了 D049、D061 的保证：随包产物可以证明来自源码。
  - 扫描源码，报出的文件和行号才准确，也不受第三方库代码影响。

  - 不在本条：模块样式表与几何类 R1 豁免、manifest 扩展（摘要格式升版）另行决策。
