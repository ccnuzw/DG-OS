# V1 冻结决策

本表记录影响范围、协议和架构的一致性决策；新证据到达后追加新编号，不改写历史结论。

**当前解释规则**：D016 取代 D003/D005 中“Skills 必须是 HTTP/CLI 或 LangChain Tools”的定义，并限定 D006 的模块授权不能被技能内容继承为任意执行权限。旧条目原文保留用于追溯；MCP、轻量运行时及应用市场边界不变。

## D001 使用 Rust + Tauri 而非 Node.js + Electron

- 状态：已冻结
- 日期：2024-01-XX
- 背景：老项目 infinite-canvas-ccnuzw 使用 Python + FastAPI，单文件 19,038 行，无法维护。需要选择能强制模块化、性能好的技术栈。
- 决策：采用 Rust + Tauri 2 作为核心技术栈
  - 后端：Rust + Axum + SeaORM
  - 桌面：Tauri 2
  - 前端：React + TypeScript + Vite
- 理由：
  - Rust 编译期强制模块化，不可能写单文件巨石
  - Tauri 轻量（<10MB），Electron 过重（>100MB）
  - Rust 所有权系统防止内存泄漏
  - 零成本抽象，性能优于 Node.js
  - 类型安全，编译期捕获大部分错误
- 后果：
  - 学习曲线较陡，但有强制模块化保证
  - Rust 生态成熟度低于 Node.js，但核心需求已满足
  - 团队需要学习 Rust，但可避免重蹈老项目覆辙
- 替代方案：
  - Node.js + Electron：生态好但无法强制模块化，容易重复老项目错误
  - Go：性能好但缺少桌面框架支持

## D002 使用 SQLite 而非 PostgreSQL

- 状态：已冻结
- 日期：2024-01-XX
- 背景：项目定位为本地优先工具，需要零配置、易备份的数据库。
- 决策：采用 SQLite 作为唯一数据库
- 理由：
  - 本地优先：单文件数据库，无需独立进程
  - 零配置：无需安装和配置数据库服务
  - 易备份：复制单个文件即可
  - 性能足够：读取速度接近 PostgreSQL，写入对单用户足够
  - 体积小：整个库只有几百 KB
- 后果：
  - 不支持多进程并发写入，但单机模式不需要
  - 无内置用户权限系统，但通过应用层控制
  - 局域网协同时只有主机有写权限
- 替代方案：
  - PostgreSQL：功能强大但需要独立进程，违背本地优先原则
  - 嵌入式 PostgreSQL（libpq）：仍然过重

## D003 不使用 QuickJS/Node.js 作为 Skills/MCP 运行时

- 状态：已冻结
- 日期：2024-01-XX
- 背景：初期误以为需要实现 Skills/MCP 执行引擎，考虑嵌入 QuickJS 或 Node.js。
- 决策：不嵌入任何 JavaScript 运行时，Skills/MCP 自己运行
- 理由：
  - Skills 和 MCP 是现有标准，有自己的运行环境
  - DGOS 只需要管理（安装/配置）和调用（HTTP/CLI），不需要执行
  - 类比：Chrome 管理扩展但不实现扩展引擎
  - 避免增加 50MB+ 的运行时体积
  - 简化架构，减少维护负担
- 后果：
  - Skills 必须提供 HTTP API 或 CLI 接口
  - 无法在沙箱中执行不可信 JavaScript 代码
  - 需要依赖外部 Skills/MCP 服务的稳定性
- 替代方案：
  - 嵌入 QuickJS：轻量但需要实现完整的 Skills 执行引擎，过度设计
  - 嵌入 Node.js：生态好但体积大，违背轻量化原则

## D004 使用 Module Federation 实现模块热更新

- 状态：已冻结
- 日期：2024-01-XX
- 背景：应用模块需要独立开发、独立版本管理、热更新（无需重启）。
- 决策：使用 Webpack Module Federation（或 Vite 版本）实现模块系统
- 理由：
  - 成熟方案：已在生产环境大规模使用
  - 真正的运行时加载：不是预打包，而是动态 import
  - 共享依赖：React、Zustand 等只加载一次
  - 独立构建：每个模块可以独立开发和发布
  - 版本管理：支持多版本共存
- 后果：
  - 需要配置 Webpack/Vite 插件
  - 模块必须暴露标准入口点
  - 共享依赖版本需要协调
  - 打包体积略大于单体应用
- 替代方案：
  - iframe 隔离：隔离性好但通信复杂，性能差
  - Web Components：标准但生态不成熟
  - 动态 import：简单但无法共享依赖

## D005 Skills 和 MCP 使用现有标准协议

- 状态：已冻结
- 日期：2024-01-XX
- 背景：需要让 DGOS 能够使用 AI 工具和能力扩展。
- 决策：直接使用现有 Skills（LangChain Tools）和 MCP（Model Context Protocol）标准，不自定义协议
- 理由：
  - Skills 已有成熟生态（LangChain、LlamaIndex 等）
  - MCP 是 Anthropic 主导的标准协议
  - 不重复造轮子，复用现有生态
  - 降低学习成本，开发者熟悉标准
  - 自动兼容未来协议演进
- 后果：
  - Skills 调用方式：可选增强，非必选
  - MCP 工具调用：通过标准协议桥接
  - 需要维护 Skills/MCP 远程仓库连接
  - 受标准协议限制，无法自定义特殊能力
- 边界说明：
  - Skills：AI 增强工具（文本生成、图像处理等）
  - MCP：系统集成工具（文件操作、搜索、外部 API 等）
  - 在 LLM 节点中，Skills 是可选的，用户可以直接调用 Provider

## D006 权限模型采用粗粒度模块级权限

- 状态：已冻结
- 日期：2024-01-XX
- 背景：模块需要申请权限才能调用系统能力（Provider、Skills、MCP、存储等）。
- 决策：V1 采用粗粒度权限，后续版本细化
  - 权限类型：`providers.call`、`skills.execute`、`mcp.call`、`storage.read`、`storage.write`、`network.local`
  - 授予对象：整个模块，不区分模块内的具体功能
  - 授权时机：模块安装时用户一次性授权
- 理由：
  - V1 简化实现，快速交付
  - 模块通常需要完整的能力集合，细粒度意义不大
  - 官方模块自动授予所有权限
  - 避免频繁的权限请求打断用户
- 后果：
  - 模块获得权限后可以调用所有 Provider（不能限制特定 Provider）
  - 模块更新增加权限时需要用户重新授权
  - 无法实现细粒度审计（例如模块 A 调用了哪个具体 Provider）
- 后续细化：
  - V2.0 可以细化为 `providers.call:openai`、`storage.read:projects/own` 等

## D007 局域网 HTTP 服务始终开启

- 状态：已冻结
- 日期：2024-01-XX
- 背景：用户希望一台电脑启动 DGOS 后，局域网内其他设备可以访问使用。
- 决策：桌面应用启动时自动启动 HTTP 服务，监听 `0.0.0.0:3000`（可配置端口）
- 理由：
  - 简化用户配置，无需手动开启"共享模式"
  - 端口可配置，避免冲突
  - 只监听局域网，不暴露到公网
  - 提供简单认证（用户名/密码）
- 后果：
  - 占用一个端口
  - 需要防火墙配置（macOS 会弹窗询问）
  - 需要简单认证机制防止未授权访问
  - 远程设备只读模式，不能修改 Provider 配置
- 安全措施：
  - 默认生成随机密码
  - 强制认证，无认证不能访问
  - 远程设备权限受限（只能使用，不能配置）
  - 可在设置中关闭服务

## D008 所有模块强制使用统一设计系统

- 状态：已冻结
- 日期：2024-01-XX
- 背景：用户明确要求"系统的整体样式管理和组件管理需要统一化，不能每个应用一个主题"。
- 决策：建立统一 Design System，所有模块必须复用，禁止自定义样式
  - 主题系统：亮色/暗色主题，全局切换
  - 色彩规范：主色、辅助色、语义色（固定）
  - 字体规范：字体家族、字号、字重（固定）
  - 间距规范：4px 基准，固定间距档位
  - UI 组件库：基于 Shadcn/ui，封装为 `@dgos/ui`
- 理由：
  - 保持视觉一致性
  - 降低开发成本（不需要重复实现组件）
  - 主题切换全局生效
  - 避免混乱的用户体验
- 后果：
  - 模块开发者必须使用 `@dgos/ui` 组件库
  - 禁止使用 inline styles 或自定义 CSS 覆盖主题变量
  - 模块审核时检查样式合规性
  - 需要维护完整的组件文档和示例
- 强制机制：
  - CI 检查：扫描模块代码，禁止出现 `style={{}}` 或自定义 CSS 变量
  - 审核阶段：人工检查视觉一致性
  - 模块示例：提供模板项目，强制使用正确方式

## D009 无限画布分多版本实现，不阻塞 V1

- 状态：已冻结
- 日期：2024-01-XX
- 背景：无限画布是核心价值功能，但复杂度高。用户要求"重点是搭建底层能力和底层框架"。
- 决策：无限画布功能拆分到 V1.2-V1.5 分步实现，V1 聚焦底层框架
  - V1.0：底层能力（Provider/Skills/MCP/模块系统）+ 基础应用（AI 工作台、系统设置）
  - V1.2：画布核心（视口、缩放、拖拽）+ 5 种基础节点
  - V1.3：10+ 种节点类型，节点连线系统
  - V1.4：实时执行，循环节点
  - V1.5：工作流导入导出，布局算法优化
- 理由：
  - 底层框架搭好，后续快速迭代
  - 避免 V1 范围过大，延期风险高
  - 可以先验证框架可扩展性
  - 画布功能独立性强，不阻塞其他模块
- 后果：
  - V1 无法展示核心价值（画布），但可以展示框架能力
  - 需要在 V1.2 前保持用户兴趣
  - 画布模块需要提前设计接口，避免 V1 架构不兼容
- 从老项目学习：
  - 保留交互逻辑（拖拽、连线、缩放手感）
  - 重做架构（避免单文件巨石）
  - 节点执行方式：实时执行（用户操作立即执行）
  - 支持循环节点（LoopNode）

## D010 应用市场采用中心化模式，人工审核

- 状态：已冻结
- 日期：2024-01-XX
- 背景：需要应用市场让开发者发布模块，用户下载安装。
- 决策：应用市场中心化设计，V1.5+ 实现
  - 中心化：官方服务器托管，不支持第三方源
  - 审核方式：人工审核（V1.5），自动化检查（V2.0+）
  - 下载权限：必须登录云端账号
  - 收费模式：V1 全部免费，V2.0+ 支持付费应用
- 理由：
  - 中心化保证应用质量和安全性
  - 人工审核初期质量高，后续自动化
  - 避免三方源带来的安全风险
  - 与云端账号系统集成
- 后果：
  - 开发者必须提交到官方市场
  - 审核周期可能较长（初期）
  - 无法安装未审核的应用（除非开发者模式）
  - 需要维护审核团队和流程
- 审核标准（V1.5）：
  - 代码安全性检查（无恶意代码）
  - 权限合理性检查（申请的权限必须有使用场景）
  - 视觉一致性检查（使用统一设计系统）
  - 功能完整性检查（不能是空壳应用）
  - 文档完整性检查（必须有使用说明）

## D011 官方 Provider 采用积分制，按类型计费

- 状态：已冻结
- 日期：2024-01-XX
- 背景：云端账号需要提供官方 Provider 能力，使用积分消耗。
- 决策：积分计费模式（V2.0 实现）
  - 文本生成：按 token 数量 * 倍率计算积分
  - 图片生成：按张数计算积分
  - 视频生成：按秒数计算积分
  - 音频生成：按秒数计算积分
- 理由：
  - 透明计费，用户可预期成本
  - 不同类型资源成本不同，分别计费合理
  - 倍率可根据模型质量调整
- 后果：
  - 需要维护模型价格表
  - 需要实时计算和扣除积分
  - 需要积分充值系统
  - 需要用量统计和账单
- 自配置 Provider：
  - 用户自己配置的 Provider（自己的 API Key）无需积分
  - 云端账号和自配置 Provider 可并存
  - 默认优先使用自配置 Provider（排序第一）

## D012 Provider 支持同类型多配置和排序机制

- 状态：已冻结
- 日期：2024-01-XX
- 背景：用户可能有多个 OpenAI 账号，或同时使用官方 Provider 和自配置 Provider。
- 决策：支持配置多个同类型 Provider，通过排序和默认选择机制使用
  - 同类型多个：可配置多个 OpenAI、Claude 等
  - 排序机制：用户可拖拽调整 Provider 顺序
  - 默认选择：没有明确指定时，使用排序第一的 Provider
  - 手动选择：在需要选择模型的地方，用户可以明确选择 Provider
- 理由：
  - 灵活性：用户可以根据需要切换账号
  - 容错性：一个 Provider 失败可以切换到备用
  - 成本优化：可以配置免费额度的多个账号轮换使用
- 后果：
  - Provider 列表需要显示排序序号
  - 调用时需要明确使用哪个 Provider
  - 错误重试时可以尝试同类型其他 Provider
- UI 行为：
  - 系统功能（无选择界面）：使用默认排序第一个
  - 用户界面（有选择控件）：用户可以选择或使用默认

## D013 局域网协同需要简单认证和实时状态显示

- 状态：已冻结
- 日期：2024-01-XX
- 背景：局域网协同时需要识别用户身份，并实时显示在线状态。
- 决策：实现简单的用户名/密码认证
  - 认证方式：HTTP Basic Auth 或 JWT
  - 用户管理：主机创建临时账号或使用主机本地用户
  - 实时显示：WebSocket 连接，显示在线用户列表
  - 权限控制：远程用户只读模式，不能修改配置
- 理由：
  - 简单认证足够局域网场景
  - 无需复杂的 OAuth 或 SAML
  - 实时状态提升协同体验
- 后果：
  - 需要维护 WebSocket 连接
  - 需要心跳检测断线重连
  - 认证信息不加密（局域网内认为安全）
- 协同细节（V2.0）：
  - 画布协同：A 用户移动节点，B 用户实时看到
  - 指针显示：显示其他用户的鼠标指针和标记
  - 锁机制：编辑节点时锁定，其他用户只读
  - 冲突解决：CRDT 或 OT 算法（待设计）

## D014 模型分类标签内置维护，不自动提取

- 状态：已冻结
- 日期：2024-01-XX
- 背景：需要给模型打标签（文本/图片/视频/音频），供不同场景使用。
- 决策：模型分类标签由 Provider 适配器内置维护
  - 标签类型：`text-generation`、`image-generation`、`video-generation`、`audio-generation`、`text-to-image` 等
  - 维护方式：在 Provider 适配器代码中硬编码
  - 不自动提取：不从 Provider API 的 metadata 自动提取（大多数 Provider 没有统一格式）
- 理由：
  - 各 Provider 的模型能力描述格式不统一
  - 自动提取容易出错，需要人工校准
  - 内置维护保证准确性
  - 模型能力相对稳定，不需要频繁更新
- 后果：
  - 新模型发布后需要更新适配器代码
  - Provider 适配器需要维护模型能力映射表
  - 用户无法自定义模型标签（V2.0 可支持）
- 示例：
  ```rust
  // OpenAI 适配器中维护
  match model_id {
      "gpt-4" | "gpt-3.5-turbo" => vec![Capability::TextGeneration],
      "dall-e-3" => vec![Capability::ImageGeneration],
      "whisper-1" => vec![Capability::AudioToText],
      _ => vec![],
  }
  ```

## D015 模块更新自动推送，图标显示版本提示

- 状态：已冻结
- 日期：2024-01-XX
- 背景：应用市场上的模块更新后，需要通知用户。
- 决策：自动检测更新并推送通知
  - 检测频率：每次启动 + 每天一次后台检测
  - 通知方式：图标小红点 + 版本号显示
  - 更新方式：用户手动点击更新（不自动静默更新）
  - 更新提示：显示更新日志（Changelog）
- 理由：
  - 自动推送让用户及时获得新功能
  - 手动更新给用户控制权
  - 避免静默更新带来的兼容性问题
- 后果：
  - 需要维护模块版本比对逻辑
  - 需要显示 Changelog 的 UI
  - 需要处理更新失败的回滚
- 更新流程：
  1. 后台检测到新版本
  2. 图标显示小红点，版本号变化
  3. 用户点击查看更新日志
  4. 用户确认更新
  5. 下载新版本模块
  6. 热重载模块（无需重启）

## D016 Skills 定位为官方优先的本地技能中心

- 状态：已冻结（产品定义；具体接口、物理表和执行权限细节须在实现前完成技术评审）
- 日期：2026-10-27
- 来源：用户明确要求“自己的官方内置 Skills 分类库、内置部分技能、预置大型第三方来源、供本地不同应用场景使用”，并确认本地技能中心方案。
- 背景：旧版 V1-FR-002 依赖单个硬编码远程地址，把技能等同于 HTTP/CLI 工具包，无法表达官方内置内容、Agent Skills 与多场景使用。
- 决策：以 `SKILL.md` 型 Agent Skills 为主，DGOS 统一分类和内容身份；核心官方技能随应用提供，官方精选保留第三方署名与许可，第三方生态通过预置适配器按需获取。来源预置不等于整站打包。
- 决策：目录、版本化本地内容、用户启用状态、应用/会话绑定、任务实际加载彼此独立；安装不执行脚本，已安装不等于已授权，运行任务固定内容版本。
- 决策：V1 先交付官方本地库与 AI 工作台使用闭环，再接入至少一个真实第三方来源；其他大型来源逐个验收，不以未部署官方服务或尚未验证接口作为启动条件。

## D021 MCP V1 客户端边界与安全默认值

- 状态：已冻结（V1-FR-003 实施基线）
- 日期：2026-10-27

## D027 模块包发布采用可恢复文件状态机

- 状态：已冻结（FR-004 开工前边界）
- 日期：2026-10-28
- 决策：模块安装/更新必须依次经过 `staged → validated → switched → committed`；失败进入 `recovery_pending`，启动时依据数据库当前指针和文件校验恢复旧版本或禁用模块。数据库事务只提交当前版本指针和更新事件，不替代文件暂存、fsync、原子目录切换、回滚和孤儿文件清理。
- 决策：新 artifact 未通过 manifest、版本、完整性和来源验证时不得写入当前版本指针；旧版本在新版本可启动前保留。热更新必须可重复执行且不自动重放模块副作用。

## D028 V1 模块信任范围与验收边界

- 状态：已冻结（FR-004 开工前边界）
- 日期：2026-10-28
- 决策：V1 首期只验收内置或宿主已发布的受信任模块包；模块加载、卸载、热更新和 Error Boundary 不等于安全隔离。AC 中的“崩溃隔离”仅表示 UI/宿主故障影响范围，安全隔离另列为后续执行边界工作。
- 决策：在 D025/D026/D027 的实现和集成测试完成前，不开放远程入口 URL、通用模块 IPC、模块市场或任意第三方 JavaScript。

## D029 模块 manifest 是能力上限，授权 broker 只授予交集

- 状态：已冻结（FR-004 包发布与 Host API 收口）
- 日期：2026-10-28
- 决策：模块 manifest 声明的能力集合是该 artifact 的静态上限；`module_permissions` 中的用户授权只能授予 manifest 已声明且属于 D006 规范集合的能力。更新到声明集合变化的版本时，宿主必须重新校验并按版本策略要求重新授权；旧授权不得扩大新包的能力。
- 决策：`ModulePermissionRepository` 只负责持久化授权、撤销和脱敏审计，不负责构造模块身份或安装包。只有发布器完成 manifest、版本、artifact 摘要和允许来源校验后，模块行才能参与 Host Capability API 的身份验证。
- 影响：未声明的能力在 grant 和实际 dispatch 两处均 fail-closed；任何 renderer、Skill 文本、模型输出或通用 IPC 都不能扩大 manifest 能力集合。

## D030 Application Service 是跨入口用例编排边界

- 状态：已冻结（V1 前置架构优化）
- 日期：2026-10-28
- 决策：Tauri command、未来 LAN handler 和模块 runtime 不直接组合 Repository、Capability Gateway 与 Domain Manager；跨入口业务流程必须通过 transport-independent Application Service / Use Case。Transport 只解码业务 DTO、绑定宿主上下文并映射协议错误；Application Service 负责用例编排、授权调用、幂等/取消/审计和错误语义；Domain Manager 继续负责资源归属、状态机和领域不变量。
- 决策：先从 Provider 调用和模块发布两个高风险路径抽取最小服务；不得以一次性重写所有 Manager 为前提，也不得把当前已抽取的服务误认为全部应用服务层已完成。
- 影响：`dgos-application` 是该层的实现归属；`src-tauri` 只保留状态 wiring 和 transport adapter。新增 Skills/MCP/Workbench/LAN 入口必须复用该边界，不能创建旁路授权或用户身份参数。

## D031 模块发布互斥采用可恢复 lease（提议中）

- 状态：提议中（需在下一切片冻结后再作为实现依据）
- 日期：2026-10-28
- 背景：当前发布器已在实例 mutex 外增加 `module_release_locks` 数据库 lease，可保护两个独立 Publisher 的正常并发；但 TTL 过期、进程强杀、释放失败和跨平台 SQLite 锁语义尚未形成稳定契约。
- 提议：V1 先保持全局 `modules` 发布锁，避免不同 Publisher 同时改写版本目录、current pointer 和 DB 指针；每个发布操作带唯一 `operation_id` 与随机 `owner_id`。lease 必须支持续租，续租失败或发现 owner 不再持有 lease 时停止提交并进入 `recovery_pending`；旧 lease 过期后由下一次操作清理。释放失败只记录告警，不覆盖原始发布结果。
- 提议：发布按 `(module_id, version, integrity)` 幂等；相同摘要的重复请求返回既有结果，不同摘要不得覆盖同一版本。lease 只提供操作互斥，不替代文件系统 fsync/rename、DB 事务或启动恢复。
- 验证要求：等待未过期 lease、过期 lease 清理、错误 owner 不能释放、强杀后恢复、重复发布、DB/指针故障注入，以及 macOS/Windows/Linux 的 SQLite/文件系统行为分别验证；在这些证据前不得宣称跨进程 crash consistency 完成。

## D032 模块可信注册只能来自发布应用服务（提议中）

- 状态：提议中（需在 FR-004 runtime 开工前冻结）
- 日期：2026-10-28
- 背景：`ModulePermissionRepository::register_module` 目前仍是公开 Rust API；虽然 Host Capability Service 会再次校验 Publisher 的包身份，但普通 crate 调用方仍可直接写入模块注册行，容易把数据库登记误认为可信身份。
- 提议：Repository 仅保留面向发布服务的内部注册端口，输入使用已验证的 `StagedPackage`/发布结果，而不是任意 `id/version/integrity/manifest` 字段。模块执行上下文只能由 Publisher 在当前用户会话下构造；不再暴露接受任意 `user_id` 和 `module_id` 的公共铸造函数。测试通过专用 test fixture 或受控内部构造，不扩大生产 API。
- 验证要求：无法从 renderer、Skill、模型输出或普通应用服务伪造模块身份；发布、更新、禁用、撤权、重启恢复后，context 的 version/integrity 与实际包和 DB current pointer 始终一致。
