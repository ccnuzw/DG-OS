# V1 需求编号管理

本文档管理 DGOS V1 版本的所有需求编号，确保编号的稳定性和可追溯性。

---

## 1. 编号规则

### 1.1 功能需求编号

**格式**：`V1-FR-XXX`

- `V1`：版本号
- `FR`：Feature Requirement（功能需求）
- `XXX`：三位数字，从 001 开始

**示例**：
- `V1-FR-001`：Provider 适配框架
- `V1-FR-002`：DGOS 技能中心
- `V1-FR-010`：局域网协同

### 1.2 非功能需求编号

**格式**：`V1-NFR-XXX`

- `NFR`：Non-Functional Requirement（非功能需求）

**示例**：
- `V1-NFR-001`：启动时间 < 2 秒
- `V1-NFR-002`：API 响应时间 P95 < 200ms

### 1.3 E2E 测试编号

**格式**：`V1-E2E-XXX`

**示例**：
- `V1-E2E-01`：完整的 Provider 配置流程
- `V1-E2E-02`：完整的 Skill 安装和调用流程（历史编号，非 D016 新门禁）

---

## 2. 编号稳定性原则

### 2.1 永不改变

编号一旦分配，**永远不改变**，即使：
- 功能名称修改
- 功能被取消
- 文档被移动

### 2.2 永不复用

即使功能被取消，编号也**永不复用**。

### 2.3 跳号允许

如果某个功能取消，编号可以跳号。例如：
- V1-FR-001：Provider 适配框架 ✅
- V1-FR-002：DGOS 技能中心 ✅
- V1-FR-003：~~画布编辑器~~（取消，移到 V1.2）
- V1-FR-004：模块系统 ✅

## 6. 编号分配流程

### 6.1 申请新编号

**步骤**：
1. 查看本文档，找到下一个可用编号
2. 在对应表格中添加一行
3. 创建功能规格文档
4. 提交 PR，包含本文档的更新

**示例**：
```markdown
| V1-FR-011 | 新功能名称 | P1 | 规划中 | @developer | [文档链接] |
```

### 6.2 编号冲突

如果多个 PR 同时申请编号导致冲突：
1. 先合并的 PR 保留编号
2. 后合并的 PR 使用下一个编号
3. 更新本文档

## 7. 功能状态定义

| 状态 | 说明 | 下一步 |
|------|------|--------|
| **规划中** | 需求已提出，待创建规格 | 创建功能规格文档 |
| **✅ 规格完成** | 功能规格文档已完成 | 评审通过后进入开发 |
| **开发中** | 正在开发实现 | 完成开发和测试 |
| **测试中** | 开发完成，正在测试 | 通过所有测试 |
| **✅ 已完成** | 测试通过，已交付 | 部署上线 |
| **❌ 已取消** | 功能取消 | 归档文档 |

## 11. 常见问题

### Q1: 编号可以修改吗？

**A**: 不可以。编号一旦分配，永远不变。

### Q2: 功能取消后编号怎么办？

**A**: 保留编号，标记为"已取消"，永不复用。

### Q3: 编号跳号怎么办？

**A**: 允许跳号。例如 FR-001、FR-002、FR-004（FR-003 被取消）。

### Q4: 如何避免编号冲突？

**A**: PR 提交前查看最新的本文档，使用下一个可用编号。

### Q5: 功能名称变了怎么办？

**A**: 更新功能规格文档和本文档的"功能名称"列，编号不变。
