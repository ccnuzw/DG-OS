# V1 需求编号管理

本文登记 V1 功能需求、非功能需求和 E2E 场景的稳定编号。功能实现状态只在 [V1 实现状态](../../02-产品与版本/当前版本/V1-实现状态.md) 维护。

## 1. 编号规则

### 1.1 功能需求

格式为 `V1-FR-XXX`，其中 `XXX` 为三位数字。编号分配后不更改、不复用；取消的需求保留原编号并标注为已取消。V1 当前已分配 `V1-FR-001` 至 `V1-FR-010`；`V1-FR-011` 至 `V1-FR-015` 已保留给路线图中的后续版本功能，不得用于新增 V1 功能。新增 V1 功能从 `V1-FR-016` 起按顺序分配，并先核对版本路线图及本表。

### 1.2 非功能需求

格式为 `V1-NFR-XXX`。如新增、变更或取消 NFR，也须保留已分配编号并同步更新其权威规格来源。

### 1.3 E2E 场景

格式为 `V1-E2E-XX`。V1 已登记 `V1-E2E-01` 至 `V1-E2E-10`；场景定义及验收以对应功能主规格为准。调整场景不重新分配或复用已用编号。

## 2. 编号稳定性

- 编号一经分配，功能改名、文档迁移或需求取消均不改变编号。
- 取消编号不复用；允许因取消而跳号。
- 本文不以示例方式占用当前已分配或预留的编号。
- 跨版本需求使用对应版本前缀；不要把 V1 编号改作 V2 编号。

## 6. 新编号分配

1. 核对[版本路线图](../../02-产品与版本/版本路线图.md)及本表，确认版本范围和下一个可用编号。
2. 对 V1 新功能从 `V1-FR-016` 起顺序分配；不得占用 FR-011 至 FR-015 的后续版本保留号。
3. 在本表登记编号、名称和主规格链接，并在对应主规格中记录相同 ID。
4. 发现并发申请冲突时，先合并者保留已分配编号，另一申请使用新的未分配编号；不得重编号或复用。

## 7. 跨版本编号

- 不同主版本使用各自前缀，例如 `V2-FR-001`，与 `V1-FR-001` 相互独立；V2 及以后版本在通过[版本进入开发门禁](../../02-产品与版本/版本进入开发门禁.md)前不分配正式编号。
- 不使用小数版本前缀（如 `V1.1-FR-001`）。
- 同一功能跨版本扩展时，保留既有版本需求，并为新版本交付范围分配新版本 ID；路线图负责说明演进关系。
- 版本路线图中的目标版本和范围优先于旧示例或历史计划。

- 功能实现状态与验证进度：见 [V1 实现状态](../../02-产品与版本/当前版本/V1-实现状态.md)。
