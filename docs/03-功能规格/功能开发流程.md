# 功能开发流程

本文档定义 DGOS 项目从需求到交付的完整功能开发流程，遵循 spec-docs-pro 规格驱动开发方法。

---

## 1. 流程概览

```
需求提出 → 功能规格 → 技术设计 → 开发实现 → 测试验证 → 验收交付
   ↓          ↓          ↓          ↓          ↓          ↓
  PRD      V1-FR-XXX   伪代码     编码+测试   验证记录    上线
```

---

## 2. 阶段 1：需求提出

### 2.1 需求来源

- 产品规划（版本路线图）
- 用户反馈
- 技术债务
- Bug 修复

### 2.2 需求评审

**输入**：需求描述

**输出**：
- 需求是否进入 V1？
- 优先级：P0/P1/P2
- 预估工作量

**检查清单**：
- [ ] 需求清晰，目标明确
- [ ] 有明确的用户价值
- [ ] 技术可行
- [ ] 不与现有功能冲突

---

## 3. 阶段 2：创建功能规格

### 3.1 分配功能编号

格式：`V1-FR-XXX`

**示例**：
- V1-FR-001：Provider 适配框架
- V1-FR-002：Skills 管理系统
- V1-FR-0XX：新功能（V1 新功能从 V1-FR-016 起分配，FR-011～015 已保留，见需求编号文档）

**规则**：
- 编号一旦分配，永不改变
- 即使功能取消，编号也不复用
- 记录在 [00-V1需求编号.md](V1/00-V1需求编号.md)

### 3.2 创建功能规格文档

使用模板创建文档：

仓库内没有模板文件。按[功能文档规范](功能文档规范.md)的章节结构新建文档，也可使用 spec-docs-pro skill 自带的 `templates/feature-main.md` 模板。

**文档位置**：根据功能所属领域选择目录
- `01-底层能力/`：框架级功能
- `02-应用模块/`：用户界面功能
- `03-系统功能/`：系统级功能

### 3.3 填写功能规格

按照 [功能文档规范](功能文档规范.md) 填写：

1. **功能元信息**（必须）
   - 功能编号、名称、版本
   - 优先级、风险级别
   - 依赖关系

2. **功能概述**（必须）
   - 一句话描述
   - 详细说明
   - 功能边界（包含 + 不包含）

3. **核心流程**（必须）
   - 用户操作流程
   - 系统处理流程
   - 异常处理流程

4. **数据模型**（必须）
   - 涉及的数据表
   - 读写关系

5. **验收标准**（必须）
   - AC 逐项测试设计表
   - Given/When/Then 格式
   - 测试层级和目标命令

6. **接口设计**（必须）
   - Tauri Commands
   - HTTP API（如有）

7. **技术设计**（如需要）
   - 伪代码
   - 分支追踪 ID（B01-01、B01-02 等）
   - 分支到测试追踪表

8. **实现与验证**（开发时填写）
   - 验证记录
   - 通过情况

### 3.4 评审功能规格

**评审人**：技术负责人 + 相关开发者

**检查清单**：
- [ ] AC 表完整，每个 AC 有明确的测试方式
- [ ] 功能边界清晰
- [ ] 依赖关系明确
- [ ] 接口设计合理
- [ ] 如有技术设计，分支追踪完整

**输出**：
- 评审通过 → 进入开发
- 需要修改 → 修改后重新评审

---

## 4. 阶段 3：技术设计（如需要）

### 4.1 何时需要技术设计

**必须创建技术设计**：
- 涉及金钱、权限、加密
- 复杂并发场景
- 外部系统回调
- 复杂状态机

**可以省略技术设计**：
- 简单 CRUD
- 纯 UI 变更
- 配置项调整

### 4.2 技术设计内容

在功能规格的"第 7 章 技术设计"中添加：

1. **核心设计**
   - 架构图
   - 关键类/模块设计

2. **伪代码**
   - 标注分支 ID（`// B01-01`）
   - 关键分支都要标注

3. **分支到测试追踪表**
   ```markdown
   | 分支编号 | 分支描述 | AC 映射 | E2E 映射 | 风险级别 |
   |---------|---------|---------|---------|---------|
   | B01-01  | 查询配置 | AC01    | V1-E2E-01 | 低 |
   | B01-04  | 重试逻辑 | AC09    | -       | 🔴 高 |
   ```

4. **并发场景说明**（如需要）
   - 冲突点
   - 控制方式
   - 预期行为
   - 失败策略

### 4.3 决策记录

**如果遇到冲突或需要做重要决策**：

1. 创建冻结决策记录
   ```markdown
   # 在 docs/06-决策记录/V1-冻结决策.md 中添加

   ## D0XX <决策标题>

   - 状态：已冻结
   - 日期：YYYY-MM-DD
   - 背景：为什么需要这个决策
   - 决策：选择了什么方案
   - 理由：为什么选择这个方案
   - 后果：影响和约束
   ```

2. 在功能规格中引用决策
   ```markdown
   Provider 排序机制（引用 **D012**）：
   - 用户可通过拖拽排序
   - 排序第一的作为默认选择
   ```

**符合 spec-docs-pro 规则 4**：冲突先决策后编码

## 5. 阶段 4：开发实现

### 5.1 创建开发分支

```bash
git checkout -b feature/v1-fr-0xx-new-feature
```

**分支命名规则**：
- `feature/<feature-id>-<description>`
- 全部小写，使用连字符

### 5.2 TDD 开发（推荐）

1. **先写测试**
   ```rust
   #[cfg(test)]
   mod tests {
       #[test]
       fn test_provider_retry() {
           // Given
           let provider = create_test_provider();
           
           // When
           let result = provider.call_with_retry();
           
           // Then
           assert!(result.is_ok());
       }
   }
   ```

2. **再写实现**
   ```rust
   pub async fn call_with_retry(&self) -> Result<Response> {
       let mut attempts = 0;
       // 实现重试逻辑
   }
   ```

3. **运行测试**
   ```bash
   cargo test -p dgos-providers
   ```

### 5.3 开发过程

**后端**（仓库根目录）：
```bash
cargo build
cargo test --offline --workspace
cargo clippy --workspace
```

**前端**（仓库根目录）：
```bash
npm run dev
npm test
npm run build
```

项目尚未配置 ESLint，没有 lint 脚本。Apple Silicon 上 Rust 链接失败时，见[工程与本地环境](../01-项目概览/工程与本地环境.md)的 arm64 环境变量。

### 5.4 提交规范

遵循 [Git 提交信息规范](../01-项目概览/Git提交信息规范.md)：

```bash
git add .
git commit -m "feat(providers): add retry mechanism

Implement exponential backoff retry for 429 and 5xx errors.

Refs: V1-FR-001"
```

## 6. 阶段 5：测试验证

### 6.1 单元测试

**后端**：
```bash
cargo test --offline -p dgos-providers --lib
```

**前端**：
```bash
npm test -- --run tests/providers.test.tsx
```

**要求**：
- 核心功能单元测试覆盖率 > 60%
- 所有 AC 都有对应的测试

### 6.2 集成测试

```bash
cargo test --offline -p dgos-providers --test tool_chat
```

**要求**：
- API 集成测试覆盖率 > 80%
- 测试真实场景，不只是 mock

### 6.3 E2E 测试

当前项目没有 E2E 测试框架，也没有 `test:e2e` 脚本；功能规格中的 E2E 资产均为规划。建立框架后在此补充命令。

**要求**：
- 关键用户流程有 E2E 覆盖
- 测试完整的用户操作路径

### 6.4 填写验证记录

按 AGENTS.md，实现状态和验证证据以 [V1 实现状态](../02-产品与版本/当前版本/V1-实现状态.md) 为准；功能规格第 10 章写验证目标，需要时可附证据摘要并链接实现状态。记录格式示例：

```markdown
#### 2026-10-26 后端单元测试

\`\`\`bash
cargo test --offline -p dgos-providers --lib
\`\`\`

**状态**：🟢 通过

**通过情况**：14/14 通过

**详细覆盖说明**：
- ✅ AC01: Provider 正常创建（包含数据库保存、模型列表自动获取）
- ✅ AC02: API Key 无效检测（401 错误处理）
- ✅ AC09: 429 错误重试（指数退避 1s、2s、4s）
- ...

**遗留工作**：无
```

**符合 spec-docs-pro 规则 6**：AC 必须可执行且可追踪

## 7. 阶段 6：验收交付

### 7.1 冒烟测试

**在真实环境中验证**：

```bash
# 启动应用
npm run tauri:dev

# 执行完整用户流程
# 1. 配置 Provider
# 2. 测试连接
# 3. 调用 API
# 4. 查看使用记录
```

**要求**：
- 功能正常工作
- 无明显 Bug
- 性能可接受

### 7.2 代码审查

**创建 Pull Request**：
```bash
git push origin feature/v1-fr-011-new-feature
# 在 GitHub 创建 PR
```

**PR 检查清单**：
- [ ] 代码通过 CI 检查
- [ ] 所有测试通过
- [ ] 代码符合规范
- [ ] 添加了必要的注释
- [ ] 更新了相关文档

**审查要点**：
- 代码质量
- 测试覆盖
- 文档完整性
- 安全性

### 7.3 合并到主分支

审查通过后合并：

```bash
# Squash merge（推荐）
git checkout main
git merge --squash feature/v1-fr-011-new-feature
git commit -m "feat(module): add new feature (V1-FR-0XX)"
git push origin main
```

### 7.4 更新实现状态

在 [V1 实现状态](../02-产品与版本/当前版本/V1-实现状态.md) 中更新：

```markdown
| V1-FR-0XX | 新功能（示例） | 🟢 核心实现完成，待验收 | 见下方验证证据 | @developer | 列出已执行命令与未覆盖范围 |
```

状态必须有可复现的验证证据支撑，不写无依据的百分比。

**符合 spec-docs-pro 规则 8**：状态只在实现状态维护

## 8. 特殊情况处理

### 8.1 功能取消

如果功能在开发过程中被取消：

1. 停止开发
2. 关闭相关分支
3. 在功能规格文档顶部标注：
   ```markdown
   > ⚠️ **已取消**：此功能已取消，原因：XXX
   ```
4. 移动文档到 `99-历史归档/`
5. 编号不复用

**符合 spec-docs-pro 规则 10**：归档不删除

### 8.2 功能变更

如果功能需求发生重大变更：

1. 创建新的冻结决策记录变更原因
2. 更新功能规格文档
3. 在文档中添加变更记录：
   ```markdown
   ## 变更记录
   
   | 日期 | 变更内容 | 变更人 |
   |------|---------|--------|
   | 2026-10-26 | 修改重试次数从 5 次改为 3 次（引用 D0XX） | @developer |
   ```

### 8.3 紧急 Bug 修复

如果是紧急 Bug：

1. 创建 hotfix 分支
   ```bash
   git checkout -b hotfix/provider-crash
   ```

2. 快速修复并测试

3. 创建 PR，标注为 hotfix

4. 审查通过后立即合并

5. 后续补充功能规格和测试

## 9. 质量标准

### 9.1 代码质量

- ✅ 通过 lint 检查（clippy；前端 ESLint 尚未配置）
- ✅ 通过格式检查（rustfmt；前端 Prettier 尚未配置）
- ✅ 无编译警告
- ✅ 单文件 < 1000 行

### 9.2 测试质量

- ✅ 核心功能单元测试覆盖率 > 60%
- ✅ API 集成测试覆盖率 > 80%
- ✅ 关键流程有 E2E 覆盖（E2E 框架建立后适用）
- ✅ 所有 AC 都有对应测试

### 9.3 文档质量

- ✅ 功能规格完整
- ✅ AC 表完整
- ✅ 验证记录已填写
- ✅ 代码注释清晰

## 11. 常见问题

### Q1: 什么时候创建功能规格？

**A**: 在开发开始之前。功能规格是开发的输入，不是事后补充。

### Q2: 技术设计可以省略吗？

**A**: 简单功能可以省略，但涉及金钱、权限、并发的必须有技术设计。

### Q3: 验证记录什么时候填写？

**A**: 开发完成、测试通过后立即填写，不要等到最后。

### Q4: 功能规格可以修改吗？

**A**: 可以修改，但要记录变更历史，并通过冻结决策记录重大变更。
